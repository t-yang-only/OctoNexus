## 0. 定位速览

| | octopus | api-monitor (MIT) | litellm |
|---|---|---|---|
| 本质 | 个人 LLM API 聚合网关 | AI API 运维监控控制台 | 100+ 供应商 SDK + 企业级网关 |
| 语言/栈 | Go+gin+gorm / React | Go+chi?/PostgreSQL+Redis / React | Python+FastAPI / Postgres+Redis |
| 部署 | 单二进制 | 双服务(api+worker)+PG+Redis | 重型,可选企业版 |
| 上游视角 | 渠道凭据→转发 | 普通用户账号→只读监控 | deployment→路由池 |
| 用户模型 | 单管理员 | 管理员+多监控目标 | 团队/key/预算多租户 |

litellm 与 octopus 同赛道但体量差两个数量级，**借鉴其"决策算法"而非架构**；api-monitor 与 octopus 互补（监控面 vs 转发面），**可整体移植其"监控-规则-通知"三层设计**且同为 Go、体量小。

## 1. 差距清单（octopus 缺什么）

### G1 通知与告警（双方都有，octopus 全无）★最高价值
- octopus 现状：渠道进冷却、成员耗尽、上游报错 → 只写 DB 日志，管理员必须盯页面。
- api-monitor：规则引擎（作用域：全局/类型/分组/实例/资产；条件：余额/额度/过期/健康/目录变化）+ 通知渠道（钉钉/飞书/企微/Webhook/SMTP/SMS），发送前可真实测试 payload。
- 借鉴：新增 `internal/notify/`（channel 抽象，先做 webhook + SMTP 两实现）+ `model.Setting` 里存规则；事件源现成——`publishGroupEvent`、relay 冷却进入、渠道健康检查失败。

### G2 上游余额/额度/公告监控（api-monitor 独有）
- octopus 用户大量使用 new-api/sub2api 类中转站渠道，上游余额耗尽 = 静默降级。
- api-monitor 用"普通用户账号"（非 admin）即可拿余额、额度窗口、公告、倍率。
- 借鉴：渠道模型加"监控凭证"位（与转发 key 分离），后台 task 定期拉余额，低于阈值走 G1 告警；内容源用指纹 diff 只报真实变化。

### G3 凭据静态加密（api-monitor 有，octopus 无）★安全红线相关
- octopus：`ChannelDetailGet` 注释自证凭据明文入库；备份 JSON 直接转储明文 key（台账 `T-sec-001` 的根因之一）。
- api-monitor：`APP_SECRET` 派生 AES-GCM 加密上游密码/token/webhook secret。
- 借鉴：config 加 `security.secret`，入库前 AES-GCM，出库仅在 relay 组装请求时解密；备份导出默认脱敏。

### G4 路由策略（litellm 丰富，octopus 仅优先级+冷却+亲和）
- litellm `router_strategy/`：`lowest_cost`、`lowest_latency`、`least_busy`、`lowest_tpm_rpm(_v2)`、`tag_based`、`adaptive/complexity/quality_router`（LLM 分类选模）。
- octopus 的 GroupMode 是枚举（manual/failover），加策略只需扩枚举 + `pickGroupItem` 分支；成员统计（时延、成功率、成本）relay 已全部在记。
- 借鉴优先级：先 `lowest_cost`（数据现成），再 `lowest_latency`；`complexity_router` 这类 LLM 决策对个人网关过重，暂缓。

### G5 Key 级限流（litellm 有，octopus 只有 MaxCost 硬顶）
- litellm：`max_budget_limiter`、`parallel_request_limiter`（RPM/TPM，Redis 或内存 DualCache）。
- octopus：单进程内存分片 cache 可支撑本地计数，无需 Redis——按 APIKey 做 RPM/TPM 滑窗是自然延伸。

### G6 周期性健康探测（litellm health_state_cache / api-monitor scan worker）
- octopus：协议探测仅在"拉取模型"时手动触发（NM-CUR-011）；冷却中成员靠请求流量恢复探测。
- 借鉴：复用 `internal/task` ticker 注册空闲期探测（低频、最小请求），失败/恢复接入 G1 告警。

### 明确不借鉴
- litellm 的 Redis 双缓存、多租户团队/SSG、guardrails、A2A/MCP 网关：与"个人、单二进制、轻"定位冲突。
- api-monitor 的独立 worker 进程 + PG + Redis 部署形态：octopus 用 task 包内协程即可。
