# T-hedge-001 首字竞速（高峰期 / 冷启动时并发请求置顶多个成员，取最快首字）设计稿

日期：2026-09-16　来源：用户指令（2026-09-16）「在高峰期，或者在突然唤醒开始调用的时候，同时在选择的分组里面请求置顶的多个 API，得到最优的首字」
关联：R-hedge-001（需求登记）、T-route-003/004/005/006/007（选路策略族）、`internal/relay/handler.go` 的转发轮次。

## 1. 要解决的问题

现有转发每轮只挑**一个**成员，等它的首个有效响应（非流式=完整响应，流式=首个事件）；挑中的成员若正在慢启动（上游排队、跨洋链路抖动、
或高峰期被限速），客户端就要一直等到该成员的整响应/首事件超时（默认 120s / 30s）才会切下一个成员。冷启动尤其明显：
第一个请求没有任何历史指标，选路只能靠 priority，慢成员会把整个请求按住。

目标：**在提交首字节之前**，允许并发向排序靠前的 N 个成员发起同一请求，取第一个给出有效响应的成员，其余立刻取消 —— 用少量额外上游调用换首字时延。

## 2. 与既有语义的边界（不可违背）

1. **首字节提交后不可切换**：向客户端写过任何一个字节之后，本次请求的成员即定局。竞速只能发生在提交之前，这与既有规则一致，不引入新的分支。
2. **失败/冷却语义不变**：落选的成员**不算失败**（是自己被取消的），不得计入 `recordRouteFailure`、不得因此进入冷却或扣成员指标；
   只有真正回错/超时的尝试才记失败。
3. **亲和/探测不变**：竞速胜出的成员走原有的 `recordRouteSuccess`（亲和延续、探针解除）。
4. **同一凭据不重复打**：竞速的候选必须来自**不同成员行**（必然不同的授权/凭据），不允许同一个凭据被并发打两次。
5. **触发条件必须可关闭、可观测**：默认关闭；触发与落选都要进日志与请求状态，便于事后算「多花了多少」。

## 3. 触发条件（两个独立开关，满足其一即竞速）

| 开关 | 配置键 | 含义 | 默认 |
| --- | --- | --- | --- |
| 慢启动（冷启动/高峰期被限速） | `hedge_after_ms` | 首选成员在 N 毫秒内未产出首个有效响应时，追加并发尝试 | 800 |
| 高峰期并发 | `hedge_peak_in_flight` | 该分组**在途请求数** ≥ 该值时，直接并发竞速（不等延迟） | 0（关闭）|

在途数取自分组维度的活动请求注册表（与 least_busy 同源口径：`RequestState.Sending` 且模型名=分组名），不引入新的计数泄漏面。

## 4. 竞速宽度与候选

- `hedge_width`：并发成员数上限，含首选；取值范围 2..5，默认 2。
- 候选顺序：沿用该分组当前模式（failover / lowest_cost / quality_first / lowest_latency / least_busy / lowest_tpm_rpm）的排序结果，
  **首选一定是该模式排序的第一名**，竞速只是把它后面 1..width-1 名提前发出去。
- 冷却中、不可用、额度归零的成员不参与竞速（口径与现有 `partitionCandidates` 一致）。
- 候选不足 width 时按实际数量并发（最少 2，否则退化为单发，不产生额外调用）。

## 5. 落选者处理（成本口径，必须写清）

- 胜出者确定后立即 `cancel` 其余尝试的轮次上下文（连接断开、上游通常按中断计费）。
- **成本提示**：竞速意味着同一份输入可能被 2..5 个上游各处理一次；上游若按 token 计费，可能按各自产出的 token 收费，
  最坏情况一次请求付 width 份钱。因此该功能默认关闭，且供应商侧「按次计费」的渠道更适合开启。
- 落选尝试**不计入**渠道/模型/凭据的成功与失败统计（避免污染质量与延迟指标）；只计入内部计数器 `hedge_spawned` / `hedge_lost` 供面板展示。

## 6. 配置面（分组级）

`GroupRelayConfig` 增补（写入 `groups.relay_config` JSON，向后兼容：老分组缺键即视为默认值）：

```json
{
  "hedge_enabled": false,
  "hedge_width": 2,
  "hedge_after_ms": 800,
  "hedge_peak_in_flight": 0
}
```

- 校验：`hedge_width` 2..5（越界按边界值归一）、`hedge_after_ms` ≥ 0、`hedge_peak_in_flight` 0..64。
- 前端：分组编辑面板「Relay 配置」区新增四个控件（开关 / 并发数 / 延迟阈值 / 在途阈值）+ 三语文案，
  并在界面标注「会产生额外上游调用与费用」。

## 7. 可观测性

- 请求状态新增字段（不影响对外结构）：本轮并发了几路、哪几路落选、各自的耗时。
- 日志：竞速开始与结束各一行（组名、宽度、首选 ID、胜者 ID、落选 ID 与耗时）。
- 统计：内部计数器按分组维度累计 `hedge_spawned`（额外发起的尝试数）与 `hedge_won_by_hedge`（非首选胜出次数），
  面板可据此判断「多花的钱是否换回了首字」。

## 8. 验证方案（**只用 mock，不打真实上游**）

mock 现有能力：模型名含 slow → sleep `MOCK_SLOW_SECONDS`（默认 15s），含 bad → 500，`mock-good` 正常，`/__control` 可运行期改行为。
用例（新建 `scripts/api-tests/run_hedge_test.py`）：

1. 关闭竞速（对照组）：分组 priority 上放慢成员 → 请求耗时应 ≈ 15s（整响应）或触发成员超时切换。
2. `hedge_after_ms=800` 开启：同一分组、同一成员顺序 → 请求应在 ~1s 内由次选（mock-good）返回；日志显示首选被取消、次选胜出。
3. `hedge_peak_in_flight=1` 开启：即使首选不慢，第二个并发请求也应立刻并行发起（用 mock 的 slow 行为验证两路并发存在）。
4. 默认关闭：不动 `hedge_enabled` 时行为与现在**完全一致**（用现有 failover 套件回归）。
5. 落选者不污染统计：竞速后检查落选成员的 `channel_model_stats` 失败计数不增加、质量样本不被记失败。
6. `width` 边界：1 或 9 提交后按 2..5 归一。

## 9. 分阶段

- 阶段 1（本轮）：配置面 + 排序候选提取 + 竞速执行 + 落选不统计 + mock 套件。
- 阶段 2：面板控件与三语文案；分组维度的 `hedge_spawned` 计数器上屏。
- 阶段 3（用户提出、后续）：权重模型 —— **包月 / 按次 / 余额 / 倍率 / 质量** 多维加权分配成员（见 §10 的口径草案）。

## 10. 后续权重模型口径草案（包月/按次/余额/倍率/质量）

现有模式各自只看一个维度（价格 / 质量 / 延迟 / 在途 / 近期消耗）。用户要的是**多维加权**：给每个成员算一个综合分，按分排序选路（并可复用竞速）。
草案：

| 维度 | 数据来源 | 方向 |
| --- | --- | --- |
| 包月（订阅额度剩余）| 渠道级配置（月额度、已用量、重置日）| 剩余越多越优先；用尽即降权（不直接剔除，避免误伤）|
| 按次（每次调用单价）| 渠道级配置（每调用价）| 越低越优先 |
| 余额 | 既有余额查询（`quota`） | 越低越降权（接近阈值直接剔除，沿用现有余额闸门）|
| 倍率 | 渠道配置的倍率系数 | 倍率越低越优先（等效价格放大）|
| 质量 | 既有成员质量样本（近期成败）| 成功率越高越优先 |

综合分 = Σ 维度权重 × 归一化取值，权重存设置项（`route_weight_*`），默认给一组保守值；缺数据的维度按中性值参与，不参与排序惩罚。
落地前需要一次口径确认（谁优先、是否允许「贵但快」压过「便宜但常错」），故列为阶段 3、等用户拍板后再动。
