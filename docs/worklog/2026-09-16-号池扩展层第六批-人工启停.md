# 2026-09-16 号池扩展层第六批：人工启停（toggle）与「谁把它关的」

## 1. 为什么补这一批

上一批公开说明过：官方账号池**不声明 toggle**，因为仓库里没有"渠道凭据级启停"的 op ——
启停这件事当时只能由号池同步按账号状态收敛。于是号池维护里少了一条最基本的动作：
"这条凭据今天不对，先别用它，但别删账号。"

补这一批时发现的问题比"缺一个接口"严重：**人工停用会被同步静默撤销**。
`OfficialPoolSync` 对 active 账号是无条件 `updates["enabled"] = true`，
所以任何"手工把 enabled 关掉"的做法，都会在下一次同步时被改回来 —— 界面上看起来
像是操作没生效。

## 2. 关键设计：Enabled 与 OperatorDisabled 分工

两列管两件事，混在一起就会互相覆盖：

| 列 | 回答的问题 | 谁在写 |
| --- | --- | --- |
| `enabled` | 这条凭据**此刻**参不参与选路 | 人工启停、渠道页保存、号池同步 |
| `operator_disabled` | **人工**要不要用它（决定本身） | 只在人工动作里写（号池 API / 渠道页） |

号池同步读到 `operator_disabled` 就跳过自动启用，并在结论里回 `held` 计数 ——
"有一条被你按住了"，而不是装作没有这条证据。

## 3. 改了什么

- `model.ChannelKey.OperatorDisabled`（新列，GORM 启动自动加，纯增量、默认 false = 老行为）；
- `op.SetChannelKeyEnabled(conn, channelID, keyName, enabled) (found bool, err error)`：
  一起写 enabled 与 operator_disabled，并刷新转发侧渠道缓存（授权没动，不刷分组）；
- `op.OfficialPoolSync`：`operator_disabled` 的凭据不再被自动启用，`Held` 计数；
  只读视图 `OfficialPoolStatusList` 的 member 加 `key_operator_disabled`；
- `syncChannelKeys`（渠道页保存）：提交启用位就是对这条凭据的最新人工决定 ——
  显式启用即解开人工停用，显式停用即落下人工停用。两个入口因此规则一致；
- `pool` 适配器声明 `CapToggle` 并实现 `SetEnabled`；条目 `detail.operator_disabled` 可见；
  账号存在但凭据还没物化时回 **409 conflict**（`pool.ErrConflict`，接口映射新增）——
  与 404 分开，外部工具才不会把"等同步跑完再来"误判成"这条是错的"。

## 5. 已知边界

- `toggle` 目前只对官方账号池有实现；其它后端（首批反代工具包）接入时按同一契约实现
  `Toggler` 即可，`pooltest` 会检查"声明了就必须实现"。
- 面板尚未加"人工停用"入口（渠道页那个开关就是它，语义已对齐）；号池页的启停按钮待面板批次。
