# 近期消耗最低选路（lowest_tpm_rpm / T-route-007 / NM-DS-014）

> 补齐路由策略族最后一块：`lowest_cost` → `quality_first` → `lowest_latency` → `least_busy` → `lowest_tpm_rpm`。
> 口径来自需求侧遗留项"lowest_tpm_rpm（需 Key 级 RPM/TPM 余量数据）"；本轮把它做成**可观察、可验证**的形态。

## 1. 口径（以及与 least_busy 的区别）

- 排序键：**窗口内 token 消耗升序 → 窗口内请求数升序 → priority 升序 → ID 升序**。
- 窗口：固定 60s（`memberLoadWindowMs`），与常见的 RPM/TPM 计量周期一致；写入时判定过期即开新窗口，
  没有后台协程、不落库、重启清零。
- **统计的是"尝试"而不是"成功"**：失败的尝试同样占用了上游连接与配额，必须计入负载。
- token 只在请求终态记一次（`state.go` 的 `finishLocked` 有 usage），归属到最近服务它的成员行；
  分轮重试时拿不到中间轮的 usage，故不会把每轮都算上（局限已写明）。
- 无记录的成员按 0 消耗参与排序（乐观先验，与 `quality_first` 的中性先验、`lowest_latency` 的 0ms 同哲学）。
- **与 least_busy 的分工**：`least_busy` 看"此刻在途"（窗口为 0），`lowest_tpm_rpm` 看"最近 60 秒已经消耗掉的量"——
  一个刚把大请求做完的成员会被让开，即使它此刻没有在途请求。
- **诚实边界**：上游真实的 RPM/TPM 限额我们并不知道（那是服务商的账）。这里排的是"我们自己最近往它发了多少"，
  作用是摊平负载、降低撞上游限流的概率，而不是严格意义上的"剩余额度最多者"。

## 4. 活体审计（`scripts/api-tests/run_rpm_test.py`，10/10）

装置：成员 `mock-slow`（上游 sleep 15s、priority 1）与 `mock-good`（正常、priority 2），同属渠道 `DS-TEST-mock`。
套件开头**删组重建**该分组，使成员行拿到新的 `GroupItem.ID`——负载按成员行聚合，于是进程内窗口天然干净，不必先等 60s。

## 6. 踩坑

- **进程内窗口让测试状态互相污染**：第一次跑该套件时，前一轮刚消耗过的成员仍在 60s 窗口里，
  "冷启动"断言直接反了（选中的是 `mock-good`）。解决办法不是加 sleep，而是**删组重建**拿到新的成员行 ——
  负载按成员行聚合，重建即等于清空该成员的窗口（比等 60s 更确定、更快）。
- **mock 必须能造出"token 消耗差异"**：原来的 mock 三个协议都返回固定 usage（11/7），
  于是两个成员在窗口内的 token 永远相同，"token 优先"根本无法验证。给 mock 的 `/__control` 加了
  `usage_scale`（按模型放大用量字段，递归处理 dict/list，SSE 也覆盖），才把这个口径测实。
- **别把"平手按 priority"当缺陷**：两边消耗相同时按 priority 决胜，效果就是在两个同样空闲的成员间交替，
  这是刻意的口径；测试里把它写成显式断言，而不是留着让人误判。

## 7. 未覆盖 / 后续

- 负载窗口固定 60s，没有按分组配置（与质量窗口 300s 一样先用常量；需要时再引入 `StrategyWindowSeconds`）。
- 只统计"我们观察到的消耗"，不知道上游真实限额，也没有把上游返回的 `429/Retry-After` 纳入负载模型。
- 分轮重试的中间轮 usage 拿不到，token 只记终态一次（口径已写在代码注释里）。
- 路由策略族至此齐全；再往上就是"按复杂度分级选路"（设计稿显式排除）与"上游限额自适应"，均需新数据源。
