# 2026-09-16 号池扩展层第十批：导出口径与列表一致 + 告警链路（"遇到问题通知我"）

## 背景
用户这轮的目标是"继续完成我的所有要求并测试，遇到问题通知我"，并给了一把 Server酱 SendKey。
上一轮已经把 Server酱 接成产品通知子系统的第六个渠道（真实推送已验证）；这一轮补两件**不需要用户拍板**的事：

1. 一个面板上看得见、又确实存在的口径缺陷：**导出的筛选口径与列表不一致**；
2. "遇到问题通知我"里属于**工具链**的那一半：套件失败时能不能主动通知到人。

## 一、导出口径与列表一致（T-pool-ext-010）

### 问题
`/api/v1/pool/export` 只读一个 `kind` 参数，其它筛选参数（q / provider / status / enabled / healthy /
has_expiry / expiring_within / sort / desc）全部被忽略；面板的导出按钮也只会传 kind。
结果就是：**屏幕上筛出来 5 条，点导出拿走一整个池子** —— 这种"看起来对、其实不是你要的那份数据"的缺陷，
比接口报错更难被发现。

### 改法
- `internal/pool/query.go`：`ExportRows(ctx, kind string)` → `ExportRows(ctx, filter Filter, now time.Time)`，
  内部复用列表那一条路径（同一个 `Filter.matches` + 同一个 `sortEntries`），只在最后一层换成扁平行；
- **导出不分页**：`Limit/Offset` 在导出里被忽略（导出就是"把当前筛选结果整个拿走"，分页只属于列表页）；
- 顺手统一了默认排序：`sortEntries` 的空排序（与 `kind`）从"只比 kind"改成 `kind → provider → name`
  三键比较器（`lessByKindProviderName`），**列表与导出共用同一个比较器** —— 否则同样一次筛选，
  面板看到的顺序与导出拿走的顺序会不一致（这正是新单测第一次跑就抓到的：`按状态: 第 0 行导出 "3" / 列表 "1"`）；
- `internal/server/handlers/pool.go`：`poolExport` 改用 `pool.ParseFilter(queryParams(c))`，与 `/pool/entries` 同一份解析；
- `web/src/api/pool.ts`：`poolExportURL(format, filter)` 带当前筛选（显式白名单，**不带 limit/offset**）；
  面板导出按钮从 `poolExportURL('csv', kind)` 改为 `poolExportURL('csv', filter)`。

### 测试
- 单测 `TestExportRowsHonoursTheSameFilterAsList`：七种筛选各跑一次"列表 vs 导出"，要求**逐条同序同 ID**
  （按名称子串 / 状态 / 启用位 / 有无到期时间 / 临期窗口 / 服务商 / 排序），再单独钉住"导出不受分页影响"；
- 活体套件 `run_pool_api_test.py` 新增 P15d/P15e/P15f：导出与列表逐条同序、导出遵守 q 过滤（只留命中的那一条）、
  CSV 导出同样遵守筛选（表头 + 恰好一行数据）。

## 二、告警链路：套件失败能通知到人（T-alert-003）

### 为什么单独做一条链路
产品自己的告警渠道（设置页那六个）要实例在跑、还得真的触发业务事件；而这轮用户要的是
**"你干活时出问题要告诉我"** —— 那是工具链的事：测试矩阵失败、实验翻车、批处理出错，
人不在电脑前也得立刻知道。

### 交付
- `scripts/api-tests/notify_problem.py`：把一条问题推到 Server酱。凭据**只从环境变量读**
  （`OCTOPUS_SERVERCHAN_SENDKEY`，测试时用 `OCTOPUS_SERVERCHAN_BASE_URL` 指向本地桩），不落仓库、不回显；
  退出码 = 语义：`0` 已投递（或 dry-run）、`1` 没配凭据、`2` 投递失败；
  **没配凭据时也要把要发的内容打印出来** —— 问题不许被静默吞掉；
  应答判定沿用产品那套（顶层 `code` 与 `data.errno` 都为 0 才算成功，非 2xx 也要把响应摘要带出来）。
- `scripts/api-tests/run_all.py`：
  - `--notify`（或 `OCTOPUS_NOTIFY_PROBLEM=1`）→ 有套件未通过时自动推一条（列出失败套件与读数）；
  - `--notify-selftest` → 只发一条"告警通道自检"并退出，用来验证**这条链路本身是通的**（不需要实例/mock）；
  - 推送失败只打印、**绝不改变矩阵的退出码**（告警是附加信息，不是结论）。
- `scripts/api-tests/run_notify_problem_test.py`（新套件 `notifyproblem`，10 例）：
  N1 dry-run 不发送；N2 未配置凭据退出 1 且打印内容；N3 走桩成功且 title/desp/tags 三件套到位；
  N3b 凭据不出现在输出里；N4 业务错误码（HTTP 200 + errno）判失败并带原文；
  N4b 网络不可达判失败并给出人话；N4c 直接喂**真实站点那两种应答**（本轮真的抓到 400
  `{"message":"[AUTH]错误的Key","code":40001,...}`）确认判定正确；
  N5 `run_all --notify-selftest` 走同一条链路；N5b 自检投递失败时退出码非 0（不假装成功）；
  **N6 全绿时不发任何推送**（绿的时候不许打扰人）。

### 本轮踩的坑（都已修）
- 子进程默认按 GBK 输出，被管道接住时中文变成替换字符 → 断言看到一堆 U+FFFD：
  **子进程要显式 `PYTHONIOENCODING=utf-8`，同时打印侧要 `errors="replace"` 兜底**（GBK 控制台遇 U+FFFD 会抛
  UnicodeEncodeError，把整个套件打断 —— 这个坑本会话第二次踩到，这次两个方向都堵上）；
- 桩里的表单 body 可能是字符串（百分号编码）也可能是 dict → 断言前统一还原（`form_text`）；
- 我第一版把"非 2xx"用例指向桩的另一个前缀，结果桩对任何 `.send` 都回成功 → 断言与事实不符：
  改成"网络不可达"活体用例 + 直接喂真实 400 报文的口径单测，两条加起来才真的覆盖了非 2xx。
