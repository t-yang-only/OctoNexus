# 2026-09-16 通知渠道新增 Server酱（ServerChan）—— "遇到问题通知我"的落点

## 1. 需求

用户给了一把 Server酱 SendKey（`SCT...`）并贴了 `serverchan-sdk` 的用法，要求"继续完成所有要求并测试，
遇到问题通知我"。仓库里既有的通知子系统已经有 5 个渠道（通用 webhook / 飞书 / 钉钉 / 企业微信 / SMTP），
这一轮就是把 Server酱 接进同一套框架，并把它作为"出问题主动告知"的实际出口。

## 2. 接口口径（按官方 Turbo/³ 实现，不引第三方 SDK）

- 推送入口：`POST https://sctapi.ftqq.com/<SendKey>.send`；
- 请求体是**表单**：`title` / `desp` / `tags`（不是 JSON —— 这是与既有四家最大的差别，所以新增 `postForm`）；
- 应答仍是"HTTP 200 包错误码"那一类：顶层 `code` 与 `data.errno` 都为 0 才算成功，
  否则把错误码与原文摘要带回去（沿用 `internal/notify` 的既有工程口径：不信任 200、失败不重试、不阻断调用方）。

## 3. 凭据处置（与 SMTP 密码同一考虑）

SendKey 本身就是凭据（它整条就是推送地址的一部分）：**优先读环境变量 `OCTOPUS_SERVERCHAN_SENDKEY`**，
没给才回落到设置表 `alert_serverchan_sendkey`；状态接口（`/setting/notify/channels`）只回"能不能发"，
永不回显 SendKey 本身（单测里专门钉了这条）。设置表的写入侧也加了校验：出现空白/斜杠/查询符当场拒绝
——否则等到真出事时会收到一条 404，而不是告警。

## 4. 新增/改动

后端：
- `internal/notify/channels.go`：`KindServerChan` + 渠道顺序 + `channelConfigState` + `deliver` 分支 +
  `sendServerChan`/`serverChanSendKey`/`serverChanEndpoint`；把 `postJSON` 拆成 `post` + `postJSON`/`postForm`；
  新增测试缝 `OCTOPUS_SERVERCHAN_BASE_URL`（生产不设即官方地址，套件借此把站点指到本地桩）。
- `internal/model/setting.go`：新增设置键 `alert_serverchan_sendkey`（含默认值与 `validateSendKey`）、
  `isNotifyChannel` 与错误提示补上 `serverchan`。

前端（面板「设置 → 通知渠道」）：
- `web/src/api/setting.ts`：设置键 + 渠道联合类型加 `serverchan`；
- `web/src/components/modules/setting/System.tsx`：渠道开关清单与设置键表各加一项，feishu/dingtalk/wecom
  那一行网格从 3 列改 4 列并加上 SendKey 输入框；
- 三语文案（zh_hans/zh_hant/en）：`setting.notify.kind.serverchan` 与 `setting.notify.serverchan`。

测试：
- 单测 `internal/notify/serverchan_test.go`（6 例）：表单形状与路径 `<SendKey>.send`、`data.errno`/
  顶层 `code` 非 0 判失败、未配置给缺项提示、环境变量优先于设置表、状态接口不回显 SendKey、测试投递覆盖它；
- 活体套件 `run_notify_audit.py`：新增 3 条用例（表单形状、业务错误码、未配置提示），并把渠道数 5→6；
- mock 上游新增 Server酱 推送桩（路径以 `.send` 结尾；sendkey 里含 `fail` 时回业务错误），
  所以套件全程只打本地桩 —— **不会把测试告警真的推送到用户手机上**。

## 5. 真实投递验证（一次性）

套件一律走本地桩；真实验证单独做一次：把 SendKey 写进本机实例的设置、勾选 serverchan，
然后调一次 `POST /api/v1/setting/notify/test`，确认用户手机收到一条来自 octopus 的推送。
这是"遇到问题通知我"这条要求的实际落地证据，跑完即保持启用状态（后续真的出问题会推送）。
