## 二、NM-CUR-022 排查报告复核结论

复核方法：逐条打开报告引用的源码位置核对（`handler.go` 转发循环 60–260 行、
`route.go pickGroupItem`、`state.go wait/markFailed/finishLocked/usageMetrics`、
`price.go UpdateLLMPrice/GetLLMPrice`、`op/llm.go LLMGet`、`task` 调度）。

### 2.1 报告写错的一条（重要，已推翻）

- **C-1「自动价格同步从不落库」不成立**。
  计费真正读的是 `price.GetLLMPrice`（`state.go:usageMetrics` 经 `op.LLMGet`？
  **否**——`usageMetrics` 直接调 `op.LLMGet` 读 `llmModelCache`（DB 回填），而
  `UpdateLLMPrice` 只刷新 `price` 包内存 `llmPrice` map，二者看似脱节。
  但 `handlers/model.go:189` 的价格管理页 + `channel.go:182` 建渠道定价读的是
  `price.GetLLMPrice`（内存新价），而 `op.LLMGet` 的 DB 缓存由 `LLMBatchSave`
  写入。核对结论：
  - 定时任务确实**不写 DB**（报告这半句是对的）；
  - 但"计费长期用旧价"**夸大了**：`usageMetrics` 用 `op.LLMGet`（DB 缓存），
    DB 缓存由首次 `InitCache` + 手动"重建价格"写入，定时同步的新价只影响价格页展示与新渠道定价。
  - 真实语义应为：**"定时价格同步只刷新展示层内存，计费口径的 DB 缓存需手动重建"**——
    是"语义割裂"（Medium），不是"计费 silently wrong"（Critical）。
  - 建议修复与报告一致（任务末尾接 `LLMBatchSave` 或明确语义），但等级降为 **Medium**。

### 2.2 确认成立（抽核通过，可直接立项修）

- **H-1 无可用成员时请求永挂**：成立。`handler.go` 三处 `request.wait` 循环
  （分组被删/无目标/授权缺失）在配置永久损坏时无总 deadline，只有客户端断开能解。
  建议：分组级 `max_total_seconds`（默认 300s）超时转 502。
- **H-2 双端口零超时配置**：成立。`server.go` 两 `http.Server` 无任何超时字段。
  建议：`ReadHeaderTimeout: 5s` 必加；relay 写超时按分组超时取大。
- **H-3 登录无速率限制 + bcrypt 烧 CPU**：成立（`op/user.go:UserVerify` + 无计数器）。
  建议：失败计数+指数退避；`Expire` 钳位到 [0, 30d]（溢出那半句属"纯自残但应钳位"，同意修）。
- **M-2 出站构造失败被记渠道故障**：成立（`handler.go` 错误分支统一 `ChannelStatsUpdate(RequestFailed=1)` +
  `recordRouteFailure`，未区分 `buildOutbound` 本地失败）。建议：本地失败直接 502，不记渠道失败。
- **M-4 定时任务无单飞保护**：成立（`task.go:runTask` 每 tick 起 goroutine）。
  建议：try-lock 跳过重叠执行。
- **M-6 备份导入不碰 relay 内存路由**：成立（`importDB` 只 `op.InitCache()`）。
  建议：导入后按 ID 集合调 `relay.ResetRouteState`。
- **M-8 JWT 密钥派生自用户名+密码哈希**：成立（与 NM-CUR-019 P0-1 同源）。
  建议：独立随机密钥 + `OCTOPUS_AUTH_SECRET` 覆盖。
