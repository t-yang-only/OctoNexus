# 转发报文 vs 探针报文对照：真实上游「探针能通、转发无首字节」的定性

日期：2026-09-16　执行：dsh-local（NM-DS-017 / 台账 T-diag-001）

## 1. 问题

真实渠道上出现一个矛盾现象：`POST /api/v1/channel/fetch-model`（probe=true，真实最小请求）能拿到 200 与协议位，
但同一模型经 relay 转发时长时间没有首字节（`first_byte_ms=-1`、`error=context canceled`，分组 `runtime.cooldowns` 里能看到该成员）。

本地看不到上游侧，但能回答一个更基础的问题：**我们自己的两条代码路径发出的请求是否不同**。若一致，则差异在上游侧。

## 2. 方法（新增 `scripts/api-tests/compare_probe_vs_relay_wire.py`，**只用本地 mock，不打真实上游**）

mock 上游会把每条收到的请求落进 `requests.jsonl`（method / path / model / body_keys / stream / 凭据指纹）：

1. 让后端对 mock 渠道跑一次三协议探针（14 条请求）；
2. 再分别用非流式与流式各转发一次；
3. 对比两者在路径、Header 组合（凭据指纹字段）、body 键集合上的差异。

## 3. 结果

| 观察项 | 探针路径 | 转发路径 |
| --- | --- | --- |
| 路径 | `/v1/models`、`/v1/chat/completions`、`/v1/responses`、`/v1/messages` | `/v1/chat/completions` |
| 凭据携带 | 与转发一致（同一套出站构造） | 同左 |
| Header 组合 | 1 种 | 1 种（两者相同）|
| body 键 | `[max_tokens, messages, model]`（探针不带 `stream`）| 客户端带了 `stream` 才带；**客户端不带时转发也不带**（mock 日志里 9 条这样的转发条目可证）|

即：**两条路径构造的请求在形状上等价**，转发并没有多带字段、也没有换 Header。

## 4. 结论

- 「探针能通、转发无首字节」不是由我们构造的请求差异造成的（该可能性已被上面的对照排除）。
  剩余解释只能是上游侧：站点对**并发/频次**的反应（本轮之前为验证确实对该站打过数百次探针请求，直连 chat 还拿到过
  Cloudflare `error code: 1010` 的浏览器指纹拦截），以及**冷却等待放大**（分组仅一个成员时，成员一进冷却，新请求会等冷却到期，客户端看到的就是长时间无首字节）。
- 因此这一项**不需要改代码**；要彻底定性需要授权打十来个真实请求（用户已要求空闲期不要用真实 API 做测试，故未做）。
- 顺带结论：竞速（T-hedge-001）在这种"单成员 + 冷却"场景下是有用的补充——多一个成员就能在延迟触发时立刻换人。

## 5. 同批补充：竞速套件补流式用例

`scripts/api-tests/run_hedge_test.py` 增加 T6：**流式**请求下竞速同样在提交首个 SSE 块之前生效。
实测 6/6：T6 首个 SSE 块 **0.8s** 由竞速胜出的快成员给出（上游侧确认慢、快两个成员都收到了尝试）。
