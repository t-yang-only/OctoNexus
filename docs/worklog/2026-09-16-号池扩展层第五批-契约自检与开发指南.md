# 2026-09-16 号池扩展层第五批：适配器契约自检工具包与开发指南

## 1. 为什么做这一批

前四批把"号池后端可插拔"这件事做完了：注册表、能力位、生命周期操作、查询面、批量、OpenAPI。
但**扩展性的真正瓶颈不是接口够不够多, 而是"别人照着写一个适配器要付多少成本"**:

- 接口写对了没有? 能力位声明和实现是否一致?
- 凭据会不会从条目里漏出去? 条目 ID 会不会重复(外部工具按 ID 操作会打错目标)?
- 列表给的 ID 用详情取不到、或者详情对不存在的 ID 不报错(上层会把"没了"显示成"活着")?

这些问题只靠人工读代码，第三者接入的成本就会高到没人接。所以这一批补的是**接入期就能发现问题**的手段。

## 2. `internal/pool/pooltest`——契约自检工具包

接入方的标准动作变成一行:

```go
func TestMyAdapterContract(t *testing.T) {
    pooltest.Run(t, &MyAdapter{})
}
```

检查项（每条都有反例测试，见 `pooltest_test.go`）：

1. `Kind` 非空、能力位合法且不重复、必须声明 `list`；
2. **声明了能力位就必须实现对应接口**（运行时会容忍并回 501，但那是给"先接只读、后补写"留的渐进口子，
   不是给接完就忘留的）；
3. 字段自描述：名字非空、不重复；
4. 条目身份：ID 非空且不重复、`kind` 回填成自己的 kind；
5. **凭据不外泄**：标了 `secret` 的字段名不许出现在 `Labels`/`Detail`（含嵌套一层）
   —— 标了 secret 是对外承诺"任何接口都不回显"，这条承诺要在条目层就守住；
6. 列表与详情一致：列表给的 ID 用 `Get` 必须取得到；不存在的 ID 必须报错；
7. `Entries` panic 兜成可读问题，不带走测试进程。

配套给 `internal/pool` 加了两个公开助手：`KnownCapability` / `AllCapabilities`
（外部工具与适配器作者校验能力位用，避免自己硬编码字符串）。

## 6. 附：stats 套件一条过强断言的修复（T-test-007，测试装置自身缺陷）

第五批回归时全量矩阵报 `stats 13/14`。失败的是我上一批自己加的那条
「已结算的上一小时：usage ≤ relay_logs（不加任何余量）」。

**根因**：那条断言依赖"usage 的桶只会丢、不会多"这个前提，而它不成立。跨小时归属是**双向**的：
骑在小时边界上的请求，在 usage 的桶（内存增量桶）与 relay_logs（落库时间戳）里会落进不同的小时，
差 1 个请求、量级就是它的 token。上一批的实证证据其实两种方向都出现过
（hour09=(−1,0,−11,−7)、hour10=(+1,0,+11,+7)）——我看过 +1 那一侧却按单向写了断言。

**修复**：settled 小时改用与当前小时同一条双向余量 `boundary_tolerance=(1,1,20,20)`，
并追加**反翻倍比例守卫**（usage 请求数/token 不得超过日志的 1.5 倍 + 2）——
真正要抓的"重复计入"是 2 倍量级，±1 的边界抖动抓不住它，两个判据各管一头。

**实证**：修复前 FAIL（hour=2026091610 usage=(284,14,5071,3158) vs relay_logs=(283,14,5060,3151)）；
修复后 14/14 通过，同一读数落在余量内且反翻倍守卫通过。
