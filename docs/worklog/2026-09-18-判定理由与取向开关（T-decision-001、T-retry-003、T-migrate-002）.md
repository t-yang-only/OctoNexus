一轮三件事，全部来自用户对 I0 待决清单的回复「我全都要」：

| 编号 | 事项 | 用户原话对应 |
| --- | --- | --- |
| T-decision-001 | 判定理由写进日志**和**响应头 | ①「判定理由写进日志/响应头」 |
| T-retry-003 | 400 类错误两种取向都要（可切换） | ④「400 类错误取向」 |

「我全都要」对 ④ 这种"二选一"的解读：**两种都要，做成开关**，默认仍是既有行为（不改变已上线语义），另一种随时可开。

## T-decision-001：这次为什么走了这个成员

在此之前日志只记「走了谁」（`target_channel`/`target_model`），回答不了**为什么是它**：是亲和期内沿用？是冷却到期被恢复探测放行？还是排序刚好轮到它？用户只能对着分组配置反推。

新增 `internal/relay/decision.go`（纯读，不参与选路）：

```
Decision{Mode, Tier, Reason, Slot, Attempt}
Text() → "mode=smart;tier=decision;reason=affinity;slot=1;attempt=2"
```

| 字段 | 含义 |
| --- | --- |
| `mode` | 分组模式（failover / manual / weighted / smart …） |
| `tier` | **仅 smart** 有：`decision`（复杂请求，走靠前成员）或 `execution`（简单请求，走靠后成员） |
| `reason` | 决定这次选择的机制：`manual` 人工指定 / `affinity` 亲和保持 / `probe` 冷却恢复探测 / `priority` 成员顺序 / `ranked` 综合排序 |
| `slot` | 成员在分组里的**顶层序号**（1 起；子分组整条链归它引用的那个顶层成员） |
| `attempt` | 第几轮（首字竞速多路并发算一轮，与面板「第几轮」同口径） |

三个出口共用同一份文本（`Decision.Text()`），避免"日志说亲和、响应头说顺序"的互相打脸：

- **响应头** `X-Octopus-Route: mode=failover;reason=priority;slot=2;attempt=2`（首字节提交前可反复覆盖，最终留下真正服务这次请求的那一份；竞速胜出后会按胜出者重算）；
- **历史日志** `relay_logs.decision`（面板日志接口/导出都能看到），导出新增「判定理由」列；
- **进程内状态流** `RequestState.decision`（在线卡片同样能看到）。

不含渠道名与凭据，只有模式/机制/序号/轮次——因此对把 Key 分发出去的场景也不泄露上游身份。

`reason` 的口径是「**谁决定了这次选择**」，不是"谁更好"：手动模式恒 `manual`（亲和/探测在手动模式恒为 0）；亲和未过期且当前成员就是它 → `affinity`；探针槽位指着它 → `probe`；故障转移且未开加权轮询 → `priority`；其余（加权/最低成本/质量/延迟/最空闲/近期消耗）→ `ranked`。

只读保证有单测守着：`DescribeDecision` 调一次不许改动路由状态（否则"看"这个动作本身会改变行为）。

## T-retry-003：请求本身非法时的两种取向

第 8 回合定的语义是「400/413/422 一类＝请求本身非法 → 不计成员失败、不打冷却、换下一个成员，全部成员都拒绝才终结」。用户要两种取向都有：

| 取值 | 行为 | 适用 |
| --- | --- | --- |
| `failover`（**默认**） | 记下该成员拒绝过，换下一个成员再试；全部拒绝才以错误结束 | 多中转混用：同一模型在不同站点的参数支持度不一致，「换一家也许能成」 |
| `failfast` | 第一个成员拒绝就结束，把上游状态码与原文回给客户端 | 想让错误反馈最快、最贴近上游原话，不想多发无谓请求 |

设置项 `relay_request_fault_action`（`internal/model/setting.go`，非法取值在 `Validate` 阶段直接 400），装配层在启动（`cmd/start.go`）与设置变更（`internal/server/handlers/setting.go`）两处注入 relay；relay 内部用包内原子量，非法值一律回落 `failover`——不进入"未知状态"。两种取向都保留上游原文，区别只在要不要先用别的成员试一次。

## T-migrate-002：存量分组回填流式无进展上限

新分组早就是 300 秒（`model.DefaultGroupRelayConfig`），但**存量分组的 JSON 里没有这个键**，反序列化后为 0 —— 而 0 的语义正是「关闭该保护」。于是升级后老分组依旧会挂在"上游吐了首帧就再也不出字"的请求上。

迁移 `014`（After 阶段，只 UPDATE 行、不碰表结构）：

- 只补这一个键；键缺失或 ≤0 → 补 300；已经是正数的分组**不动**（尊重用户显式配过的值）；其它字段逐字保留（不做"整体重置成默认"）。
- 显式配成 0 的分组会被一起补上——这是刻意的：迁移只跑一次，想关掉的分组在面板上改回 0 即可。
- `relay_config` 解析不了的行原样跳过（那是另一个问题，不该由本迁移顺手覆盖）。

**活体证据（本地实例，真实库）**：迁移前 388 个分组里 362 个是「缺键/0」；重启（迁移执行）后 **388 个全部为 300，0 个缺键**。单测另守三种情形：缺键补齐、显式 0 补齐、已是正数保留、坏行跳过、重跑幂等。
