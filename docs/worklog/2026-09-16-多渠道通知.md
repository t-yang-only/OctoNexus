# 多渠道通知（R-alert-001 / T-alert-001）

> 目标：告警不再只有一个通用 webhook —— 一个事件同时投递到全部启用渠道（通用 webhook / 飞书 / 钉钉 / 企微 / SMTP），
> 并且能在面板上"发送前真实测试"；密钥口径不退化（SMTP 密码不进库）。
> 这是需求事实源 §4 未立项项第 4 条（U-alert-001 的剩余部分）。

## 1. 口径

| 渠道 | 报文形状 | 成功判据 |
|---|---|---|
| `webhook` | 与改造前**完全一致**：POST 原始 `Event` JSON（n8n/自建服务照旧消费） | HTTP < 400 |
| `feishu` | `{"msg_type":"text","content":{"text":"…"}}` | HTTP < 400 且 `code`（或旧字段 `StatusCode`）为 0 |
| `dingtalk` | `{"msgtype":"text","text":{"content":"…"}}` | HTTP < 400 且 `errcode` 为 0 |
| `wecom` | 同钉钉形状 | HTTP < 400 且 `errcode` 为 0 |
| `smtp` | RFC2047 主题 + base64 UTF-8 正文 | SMTP 全流程（MAIL/RCPT/DATA）无错 |

三条工程口径：

1. **不信任 HTTP 200**：三家群机器人都习惯用 200 包业务错误码，判据必须看响应体里的码，
   并把原文摘要带进结果表 —— 否则"webhook 地址写错/被限流"会被当成发送成功（实测 feishu `code=19024` 与钉钉 `errcode=310000` 都被判失败）。
2. **投递永不阻断调用方**：每个渠道失败只记日志并进结果表，不重试、不阻塞（告警是尽力而为的通知）；
   单个渠道失败不影响其它渠道（实测 4 通 1 败时其它渠道照常投递）。
3. **密钥不外溢**：SMTP 密码只从环境变量 `OCTOPUS_SMTP_PASSWORD` 读，**不进设置表、不进数据库、不进备份转储**；
   邮箱密码与三个机器人 URL 的区别是：URL 本身即凭据、与既有 `alert_webhook_url` 同性质（面板可见可编辑），密码则有替代入口。

投递走 `rhttp.Direct()`（不走代理设置），单渠道超时 10s。

## 3. Go 单测（`internal/notify/channels_test.go`，8/8）

1. `TestRobotPayloadShapes`：四家各收到符合自身规范的报文，且都判成功（webhook 收到的仍是原始事件 JSON）。
2. `TestBusinessErrorCodeFailsTheChannel`：HTTP 200 + `code=19024` / `errcode=310000` 判失败，详情带业务码。
3. `TestChannelSelection`：只有 `alert_channels` 列出的渠道被投递（未启用渠道 0 次请求）。
4. `TestEnabledKindsDefaultsToWebhook`：设置缺失/为空回退 webhook；未知渠道名被忽略。
5. `TestTestSendReportsConfigurationGaps`：测试接口对未配置渠道给出缺项（`alert_smtp_host` 等），已配置渠道真投递。
6. `TestTargetsHideSecrets`：状态接口序列化后不含 webhook 凭据。
7. `TestSMTPDeliversMail`：内置最小 SMTP 服务端收到 DATA；断言 `To` 多收件人、中文主题 RFC2047 编码、正文 base64+charset=UTF-8。
8. `TestSMTPWithoutPasswordButWithUserIsAConfigurationGap`：有用户名没密码时提前报缺项，而不是等 AUTH 失败。

## 4. 活体审计（`scripts/api-tests/run_notify_audit.py`，14/14）

装置：mock 上游新增通知桩（`/notify/echo|feishu|dingtalk|wecom` 返回各家成功应答、`/notify/feishu-fail` 返回"200 + 业务错误码"）；
套件内自带 SMTP sink（Python 实现的最小 SMTP 服务端，收下 DATA 并解码 base64 正文）。

| 断言 | 实测 |
|---|---|
| 10 个通知设置全部可写 | 全 200 |
| 状态接口列出五个渠道且都 configured | `kinds=[webhook,feishu,dingtalk,wecom,smtp] configured=[True×5]` |
| 状态接口不泄露凭据 | 响应键只有 configured/enabled/hint/kind |
| 测试接口五渠道全投递成功 | `[webhook,feishu,dingtalk,wecom,smtp]` 全 True |
| 四家报文形状 | echo 收到原始事件 `type=notify_test`；feishu 收到 `msg_type/content.text`；dingtalk/wecom 收到 `msgtype/text.content` |
| SMTP 真投递 | sink 解码正文 = `[octopus] 通知渠道测试 …` |
| 业务错误码判失败 | feishu→`/notify/feishu-fail` 时 `sent=false detail="feishu returned code=19024"` |
| 单渠道失败不影响其它 | 同一次调用里 webhook/dingtalk/wecom/smtp 全 True |
| 未配置渠道报缺项 | 清空 `alert_smtp_host` 后 `detail="not configured: missing alert_smtp_host"` |
| **真实事件经 fan-out 抵达** | 打开探活 → mock-bad 失败冷却 → 上游恢复 → 探活解除冷却：webhook 桩收到 `type=route_probe_recovered`（detail 含 group/model），同时 feishu 桩收到渲染标题「冷却成员已恢复」 |
| 收尾复原 | 全部设置回到原值（`alert_channels=webhook`、探活关闭），测试用的本地 mock 不会留在用户配置里 |

## 6. 踩坑

- **`op.SettingSetString` 只认缓存里已存在的键**：新设置必须同时进 `model.DefaultSettings()`，
  它会在启动时补齐缺失行；否则接口能过校验却写不进去（探活那轮已记过一次，本轮 10 个新键同样适用）。
- **`Event` 不能既有 `Title` 字段又有 `Title()` 方法**：首版把渲染标题写成方法 `Title()`，与新增字段同名，编译直接报重复声明；
  方法改名 `DisplayTitle()`。
- **测桩要跟代码同步重启**：先跑的 notify 套件因为 mock 还是旧进程（没有 `/notify/*` 桩）而 4 项失败 ——
  报文断言仍通过（mock 先落盘再分发），但响应是 404 导致被判投递失败。重启 mock 后 14/14。
  教训：套件里的"外部依赖版本"也是被测对象的一部分。
- 中文邮件头必须 RFC2047 编码、正文用 base64：否则中间 MTA 会把标题里的中文改写成乱码。

## 7. 未覆盖 / 后续

- **规则引擎**（设计稿 §3 的 `NotifyRule`/`NotifyEvent`：按 scope/条件/阈值/窗口配置、去重收敛）未做：
  本轮是"渠道层 + 真实测试"，规则与去重仍是"事件源直接投递"的形态。
- 事件源仍只有三个（余额告警、归零停用、探活恢复）；公告/价格变化/内容变更（E5/E6）与失败率类窗口条件未接。
- 钉钉/企微的加签（secret 签名）未实现：只支持"自定义机器人 + 关键词/无校验"的 URL 形态；
  需要加签时得再补 `timestamp/sign` 计算。
- 通知渠道的投递历史没有落库（只有日志与测试接口的即时结果）。
