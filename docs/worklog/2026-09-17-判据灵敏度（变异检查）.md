# 判据灵敏度（变异检查）

## 目的

第 8 回合新增/修改的守卫（取消记账、尝试上限、成员故障分类、developer 角色归一化、全成员被拒终止）都有对应用例。
但「用例通过」不等于「用例真的在测这件事」：断言写松了、或压根没走到那条分支，守卫被删掉也一样绿。
本轮把守卫逐个改回旧行为或改成别的值，**要求指定用例在对应套件里变红**。

## 方法与纪律

- 逐个变异：改一处 → **只重建 Go 侧**（`rebuild_go_only.py`，前端不动）→ 跑目标套件脚本（能看单条用例明细）→
  记录判定与明细 → `git checkout --` 还原 → 下一个；全部结束再做一次干净重建，并复跑两个套件确认全绿。
- **变异期间实例是「故意坏的」**：为避免坏构建触发真实告警推到手机上，这一段把 ServerChan 指向本地 mock
  （`OCTOPUS_SERVERCHAN_BASE_URL=http://127.0.0.1:18099`），也不跑通知类套件；最后的重建回到生产模式。
- 上限这一条用「改值 6→8」而不是「删掉上限」：删掉会让退避累积到几十分钟、套件长时间挂住，
  改值足以验证断言确实在测**次数**，而不是碰巧通过。

## 副产品：变异没变红，牵出一条真实漏网路径（T-devrole-001）

把 `upstream.go` 转换中间件里的 `normalizeDeveloperRole` 注释掉后，retry 套件**全绿**。
顺着这条线索做了「客户端 chat + developer 角色，分别打到只说 chat / responses / messages 的成员」的分协议位探针：

| 成员协议位 | 上游路径 | 上游正文里的角色 | developer 残留 |
| --- | --- | --- | --- |
| chat(2) | /v1/chat/completions | system, user | 无 —— 由 `protocol.go` 的钩子归一化（M6 可证） |
| responses(4) | /v1/responses | input=[developer, user] | **有（缺陷）** |
| messages(8) | /v1/messages | 顶层 system + user | 无 —— 转换器把 developer 折进 system 字段 |

根因：Responses 形状的角色在顶层 `input` 数组里，而 `normalizeDeveloperRole` 只认 chat 的 `messages` 数组，
所以上游 #360 那条「developer 一律改写成等价的 system」的约束**在 Responses 路径上从来没生效过**。

- 修复：按上游协议选角色所在路径（chat→`messages`、responses→`input`），逐项判 role；
  `input` 是字符串 / 空数组 / 条目无 role 时安全跳过，除 role 外不改动任何字段（单测 5 例覆盖）。
- 回归：retry 套件新增 **R9**（chat 客户端 → 只说 responses 的成员）与配套夹具（`mock-plain` 模型、`respkey` 凭据、
  `protocols=4` 授权、`DS-TEST-retryresp` 分组），断言上游路径是 `/v1/responses`、正文里不再出现 developer、文本仍保留。
- 修复后探针读数：responses(4) 的 developer 残留由 **True → False**；把 M4 的期望改成 R9 后变异如期变红。

## 结论与边界

- 六处守卫都不是空转判据：改回旧行为或改值后，指定用例分别在各自套件里变红，明细报出的正是被改掉的那个量
  （成员失败计数、上游尝试次数、上游收到的角色 / 输入条目角色）。
- 反向也成立：变异只影响目标用例，套件其余用例仍绿 —— 用例之间没有互相遮盖。
- **证伪方向同样有价值**：用例在变异下不变红只有两种解释 —— 用例测的不是那处代码，或者那处行为并不依赖它。
  本轮 M4 属于后者，而且顺着它查出上面那个真实缺陷。
- 不能证明的事：变异检查只说明「这条判据能发现这个改动」，不覆盖真实故障形态
  （例如并发下的计数竞争、流式中途失败后的记账顺序）。

## 复现

