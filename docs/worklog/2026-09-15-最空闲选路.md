# 最空闲选路 least_busy（T-route-006 / NM-DS-007）

> 触发：「Iterative Upgrades」——补齐对照 litellm router_strategy 的路由策略族
> （lowest_cost → quality_first → lowest_latency → least_busy）
> 执行：dsh-local ｜ 状态：**已交付并活体验证**

## 1. 口径

1. **在途（in-flight）**：该成员当前"正在被等待响应"的请求数。数据来源是 **`state.go` 的活动请求注册表**
   （`requests` map）——请求在 `startRound` 时记下本轮选中的成员行 ID（新增字段 `TargetItemID`），
   在 `finishRound` 时把 `Sending` 置假；`memberBusyCount(itemID)` 遍历注册表数 `Sending && TargetItemID == itemID`。
   于是**结构上不存在"计数漏释放"**：不需要 acquire/release 成对维护，也不会出现某成员被永久当成忙
   （这正是 T-route-006 立项时担心的失败模式）；
2. **排序**：在途数升序 → priority 升序 → ID 升序；
3. **过滤/冷却**与其它策略完全同源（`partitionCandidates`）；provider 未接线时全部按 0 → 退化为 priority 定序；
4. 模式本身即开关：不选 least_busy 的分组行为一字不变；
5. 已知口径取舍：口径只覆盖"等上游响应"这段（非流式=整段响应、流式=首帧之前），流式提交之后不再计入；
   人工中止那一轮会停在 `Sending` 为真直到下一轮开始，属已知的轻微高估（人工操作且下一轮即刻修正）。

## 3. 验证

**单测 4 例**（internal/relay/busy_test.go）：在途定序（平手按 priority、再按 ID）、冷却成员压队尾、
provider 未接线退化为 priority、模式真的改变选中的人（failover 按 priority 选被占用的成员、least_busy 选空闲成员；
两者都在途时回落 priority），以及**注册表派生口径的泄漏自检**：一轮开始即计入、两个请求压在同一个成员上算 2、
轮次结束即归零、哨兵 `itemID 0` 恒为 0。

**全量**：`go build ./...` 0、`go vet ./...` 0、`go test ./... -count=1` 九包全绿；`pnpm build` 通过（产物含 least_busy）。

**活体 4/4**（脚本 run_busy_test.py；成员 mock-slow 上游 sleep 15s / priority 1，mock-good 正常 / priority 2）：

| 场景 | 结果 |
|------|------|
| 并发请求 A（冷启动、无人占用 → 平手 → priority） | HTTP 200，**15.01s**，选中 mock-slow 并占住它 |
| 1.5s 后并发请求 B | mock-slow 在途 1 / mock-good 在途 0 → **改选 mock-good，0.0s 返回**；mock 上游全程只收到 1 次 mock-slow |
| 对照 DS-TEST-busyf（同成员、failover、同样并发时序） | C 15.0s / D 15.0s，两个请求都撞 mock-slow |

即"把并发摊到空闲成员"成立：**第二个请求不再排队等 15 秒**。

## 4. 已知限制与后续

- 在途与质量/延迟样本一样按**展平后的成员行**（GroupItem.ID）聚合：同一授权挂在不同分组里各算一份，
  跨分组不共享（要共享应改为按 `ChannelGrantID`，已记在 ledger 待办里与质量/延迟一并处理）；
- 流式提交之后不再计入在途（口径见 §1.5）；若要让"正在流式输出"也算占用，需把清除时机从 `finishRound`
  挪到请求终态，并先定清"占用到何时"；
- 对照 litellm 的 router_strategy，路由策略族至此齐了 `lowest_cost / quality_first / lowest_latency / least_busy`
  （`lowest_tpm_rpm` 尚未做，它更像"按限流余量排序"，需要用到 Key 级 RPM/TPM 余量数据）。
