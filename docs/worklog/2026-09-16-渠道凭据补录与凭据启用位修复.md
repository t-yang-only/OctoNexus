### 2.1 longcat 的正确基址（实测）

- `https://api.longcat.chat/v1/models` → **404**（openresty 直出 404）
- `https://api.longcat.chat/openai/v1/models` → **200**，返回 `LongCat-2.0`
- 结论：基址必须写 `https://api.longcat.chat/openai`，不是裸域名。这正是 NM-DS-004 那套「BaseURL 末尾版本段去重」能覆盖的形态。

### 2.2 非破坏更新渠道凭据的做法（复用要点）

`/channel/update` 收的是**整个 `ChannelDetail`**（keys/models/grants 一起提交），按名称同步：
- 先 `GET /channel/detail/{id}` 读回完整配置（含真实密钥，接口不做掩码）；
- 只替换 `keys[].key`，models/grants 原样回写；
- 提交后断言三张表的计数不变。

**不要**用「只带 keys 的部分体」调 update：那等于声明「其余集合为空」，会把模型与授权连带删掉。
**也不要**用 `/channel/list` 判断渠道是否存在：它是分页的，靠它做存在性检查会误判 → 改用库里按名字取 id。

## 3. 修复：创建渠道时 `enabled:false` 的凭据被静默忽略（T-chan-001）

**现象（活体实测）**：`POST /api/v1/channel/create` 提交 `keys:[{name:"k-off",key:"sk-off",enabled:false}, …]` → 接口返回 `enabled=true`，
库里 `channel_keys.enabled = 1`：本意禁用的凭据照样参与选路。

**根因**：`model.ChannelKeyConfig.Enabled bool` 带 `gorm:"default:true"`，GORM 对带默认值标签的零值字段在 INSERT 时跳过该列、交给列默认值 ——
与历史上 APIKey.Enabled 那处缺陷同族（那次记在 key 记忆 9614b29d）。

**修法**（与 APIKey 同一处方：默认值移到请求层）：

- `internal/model/channel.go`：`ChannelKeyConfig.Enabled` 去掉 `gorm:"default:true"`；新增请求侧形状 `ChannelKeyInput{Name, Key, Enabled *bool}`
  与 `Resolved()`（nil → 启用）、`ChannelKeyOutput()`，`ChannelDetail.Keys` 改用 `[]ChannelKeyInput`（JSON 形状不变）。
- `internal/op/channel.go`：`syncChannelKeys` 收 `[]ChannelKeyInput` 并在内部 `Resolved()`（显式 false 真的写 false，未提交默认启用）；
  `channelDetail()` 用 `ChannelKeyOutput()` 回读，读写共用一份契约。

**验证**：

- 新增单测 `internal/op/channel_key_test.go`（内存 SQLite + `db.SetDBForTest`）：创建时 `enabled:false` 必须落库为禁用、未提交的默认启用、
  更新路径反过来改也生效。
- 活体复验：修复后同一条请求 → 接口返回 `[('k-off', False), ('k-on', True)]`，库里 `k-off = 0`。
- 全量 API 矩阵 19 套件通过；`go build ./...` / `go vet ./...` 退出码 0；`go test ./... -count=1` 十包全绿。

## 4. 两条中转站账号的登录测试（未完成自动化）

| 站点 | 登录页 | 惯用登录接口 | 结论 |
| --- | --- | --- | --- |

两个站点登录页还要求：① 先同意更新后的服务条款（弹层「同意并继续」）；② 完成人机验证（页面文案「点击完成人机验证」）。
浏览器动作在本轮被人工拒绝一次，故**没有继续自动化登录**，也没有把账号密码写入任何持久化位置。

结论与建议：站点禁止/阻碍无人值守登录时，正确入口是网关里的**手动登录跳转页**（`internal/server/handlers/jump.go`，T-acct-005）——
把浏览器交给用户本人登录，网关不代持中转站凭据。若确实要我自动登录，需要用户明确授权并接受人机验证可能仍然拦下。

## 5. 观察记录（非缺陷，供决策）

1. **单成员分组在成员冷却期内，请求会静默等待**：三条真实渠道的分组各自只有一个成员，成员一旦失败即进入 `member_cooldown_seconds`（默认 60s）；
   冷却期内新请求不返回错误而是等待（`internal/relay/handler.go` 注释写明等冷却到期或人工改配置）。
   实测表现：客户端等 40~180s 拿不到任何首字节，日志里 `first_byte_ms=-1`、`error=context canceled`，分组的 `runtime.cooldowns` 里能看到该成员。
   若希望「全员冷却时立刻失败并回 503 + Retry-After」，这是产品语义变更，需用户拍板后再改。
2. **探针与转发打过上游后的自伤效应**：本轮对 `api.x5m5x.com` 做了数百次探针请求（13+39 模型 × 三协议 × 多轮），
   之后转发请求长时间无首字节；直连该站的 chat 请求返回 **Cloudflare `error code: 1010`**（浏览器指纹拦截）。
   即：站点侧对我们这类非浏览器客户端有限流/拦截，转发链路上的「冷成员也超时」现象与此高度相关，但尚未定论（未做冷成员的干净单发复验）。
3. **协议位映射**：`Protocol` 位掩码是 chat `1<<1=2`、responses `1<<2=4`、messages `1<<3=8`。
   本轮一度把映射写成 1/2/4，得出「chat 位=0」的假结论 —— 写脚本核对位掩码时务必从 `internal/model` 取值，别照抄十进制。
