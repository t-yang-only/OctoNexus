# 智能路由的显式档位（决策引擎渠道由用户指定，而不是靠顺序）

十项清单里的最后一条代码项：**显式指定决策引擎渠道**。此前 `mode=smart` 只能靠「成员在列表里的先后顺序」
分档（前半 = 决策引擎档、后半 = 执行引擎档），用户想换档就得拖动成员排序，而顺序同时还决定
failover 的切换顺序与界面展示——两件事被绑在一起。本轮把它们解开。

## 1. 口径（三条规则，按优先级排列）

| 情形 | 行为 |
| --- | --- |
| **没有任何成员声明档位** | 逐字保持既有口径：靠前的顶层成员归决策引擎档（奇数多出来的归它），靠后的归执行引擎档 |
| **有成员声明了档位** | 整批成员改走显式口径：声明 `decision` 的进决策档、声明 `execution` 的与**未声明的**一起进执行档 |
| **目标档为空** | 回退全体成员（而不是返回空集）——「标错一边」（例如全部标成决策档而请求是简单的）不会把功能变成故障 |

档位是**顶层成员粒度**的，并且在展平时**下传给整条链**：把一个子分组标成决策档，它内部的每条成员都带上
同一个档位（内层自己声明的档位优先，就近原则）。不这样做的话，档位会在子分组那一层被展平丢掉——
「标在子分组上等于没标」正是这条最容易被忽略的地方。

## 3. 三个「静默丢字段」的坑（本轮实际踩到并堵上）

1. **保存路径是重建而不是透传**：`GroupCreate`/`syncGroupItems` 用 `model.GroupItem{ChannelGrantID: …, ChildGroupID: …, Priority: …}` 重新构造成员行。只在 `GroupItem` 上加字段是不够的——`GroupItemInput` 也要有，三个构造点也要带上，否则面板送来的档位被安静丢掉（现象：界面点了没反应，日志里也没有任何错误）。
2. **提交条件不看档位就会丢修改**：卡片只在「成员集合或顺序变化」时才提交 `items`。只改档位不动顺序时，这个条件为假 → 整次修改被丢弃。已把档位并入差异键（`g:12@decision` 形态）。
3. **拖拽提交是另一条载荷路径**：`submitMembers` 直接拼成员表，漏掉档位会让一次拖拽把显式档位悄悄清空。两条路径现在共用一个 `memberPayload` 构造函数。

| 用例 | 变异下的读数 |
| --- | --- |
| S10（档位落库并回读） | **仍绿** —— 字段照样存进去了 |

## 5. 边界与未覆盖

- 档位只在 `mode=smart` 下被读；其它模式（manual/failover/weighted/lowest_cost…）标了也不影响行为，
  这一点由「增改只在 smart 分支内」保证，没有额外的活体用例。
- 未覆盖：`smart_tier` 的非法值只有单测与绑定层（400）覆盖，没有活体用例专门送一个非法值。
  绑定 tag 与分组模式的 `oneof` 同款，风险等同既有枚举。
- 首字竞速与显式档位共用 `smartTierItems`，因此竞速自动只在选中的那一档内进行（见 S10d）。
