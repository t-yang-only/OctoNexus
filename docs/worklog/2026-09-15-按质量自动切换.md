> ledger T-route-004 记录过「缺的不是接缝而是数据」——本轮补的正是那份数据。

## 1. 口径

1. **指标**：成员维度（GroupItem.ID，即展平后的成员行）的最近窗口成败计数。窗口 300s，用
   「写入时衰减」实现——没有后台协程、没有环形缓冲、不发额外请求：距窗口起点超过窗口就把该成员
   样本清零重计；
2. **写点**：挂在 recordRouteSuccess / recordRouteFailure 上（手动模式也记，便于切到质量模式时
   立刻有历史可依）；不落库，进程重启即清零（个人网关够用，且避免为此加表）；
3. **排序**：最近窗口成功率降序 → priority 升序 → ID 升序；**无样本按中性先验 1.0 处理（乐观）**——
   新成员照样会被尝试，失败过的成员自然沉到已验证成员之后；坏成员另有既有冷却/探测链路兜底；
4. **过滤/冷却**与 lowest_cost 完全同源（partitionCandidates）：不可用与剩余额度归零剔除、
   冷却成员压队尾、可尝试为空返回 ErrNoEligibleMember 由调用方等待；
5. 模式本身即开关：不选 quality_first 的分组行为一字不变；route_balance_enabled 语义不变。

## 3. 验证

**单测 6 例全过**（internal/relay/metrics_test.go）：窗口衰减（注入时钟，含哨兵 itemID 0 不统计）、
成功率定序（0.2 / 0.9 / 无样本→中性）、provider 未接线时保持 priority 序、冷却压尾与剔除口径、
模式真的胜过 priority（同批成员 failover 选 priority 首个而 quality_first 选成功率高的）、
**写点→选路闭环**（坏成员失败两次后，质量优先直接交给好成员）。

**全量**：go build/vet 0、go test ./... -count=1 连跑 2 次九包全绿；前端 pnpm build 通过、
产物含 quality_first 且由实例正常 serve。

**活体 4/4**（脚本 run_quality_test.py；成员 mock-bad（上游 500，priority 1）与 mock-good（正常，priority 2））：

| 场景 | mock 上游收到的尝试 | 结果 |
|------|--------------------|------|
| DS-TEST-quality 第 1 次（冷启动、双方无样本） | [mock-bad, mock-good] | 200，3.01s：按 priority 先撞坏成员，失败后让位 |
| DS-TEST-quality 第 2 次（坏成员 0%、好成员 100%） | [mock-good] —— 坏成员 0 次尝试 | 200，**0.0s** 直达好成员 |

差异只来自模式，正是「按质量自动切换」的最小闭环。

## 4. 踩坑（我自己犯的，已入技能建议）

新模式只加了常量 + IsValid + 逻辑，**漏了 binding:"oneof=..." 标签**（三处），建档被 gin 直接判 400。
教训：GroupMode 的判定点共 5 类——①常量 ②IsValid() ③三处 binding 标签 ④备份导入校验
⑤前端联合类型/下拉/UI 分支；新增模式必须一次找齐，否则出现「后端支持、前端选不到」或「建档/导入被判非法」。
