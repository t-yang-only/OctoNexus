# 模型拉取失败根因：上游地址与端点路径版本段重复（NM-DS-004）

> 触发：用户报告「模型拉取失败」并贴出报错
> `openai: Get "https://api.apikey.fun/v1/v1/models": dial tcp 31.13.96.195:443: connectex: ...`
> 执行：dsh-local ｜ 日期：2026-09-15 ｜ 状态：**已修复并活体验证**

## 1. 先取地面真值（不猜）

直连实测三个上游（本机 python 脚本，密钥不入库）：

| 上游 | 请求 | 结果 |
|------|------|------|
| https://api.thqllm.com/v1 | GET /v1/models | **200**，返回 14 个模型 |
| https://api.thqllm.com/v1 | GET /v1/v1/models | **404** ← 正是应用拼出来的地址 |
| https://api.x5m5x.com | GET /v1/models | 200（首测一次 403 是 Cloudflare 1010 瞬时拦截，重试即 200） |
| https://api.apikey.fun | DNS | 解析到 31.13.96.195，本网络 TCP 不可达（需代理/换域，与应用无关） |

结论：报错里的 /v1/v1/models 不是上游要求，而是**应用把版本段拼了两次**。

## 2. 根因

渠道 base_url 有三种常见写法：https://host、https://host/v1、https://host/api/v1，
而各协议端点路径（默认 /v1/chat/completions、/v1/responses、/v1/messages）本身自带版本段。
旧代码一律 TrimRight(baseURL,"/") + path，于是把版本段写进 base_url 的渠道被拼成
https://host/v1/v1/...：模型拉取得 404、转发也打不中端点。

## 3. 修复（一处口径，三处统一）

新增 internal/model/channel.go 的拼接口径：

- IsAPIVersionSegment(seg)：识别 v1 / v12 / v1beta / v2alpha，纯字母段（vip、v）不算；
- ChannelBaseURL(baseURL, endpointPath)：base 末尾段与端点路径首段是**同一个**版本段时去掉 base 末尾那段，
  其余写法原样（只规范尾斜杠）；纯主机名（形如 https://v1）不动；
- JoinUpstreamURL(baseURL, endpointPath)：按上述口径拼接，保证中间恰好一个斜杠；
- EndpointPathOrDefault(value, fallback)：端点路径留空时落回该协议默认路径，与库列默认值同值。

三处统一改为该口径：

| 位置 | 原来 | 现在 |
|------|------|------|
| 模型拉取 modelsURL（handlers/channel.go） | TrimRight(baseURL,"/") + parent + "/models" | model.JoinUpstreamURL(baseURL, parent+"/models")，且端点路径留空时按协议默认值取父目录 |
| 三协议实测探测（chat/responses/messages） | TrimRight(baseURL,"/") + path | model.JoinUpstreamURL(...) |
| 转发出站转换器（relay/channel.go 三处） | BaseURL: channel.BaseURL | BaseURL: model.ChannelBaseURL(channel.BaseURL, 端点路径或默认) |

## 4. 验证

**单测**：internal/model/channel_url_test.go 5 例（版本段识别、四种 base 写法、拼接、端点默认值、
以及「任何写法都不许出现两段相同版本段」的回归守卫），全过。

**活体 15/15**（脚本 run_channel_add.py，三个真实渠道）：

| 渠道 | base_url | 拉取 | 三协议实测 | 自动分组 | 真实转发 |
|------|----------|------|------------|----------|----------|
| DBG-53HK | https://api.x5m5x.com | 13 模型 | glm-5.3-flash → chat/response/message 全 200（协议位 14） | DBG-53HK/glm-5.3-flash 建成 | 200（cost 1.28e-05） |
| DBG-53HK-L | https://api.x5m5x.com/v1 ← 带 /v1 | 39 模型 | 3 个模型均三协议全 200 | 3 个「渠道名/模型名」分组建成 | 200（cost 2.16e-05） |
| DBG-THQ | https://api.thqllm.com/v1 ← 带 /v1（修复前 404） | 14 模型 | codex-auto-review 仅 chat 通过（response/message 403 如实记录） | 建成 | 200 |

即：**带 /v1 的 base_url 现在与不带的一样可用**；用户要的「拉取模型时自动建 渠道名/模型名 分组」
也在同一轮被真实验证（三家共 5 个自动分组，逐个核对存在）。

## 5. 顺带修掉的测试缺陷（非产品缺陷）

internal/op/usage_query_test.go（NM-DS-002 的回归守卫）出现**偶发失败**（3 次中约 1 次）：内存桶与库句柄
都是包级全局，用例之间用同名模型名（mock-good）互相污染，断言又用绝对行数。已改为：用例名作模型名前缀、
用例前后都清空内存桶（t.Cleanup 保证失败退出也清）、断言只按本用例前缀过滤。修后 op 包连跑 6/6、
全量 go test ./... 连跑 2/2 全绿。

## 6. 「跳转页」不是缺陷（同批澄清）

用户引用的文案来自 internal/server/handlers/jump.go 的 **T-acct-005 手动登录一次性跳转页**：
设计目标是网关**不代持中转站凭据**，把浏览器交给用户去站内登录（含验证码），回来后由用户把结果交给网关。
跳转目标 TargetURL **由创建令牌的请求给出**（库内三条：api.53hk.cn/login ×2、sub.tohoqing.com/login ×1，
均为本人当日创建）。页面里「已即时失效」指**页面 URL 上的一次性令牌**，目标链接本身照常可用。
若希望改成「页内确认后再跳」、调整文案或干脆隐去该入口，属产品口径变更，待用户拍板。
