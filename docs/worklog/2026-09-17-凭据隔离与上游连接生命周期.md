# 凭据隔离与上游连接生命周期（活体测量）

NM-DS-037 ｜ 任务：T-test-019 / T-test-020 ｜ 记录时间：2026-09-17

## 为什么要做这一轮

上一轮把上游剩余报告全部结案，其中两条的结论当时还只由**代码推导**支撑、没有实测：

1. **客户端凭据不得出现在上游请求里**（上游 #372 的同类头部处理）——泄露就是凭据外泄，而
   mock 上游不校验密钥，功能用例在这种情况下**不会变红**，所以必须有直接看上游头部的断言。
2. **客户端断开后 relay 必须随即中止这次上游请求**（上游 #338「客户端断开后后台空转」）——
   "首帧之后挂到客户端自己放弃"是用户线上日志的主症状，无进展上限（T-timeout-001）只是给它
   加了上限；"客户端一走就停"这件事此前没有正面证据。

本轮**不新增修复代码**：行为已正确，缺的是可复核的证据。改动仅限测试装置与断言，避免把
"验证补强"混成功能变更。

## 装置改动

- `scripts/api-tests/mock_upstream.py`：
  - 静默分支不再 `time.sleep(STALL_SECONDS)` 死等，改为 `_stall_watch_peer()` —— 用 `select` + `recv`
    盯住这条上游连接，对端一关就记一条事件行 `{"event": "stall_peer_closed", "closed_after": 秒数}`
    （等满静默上限仍是 null）。事件行不带 `method` / `model`，因此不会被各套件的"上游尝试次数"
    统计当成一次请求；`run_stream_idle_test` 的 `attempts_since` 也显式跳过事件行（一条日志被两个
    口径共用时，宁可两边都写清楚）。
  - 落盘新增 `headers` 字段 = **所有**请求头的「小写名 → 值指纹」（同一请求 7 条：host / user-agent /
    content-length / accept / authorization / content-type / accept-encoding）。`authorization` 与
    `x_api_key` 两列保留，用于正面断言；`headers` 是它们的补集——自定义头也进入证据范围。
- `scripts/api-tests/run_lossless_tests.py`：新增**聚合断言**「凭据隔离[10 条协议路径]」——
  3 个客户端协议 × 3 个上游协议位 + 1 条流式，窗口内**每一条**上游请求都必须携带渠道密钥、
  且一条都不含客户端凭据。判据两层：① 标准凭据列 / 任意头部的指纹比对（按 `mock_upstream._redact`
  的同款算法：`bearer:` / `key:` + sha256 前 12 位）；② 兜底——整行里出现客户端凭据**原文**也算泄露
  （正文、查询串等 mock 未单独建列的位置都盖住）。全程不落凭据原文。
  另加**判据自检（负向对照）**：伪造 4 行（1 合规 + 1 自定义头泄露 + 1 正文泄露 + 1 事件行）跑同一判据，
  要求恰好报出那两条泄露，防止判据日后被改瞎了还一路绿。
- `scripts/api-tests/run_retry_test.py`：R7 同步采用同一套判据（两个凭据列 + 任意头部 + 原文兜底）。
- `scripts/api-tests/run_stream_idle_test.py`：新增 I8、I9（见下），并共用 `idle=0` 的分组
  （看门狗关闭），于是上游连接若被关掉，只能归因于"客户端断开"而不是上限兜底。

## 读数

| 用例 | 读数 |
| --- | --- |
| 凭据隔离（lossless 15/15） | 上游请求 10 条, 携带渠道密钥 10 条, 携带客户端凭据 0 条（含任意头部与原文兜底） |
| 凭据判据自检（负向对照） | 伪造 4 行 → `total=3 carried=3 leaked=['self-leak-header','self-leak-body']`：两种泄露都抓到、合规行与事件行都没有误判 |
| I2 服务端无进展上限 | 上游连接 **2.0 秒**关闭（与分组 `idle=2` 一致） |
| I9 客户端在等（客户端上限 8 秒） | 上游连接 **8.01 秒**关闭——客户端还在等时**不会**提前关上游 |
| I8 客户端立刻放弃 | 上游连接 **0.0 秒**关闭——不等无进展上限 |

三档关闭时刻出自**同一次套件运行**的 mock 事件行，构成因果对照：`2.0` = 服务端看门狗、
`8.01` = 客户端放弃（I6/I7 那次调用客户端等满 8 秒才超时）、`0.0` = 客户端立刻断开。
I9 是 I8 的反向对照：若"客户端走了上游就停"只是假象（例如连接本来就要被关掉），I9 就会看到
小于 7 秒的提前关闭。三档同时成立，才能说清"是谁结束了这次上游请求"。

## 边界与未覆盖

- 凭据判据现在覆盖：标准凭据列、**任意头部**（`headers` 指纹）、以及整行里的**凭据原文**兜底。
  仍未覆盖：TLS 层（SNI/证书）与 mock 看不到的信道；也**不**覆盖"凭据被改写成别的形态"这种
  需要语义判断的情形（例如上游收到的是被 base64 过的凭据）。判据的正面半边（10/10 命中渠道密钥）
  自证了指纹算法与字段读取正确，反向半边是同款比较换成客户端凭据的指纹。
- `closed_after` 是**从 mock 进入静默等待开始**计的秒数，不是从请求开始计的；三条读数因此
  都能与各自触发原因对上（看门狗 2 秒 / 客户端 8 秒 / 立即断开）。
- I8/I9 只覆盖流式路径；非流式路径的取消记账由上轮的 R2/R5 覆盖。
