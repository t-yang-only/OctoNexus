# 凭据隔离与上游连接生命周期（活体测量）

NM-DS-037 ｜ 任务：T-test-019 / T-test-020 ｜ 记录时间：2026-09-17

## 为什么要做这一轮

上一轮把上游剩余报告全部结案，其中两条的结论当时还只由**代码推导**支撑、没有实测：

1. **客户端凭据不得出现在上游请求里**（上游 #372 的同类头部处理）——泄露就是凭据外泄，而
   mock 上游不校验密钥，功能用例在这种情况下**不会变红**，所以必须有直接看上游头部的断言。
2. **客户端断开后 relay 必须随即中止这次上游请求**（上游 #338「客户端断开后后台空转」）——
   "首帧之后挂到客户端自己放弃"是用户线上日志的主症状，无进展上限（T-timeout-001）只是给它
   加了上限；"客户端一走就停"这件事此前没有正面证据。

本轮**不新增修复代码**：行为已正确，缺的是可复核的证据。改动仅限测试装置与断言，避免把
"验证补强"混成功能变更。

## 装置改动

- `scripts/api-tests/mock_upstream.py`：静默分支不再 `time.sleep(STALL_SECONDS)` 死等，改为
  `_stall_watch_peer()` —— 用 `select` + `recv` 盯住这条上游连接，对端一关就记一条事件行
  `{"event": "stall_peer_closed", "closed_after": 秒数}`（等满静默上限仍是 null）。事件行不带
  `method` / `model`，因此不会被各套件的"上游尝试次数"统计当成一次请求；`run_stream_idle_test`
  的 `attempts_since` 也显式跳过事件行（一条日志被两个口径共用时，宁可两边都写清楚）。
- `scripts/api-tests/run_lossless_tests.py`：新增**聚合断言**「凭据隔离[10 条协议路径]」——
  3 个客户端协议 × 3 个上游协议位 + 1 条流式，窗口内**每一条**上游请求都必须携带渠道密钥、
  且一条都不含客户端凭据。按 `mock_upstream._redact` 的同款算法比对哈希（`bearer:` / `key:`
  + sha256 前 12 位），全程不落凭据原文——装置不持久化凭据是既有纪律。
  窗口内允许后台探活等并发请求，故不强求"恰好 10 条"，但**条条都要合规**。
- `scripts/api-tests/run_stream_idle_test.py`：新增 I8、I9（见下），并共用 `idle=0` 的分组
  （看门狗关闭），于是上游连接若被关掉，只能归因于"客户端断开"而不是上限兜底。

## 读数

| 用例 | 读数 |
| --- | --- |
| 凭据隔离（lossless 14/14） | 上游请求 10 条, 携带渠道密钥 10 条, 携带客户端凭据 0 条 |
| I2 服务端无进展上限 | 上游连接 **2.0 秒**关闭（与分组 `idle=2` 一致） |
| I9 客户端在等（客户端上限 8 秒） | 上游连接 **8.01 秒**关闭——客户端还在等时**不会**提前关上游 |
| I8 客户端立刻放弃 | 上游连接 **0.0 秒**关闭——不等无进展上限 |

三档关闭时刻出自**同一次套件运行**的 mock 事件行，构成因果对照：`2.0` = 服务端看门狗、
`8.01` = 客户端放弃（I6/I7 那次调用客户端等满 8 秒才超时）、`0.0` = 客户端立刻断开。
I9 是 I8 的反向对照：若"客户端走了上游就停"只是假象（例如连接本来就要被关掉），I9 就会看到
小于 7 秒的提前关闭。三档同时成立，才能说清"是谁结束了这次上游请求"。

## 边界与未覆盖

- mock 只落盘 `Authorization` / `x-api-key` 两个头部字段，因此"客户端凭据是否经**自定义头**
  外泄"不在本次证据范围内（自定义头本身是上游 #372 的推荐绕过手段，属另一个话题）。
- `closed_after` 是**从 mock 进入静默等待开始**计的秒数，不是从请求开始计的；三条读数因此
  都能与各自触发原因对上（看门狗 2 秒 / 客户端 8 秒 / 立即断开）。
- I8/I9 只覆盖流式路径；非流式路径的取消记账由上轮的 R2/R5 覆盖。
