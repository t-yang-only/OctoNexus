## 目标

完整研究项目的可升级方向：先摸清现状与既有缺口，再按"价值 × 成本 × 与项目定位契合度"给出分级路线。

## 0. 项目定位与现状基线（升级方向必须服从的前提）

Octopus 是**个人自用**的 LLM API 聚合网关：单二进制、内嵌前端、SQLite 默认、
双端口（admin/relay）、协议互转（OpenAI Chat / OpenAI Responses / Anthropic Messages）、
分组故障转移（冷却/探测/亲和）、价格同步（models.dev）、请求全链路实时可视化（SSE）、
统计内存批量落库、自动建分组、上游自更新、Docker 多架构发行。

**差异化**：相对 litellm（大而全的 SDK+网关），octopus 走"少而精 + 可视化 + 开箱即用"。
升级方向不应把它推向 new-api/litellm 的复杂度，而应强化其已有的差异化能力。

## 2. 可升级方向（按主题 × 优先级）

### P0 安全基线（小成本、高收益、欠账明确）

1. **JWT 密钥独立化**（`internal/server/auth/auth.go`）
   现状：`secret := user.Username + user.Password`（bcrypt 哈希拼用户名的派生密钥）。
   问题：改用户名/密码即全员下线；密钥派生链依赖口令强度。
   升级：首次启动生成随机 32B 密钥落库/落配置文件，提供 `OCTOPUS_AUTH_SECRET` 覆盖；
   登录限流（bcrypt 已是成本，但 admin 接口可爆破）。
2. **Cookie 安全位**（`internal/server/handlers/user.go:52`）
   现状：`c.SetCookie("auth", token, maxAge, "/", "", false, false)` —— HttpOnly/Secure 双 false。
   升级：HttpOnly=true，SameSite=Lax/Strict；Secure 按是否反代 TLS 配置；同步修
   `middleware/auth.go` 里清理 cookie 的同款调用。
3. **凭据静态加密**（`internal/model/channel.go` ChannelKey.Key、`model/apikey.go` APIKey、
   `internal/op/backup.go` 导出含明文）
   升级：主密钥（env `OCTOPUS_MASTER_KEY`）+ AES-GCM 加密落库；备份导出默认脱敏、可选 `--with-secrets`。
   关联未结项：T-sec-001（工作区 `数据备份.json` 明文密钥未迁出未轮换 —— **最高优先，先于一切**）。
4. **自更新校验**（`internal/update/core.go`）
   现状：下载 GitHub release zip 直接解包替换，无校验和/签名验证。
   升级：release 附 SHA-256 清单并校验；可选 cosign/minisign；镜像源可配（国内场景）。
5. **登录/管理口防爆破**：`/api/v1/user/login` 与 apikey 鉴权失败计数 + 指数退避（内存即可）。

### P0 工程门禁（CI 现在只"能编译"，不"测"）

6. **CI 补 test/lint 关卡**（`.github/workflows/build.yaml` 无测试步骤；仅 2 个 `*_test.go`）
   - 后端：`go vet ./...`、`gofmt -l`、`go test -race ./...`、golangci-lint
   - 前端：`pnpm lint` 进 build workflow；vitest（现无任何前端测试）
   - **relay 集成测试**是最高价值缺口：httptest 假上游覆盖 `Forward` 全链路
     （同协议直通 / 跨协议转换 / 流式首帧超时 / 冷却让位 / 亲和 / 探测单发 / 人工中止 /
     `inspectStreamEvent` 三协议终止与错误帧判定 / 提交后不可重试）。这些是 README 卖点，目前零测试。
7. **环境债**：T-env-001（本机无 Go 工具链，提交前无法 vet/build/test）需闭环，
   否则只能继续依赖 `scripts/check_*.py` 文本检查兜底。

### P1 网关核心能力

8. **负载均衡策略**（单一接缝：`internal/relay/route.go` `pickGroupItem`）
   现状：严格按 Priority 顺序取首个可用成员；同优先级成员永远只用第一个。
   升级：`GroupRelayConfig` 加 `strategy` 字段（默认 `priority` 不变，向后兼容）：
   - `weighted`：成员加 weight 列，加权轮询（配平滑 WRR，纯函数好测）
   - `latency`：复用 `StatsMetrics.WaitTime/RequestSuccess` 的滑动窗口选优
   - `least-busy`：relay 内存计每成员在途请求数（finishLocked 已有原子计数入口可扩展）
   - `cost`：结合 price 表选当前请求最便宜成员
   路由状态 `RouteState` 已随 SSE 推送，前端可视化"当前承载成员"无需改造。
9. **Gemini 原生协议**（README 特性表已写 Gemini，代码未实现 —— **文档超前于代码的漂移**）
   - `model.Protocol` 加 `1<<4`（注释已声明 1<<0 保留、位值落库不可变更 → 新位只能追加）
   - `ChannelConfig` 加 `gemini_path`（默认 `/v1beta/models` 族），`normalizeChannelConfig`
     补校验；`buildOutbound`（relay/channel.go）补 case；fetchModel/probeModels 加第三侧探测；
     前端 Form/FormGrants/授权矩阵补一列协议。axonhub 已有 `llm.APIFormatGeminiContents`，
     迁移 `migrate/003.go` 还留有它和 `APIFormatOpenAIEmbedding` 的历史痕迹 —— 补上顺理成章。
10. **Embeddings 端点**：`/v1/embeddings` 转发（axonhub `APIFormatOpenAIEmbedding` 现成），
    统计/计费复用 usage 的 prompt/completion 口径需单独映射。
11. **限流与配额**：APIKey 加 `rpm/tpm`（内存滑动窗，中间件层）；上游返回 429 时解析
    `Retry-After` 作为冷却时长下限（recordRouteFailure 现用固定 cooldown）。
12. **模型别名**：分组已天然是一层别名（group name → 成员模型）；可再加
    APIKey 级 alias 表与 `/v1/models` 隐藏组（当前 `/v1/models` 直接吐全部分组名，
    多 key 隔离场景想藏住某些模型只能删组）。

### P1 可观测性（差异化卖点"全链路可视化"目前断电即失）

13. **请求日志持久化（可选开关）**：`relay/state.go` 的 `RequestState` 已含全部字段，
    落库时只存元数据+截断正文，保留 `maxFinished` 改为可配的保留策略（条数/天数），
    提供查询/导出 CSV 接口。与 stats 一样走批量写避免拖慢转发。
14. **统计时序化**：`stats_hourly` 固定 24 槽且每日整体覆盖（`persistStatsSnapshots`），
    今天之前的逐时趋势已丢失；升级为按 `date+hour` 主键持久 + 保留窗口，
    首页趋势图从"今日 24 格"扩为任意区间。
15. **`/healthz` + 优雅下线**：无存活探针端点；Dockerfile 无 HEALTHCHECK、无 USER（root 运行）；
    容器里 `server.Close()` 是硬 Close，升级 `Shutdown(ctx)` + 在途流式请求排空，
    配合"统计内存写"现状（README 已警告 kill -9 丢统计 —— 给 SIGTERM 一个真正的排空语义）。
16. **告警推送（webhook 即可）**：成员进入冷却/组全灭/连续失败/成本越阈
    推送到 webhook（用户侧 n8n/钉钉/飞书随便接）；对照 api-monitor 的通知层设计但不引其重依赖。
17. **上游余额/额度探测**：对照 api-monitor；OpenAI 有 `dashboard/billing/credit`，
    中转站多有 `/v1/balance`；做成渠道可选的"凭据级探测任务"，结果并入渠道卡片与告警。

### P3 远期/明确不做（防止 scope creep）

  与"个人自用单二进制"定位冲突或重依赖，远期再议；要做也应走独立子项目/插件。
- 协议转换层继续押注 axonhub 上游（`looplj/sse`、`looplj/go-sse` 两个 replace 已说明

## 3. 建议的实施顺序（一条线收口）

```
第 1 步（安全/门禁）: T-sec-001 迁出备份 → JWT/cookie → 登录限流
第 2 步（CI 测试关）  : 环境闭环(T-env-001) → relay 假上游集成测试 → vet/race/lint 进 CI
第 3 步（核心增强）  : 路由 strategy（weighted/latency） → Gemini 协议 + Embeddings
第 4 步（可视化补全）: 请求日志持久化 → stats 时序化 → healthz/优雅关停
第 5 步（体验运维）  : 文档/compose/版本号同步 → 自动分组遗留 → 告警 webhook
```
