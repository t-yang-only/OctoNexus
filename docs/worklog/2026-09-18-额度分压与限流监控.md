## 口径（四条，都写进了代码注释）

1. **剩余请求数**：包月余量（额度 − 已用）优先；否则余额 ÷ 单次成本（按次价优先，其次 倍率 × 估算 token × 单价）；两者都不知道 → **未知**，取已知成员权重的中位数参与（未知不惩罚，也不显示成 0）。
2. **权重**：余量最大的成员铺到 100，其余按比例；再乘健康折扣（成功率低 / 超慢阈值 / 刚被限流 → 打折，最低保 1，只削权不剔除）。
3. **分配**：平滑加权轮询（累加器挂 `RouteState.allocCurrent`），长期份额正比于权重；余量不足一次（< `route_allocate_min_requests`）即剔除。
4. **限流与速度**：上游 429 带 `Retry-After`/`X-RateLimit-*` 时——立即换成员 + 冷却按提示走 + 以 `route_ratelimit_cooldown_max_seconds`（默认 300s）封顶；不带提示则保持既有的可恢复语义。我方自限流（`route_member_rpm_limit`/`route_member_tpm_limit`，默认 0=不限）到顶让开一轮，全员到顶时仍照常使用。

监控页把上述事实逐个摊开：每个成员的剩余请求数（含来源：包月余量/余额折算/未知）、权重条、健康系数、近一分钟请求与 token、成功率、最近耗时、冷却与限流剩余时长、被限流次数、以及当前生效的设置口径。

## 本轮抓到的真缺陷（都是演练先撞上、再修）

1. **渠道保存丢计费事实**：`ChannelUpdate` 用「逐列点名」的 `Select` 更新，名单里没有 `billing_mode / multiplier / per_call_price / monthly_quota / monthly_used`。表现为「面板上填了、接口回 200、进程缓存里也有值（当下选路正确）」而**库里那一行始终是 NULL**——重启或换实例后，分压的剩余请求数与加权模式的余额/倍率维度一起悄悄退回「未知」。已修 + 单测 + 变异。
2. **装置缺陷两处（不改产品代码，改用例）**：A2 的断言方向与装置标反了（包月挂在渠道上，我把「余量 900 的那一方」认成了另一个成员）；A7 复用 A3 用过的成员，而 A3 已把该渠道余量改成 0，导致「只剩一个候选」时去断言「换人」——两者都改成显式前置与自洽读数。
3. **限流封顶只封了一半**（本轮早段已修）：`retry_after` 的封顶原本只作用于限流账，没作用于冷却时长，1 小时的 `Retry-After` 会造出 1 小时冷却。

## 边界

- **未做**：live 限流套件只覆盖 429 一类；`Retry-After` 的 HTTP-date 形式只有单测覆盖（mock 桩只回秒数）；「速度不好」目前只有「最近一次尝试耗时」这一个维度的健康折扣与既有的 `lowest_latency` / 首字竞速，没有做**上游吞吐/首帧速度的长期统计**（需要新增滑动窗口，另立目标更合适）。
- **用户侧**：① 服务商控制台轮换上游 key（T-sec-001）；② 上线（T-deploy-002）——本叉内置更新器写死上游仓库，只能人工替换二进制。
