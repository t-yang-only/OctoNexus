# 智能路由：只填一个模型名，按请求特征分档

## 需求来源

用户 2026-09-17 给出参考实现：[Step Router V1 智能路由](https://platform.stepfun.com/docs/zh/guides/models/step-router) ——
「只需在 `model` 字段填入 `step-router-v1`，系统会根据每次请求的特征在 `deepseek-v4-pro` 与 `step-3.7-flash` 之间自动调度：
复杂推理与长链路决策交由决策引擎，高频与结构化执行交由执行引擎，开发者无需自行实现分流逻辑」，
判定依据是**消息轮数、输入量、工具数量**，计费按实际命中的引擎算。用户要求「大概和这个相似的功能」。

## 设计（为什么这样做）

1. **客户端零改动**：本项目里「分组名就是客户端请求的模型名」，所以新增一个分组模式就等于给了用户一个 `step-router-v1`
   那样的虚拟模型名 —— 不需要新协议、不需要客户端配合。
2. **判定看请求、不看成员统计**：与参考实现一致。三项特征等权归一到 0..100，取平均得复杂度评分；
   阈值可配（`relay_config.smart_route_threshold`，1..100，缺省 50）。
   等权带来一个可解释的性质：**单项特征最多 33 分（低于默认阈值），任意两项 ≥ 66 分（高于默认阈值）** ——
   这正是活体套件 S3 灵敏度阶梯断言的那条线。
3. **档位 = 成员顺序**：靠前的成员是决策引擎档，靠后的是执行引擎档（双成员时就是「一强一快」两档，与参考实现同构）。
   好处是不新增表字段、不动迁移、不依赖统计数据，用户拖拽顺序就能表达「复杂走 A、简单走 B」；
   用子分组时更是天然的「两条链」两档。
4. **档内沿用既有选路**：加权轮询开启时走加权，否则按成员顺序（failover 语义）；冷却/探测/亲和仍归顶层 RouteState。
5. **档内无人可转发时回退到全体成员**：档位只是「优先考虑谁」，不是「只许用谁」。
   简单请求占多数，如果执行引擎档整档掉线就放弃，会把「省钱」变成「不可用」—— 这条回退是刻意的，
   活体用例 S5 用「决策档上游必失败 → 冷却 → 换人」的真实失败路径验证它。

## 边界与未做（写在这里以免误以为已覆盖）

- **不做 LLM 分类器**：判定只用请求形状（与参考实现文档描述的口径一致），不额外发一次模型调用，也不产生费用。
- **不按统计自动分档**：档位只由成员顺序决定。若将来要「按实测质量/成本自动分档」，是另一种取径（需要明确
  数据缺失时的先验，否则会出现「便宜但常失败」的成员被当成执行引擎）。
- **亲和会短暂覆盖档位**：`member_affinity_seconds` 是故障切换后的粘性设置，亲和期内请求继续走当前成员。
  默认 0（不粘），需要稳定分档就把亲和留 0；这是既有可靠性设置，不在本模式内改动。
- **档位没有单独写进请求日志字段**：日志行里的 `target_channel` / `target_model` 已经能看出是谁服务的；
  若要「为什么选了它」的一句话直接落到日志/响应头，属于观测性增强，待用户确认是否需要。
- 阈值只在 `smart` 模式下被读取，其它模式行为与改动前逐字一致（S7 + 全量矩阵为证）。

## 判据灵敏度（变异检查，T-smart-005）

沿用本仓库的变异纪律：把守卫改回旧行为/改值，要求**指定用例变红**，否则那条判据可能是空转的。
四条各自的读数（明细取自套件输出）：

| 变异 | 改的是什么 | 期望变红 | 实测明细 |
| --- | --- | --- | --- |
| SM1 | 档位切分：执行档返回全体成员（等于不分档） | S1 | 简单请求命中 `mock-good`（期望 `mock-plain`）；连带 S3/S4/S8 也红 |
| SM2 | 评分：工具数量这一维不计分 | S3 | 阶梯里「8 轮 + 8 工具」与「8 工具 + 长正文」两条掉到执行档（降为 37 分） |
| SM3 | 回退：档内选不出人时返回零值 | S5 | 复杂请求 HTTP **502**、上游模型 `mock-bad`（不再回退到执行档） |
| SM4 | 竞速候选不再按档位收敛 | S8 | 复杂请求的上游尝试变成 `['mock-good', 'mock-plain']`（把执行档拉进了竞速） |

其中 SM3 的锚点一开始写错了（把 `pickGroupItemByMode` 写成了带特征的同名变体），首次跑报「锚点命中 0 次」，
修正后单跑该变异，S5 如期变红。变异跑完自动还原并重建，随后复跑 streamidle 9/9、retry 9/9 全绿。

## 与首字竞速的交叉点（T-smart-004）

竞速候选走的是 `hedge.go` 自己的模式分派，`smart` 落进默认分支后会把**全体成员**当候选 ——
简单请求因此可能把靠前的强成员一起拉进竞速跑一遍：复杂度分档的成本控制被竞速绕过，
而且竞速本身就要多发请求，等于花了贵渠道的钱还没走分档。

修复：新增 `rankedHedgeCandidatesWithFeatures`，`smart` 下先在选中那一档内竞速（档内走 failover 口径，
含加权轮询与延迟档内排序），档内没有可竞速成员时与选路一致地回退全体成员；其余模式逐字不变。

读数：单测 `TestRankedHedgeCandidatesStaysInsideTier` 通过；活体 S8（四成员分组：决策档两名 + 执行档两名，
开启竞速 width=3 / after_ms=1）—— 简单请求上游尝试 `['mock-plain','mock-plain']`（两条竞速路都在执行档）、
复杂请求 `['mock-good','mock-good']`，都不越档；SM4 变异后立刻变红，证明这条判据不是空转。
