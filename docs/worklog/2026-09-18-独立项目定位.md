# 独立项目定位（T-identity-001）

> 日期：2026-09-18
> 分支：`master`（工作区改动，未提交）
> 用户原话：「那么就不要本本项目设置为分叉,直接建立一个自己的项目,标注是基于什么项目进行升级就行了」

## 1. 先把事实查清（不要凭"听起来像"动手）

| 待核实 | 实测结果 |
| --- | --- |
| GitHub 上 `t-yang-only/OctoNexus` 是不是 fork？ | **不是**：`gh api repos/t-yang-only/OctoNexus` → `fork=false`、`parent=null`、`source=null`（描述里已写明 "Octo (from bestruirui/octopus) + Nexus"） |
| 那是"哪里"把它当成分叉？ | **本地 remote 布局**：`origin` 指向上游 `bestruirui/octopus`，自己的仓库反而叫 `octonexus`；`master` 跟踪 `octonexus/master`（ahead 126） |
| 上游许可到底是什么？ | `LICENSE` 首行 = **GNU AFFERO GENERAL PUBLIC LICENSE**；GitHub 识别为 **AGPL-3.0**。而 `README_zh.md` 当时写的是 **GPL-3.0** —— 归属信息写错了 |
| 内置更新器指向谁？ | `internal/update/update.go` 的 `updateUrl` / `updateApiUrl` 写死上游 `bestruirui/octopus` |

结论：GitHub 侧不需要"取消分叉"（本来就不是）；要改的是**本地 remote 名义**、**文档归属措辞**与**产品自身的更新来源**。

## 2. 改了什么

1. **remote 名义归位**（本地动作，可逆）：`git remote rename origin upstream` → `git remote rename octonexus origin`。
   现在 `origin` = 本项目仓库、`upstream` = 上游（只读参考），`master` 跟踪 `origin/master`。
   默认 `git push/fetch` 都落在本项目上；不会再"顺手把本项目的历史推到上游"或"把上游当主线跟进"。
2. **新增 [`docs/项目定位.md`](../项目定位.md)**：仓库身份表（origin/upstream/许可/分支）、与上游的关系
   （血缘 + 本项目升级了什么 + 上游同步策略）、发布与更新通道、以及"不要把本项目当分叉去跟进"的口径。
3. **归属措辞统一**（都是可核准的外部事实，不做风格润色）：
   - `README.md`：`an extended fork of bestruirui/octopus` → **独立项目**（不是 GitHub 分叉网络成员）+ 许可 AGPL-3.0 + 指向项目定位文档；
   - `README_zh.md`：同上，并**修正许可**（GPL-3.0 → AGPL-3.0）；
   - `CLAUDE.md`：写清 origin / upstream 各自是什么；
   - `docs/worklog/README.md` 抬头：仓库地址与跟踪关系（remote 改名后原文已失真）。
4. **更新源改归本项目**（这是"独立项目"里唯一会被用户直接踩到的一处）：
   `internal/update/update.go` 的 `updateOwner/updateRepo` 改为 `t-yang-only/OctoNexus`。
   理由：本项目已比上游多出 126 个提交，更新源若留在上游，产品里的"检查更新"会把**上游原版二进制**装进来 ——
   那不是升级，而是把本项目的能力整套抹掉（用户只会感觉"更新完就坏了"）。
   宁可明确报"没有可用版本"（本项目尚未发布 release，这是预期行为），也不装错东西。

## 3. 判据

- 新增 `internal/update/update_test.go`：双向断言 —— 更新源必须指向本项目坐标，且**不得**出现 `bestruirui/octopus`；
  两个 URL 必须同仓、且都是 https（一个查版本、一个下包，指到不同仓库会出现"查到有新版、下的是别人的包"）。
- 变异 `ID1`（把 `updateOwner/updateRepo` 改回上游）→ 判据**变红**（`TestUpdateSourcePointsAtThisProject` 明确报出坐标不对），还原后复跑绿。
- `git remote -v` 实测：`origin` = `https://github.com/t-yang-only/OctoNexus.git`，`upstream` = `https://github.com/bestruirui/octopus.git`；
  `git branch -vv` 实测：`master dba9de4 [origin/master: ahead 126]`。

## 4. 未做 / 需要用户决定的

- **GitHub 仓库描述**保持原样（"Octo (from bestruirui/octopus) + Nexus: …"）：它已经表达了"基于某某"，
  没有"fork"字样；要不要再改文案由用户定（改动会写进 GitHub 侧，属外部可见动作）。
- **发布第一个 release**：内置更新器要真正可用，本项目 release 资产必须按 `octopus-<os>-<arch>.zip` 命名
  （与 `internal/update/core.go` 的规则一致）。发布属外部动作，等用户授权。
- 上游仍需**对照**（issue/PR 同源问题一并解决，见 `docs/agents/需求登记.md` 的 `R-upstream-*`），
  但那是"参考"，不是"跟着上游走"。
