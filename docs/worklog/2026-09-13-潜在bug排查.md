# 2026-09-13 Octopus 潜在 Bug 排查报告

- 台账编号：`NM-CUR-022`
- 方法：纯静态通读 Go 后端（`relay/handler|route|state|upstream|protocol|channel`、
  `op/stats|apikey|group|channel|llm|backup|user|cache`、`server/*`、`update/*`、
  `price/*`、`task/*`、`rhttp/*`、`db/*`）+ 关键调用链交叉验证（rg 调用方枚举）。
  未运行时验证、无 Go 工具链（T-env-001），标注"已验证"的均为源码级确认。
- 结论：**2 Critical + 4 High + 9 Medium + 12 Low/Warning**。纯研究，未改任何业务代码。

## Critical（数据丢失 / 计费 silently wrong）

### C-1 自动价格同步从不落库，计费长期用旧价，还显示"已更新"（已验证）

- 计费读的表：`usageMetrics` → `op.LLMGet` → `llmModelCache`（DB 回填，
  `internal/op/llm.go:145`），落库唯一入口是 `LLMBatchSave`。
- `price.UpdateLLMPrice` 的调用方只有两处（rg 全仓枚举）：
  `task.Init()` 定时任务（`internal/task/init.go:28`）和"更新价格"按钮
  （`internal/server/handlers/model.go:170`）；两者都**只刷新 `price` 包内内存
  `llmPrice` map**（`internal/price/price.go` 末尾三行），没有任何写 DB /
  刷 `llmModelCache` 的动作。
- `LLMBatchSave` 的唯一调用方是"重建价格"（`model.go:193`）。
- 后果：README"自动更新模型价格"实际只更新了模糊匹配参考表；
  `/model/last-update-time` 显示新鲜时间，造成"价格已同步"假象，计费继续按旧价。
- 修复：定时任务末尾接 `LLMBatchSave`（或明确语义并打 warn）；`update-price`
  成功后返回实际生效的模型数而非空。

### C-2 跨天首个请求触发全量统计同步落库：阻塞转发 + 失败即丢前一天数据（已验证）

- 链路：`finishLocked`（`relay/state.go`，**调用时持有 relay 全局 `mu`**，
  `markSucceeded/markFailed/markCanceled` 均先 `mu.Lock()`）→
  `op.StatsDailyUpdate` → 日期翻天 → `statsSaveDBWithDailyOverride` →
  `persistStatsSnapshots`（total+daily+hourly+全部脏渠道/模型/凭据/apikey，顺序写库）。
- (a) 延迟：一次普通转发的收尾路径里同步做全量 DB flush，期间 relay 全局锁被占住，
  全部在途请求的状态推进与 SSE 推送都被挡住（SQLite 单写者下可达秒级）。
- (b) 丢数：`prevDaily` 已在内存中被新日期替换；若本次 persist 失败，
  `restoreStatsDirty` 只恢复脏 ID 集合，**前一天的增量永久丢失**（内存里已没有它了）；
  且 `finishLocked` 用 `_ =` 吞掉了这个错误。
- 修复：翻天时只 swap 内存、把"落旧日"交给后台 flush 任务
  （已有 `StatsSaveDBTask` 机制，加一个 pending-daily 队列即可）；
  收尾路径永不做同步 DB 写。

## High（可用性 / 安全）

### H-1 转发主循环无整体上限：坏分组 = 连接无限挂起（已验证）

- `relay/handler.go` 的 `for {}` 在以下情况 `wait + continue` 永不返回：
  无可用成员（全冷却/全不可用，`item.ID == 0`）、授权缺失、渠道被删、分组被删。
  注释写"可能很快被改回可用配置"——但若配置永久损坏，连接挂到客户端超时。
- 联动：H-2（Server 零超时）使服务端也永不掐断；联动 M-2（协议位全非法同样永挂）。
- 修复：整请求 deadline（如 `RelayConfig` 新增 `max_total_seconds`，默认 300s），
  超时按 502 定稿；或"连续 N 轮无可用成员"直接失败。

### H-2 双端口 `http.Server` 零超时配置（已验证）

- `server/server.go`：`adminSrv`/`relaySrv` 均未设 `ReadTimeout/ReadHeaderTimeout/
  WriteTimeout/IdleTimeout` → Slowloris 可零成本占满连接；配合 H-1 更易堆积。
- 修复：`ReadHeaderTimeout: 5s` 必加；relay 写超时要大于流式长尾，设 1h 或按分组超时来。

### H-3 登录接口无速率限制 + bcrypt 可被动烧 CPU（已验证）

- `/api/v1/user/login` 未认证可达，每次走 `bcrypt.CompareHashAndPassword`
  （`op/user.go:UserVerify`，DefaultCost）；无失败计数/退避 → 未认证 CPU 耗尽向量。
- 修复：登录失败计数 + 指数退避（内存即可）。

### H-4 CORS `*` 与 `AllowCredentials=true` 可组合（已验证）

- `middleware/cors.go`：`AllowCredentials=true` 写死，`AllowOriginFunc` 允许配 `"*"`。
  一旦配了 `*`，任意站点可凭受害者 cookie **读取**管理接口响应
  （含渠道凭据明文、API Key）。
- 修复：`allowed=="*"` 时强制 `AllowCredentials=false` 并打 warn；或文档明确禁止该组合。

## Medium（正确性 / 运维）

### M-1 `APIKeyDelete` 删错映射，僵尸映射永久残留（已验证）

- `op/apikey.go:APIKeyDelete`：`k := model.APIKey{ID: id}`（`APIKey` 字段为空），
  末尾 `apiKeyIDMap.Del(k.APIKey)` 实际删的是 `""` 键，**真实 key→id 映射永远残留**。
- 现状安全方向正确（`APIKeyGet` 查不到 id 仍 401），但 map 无界增长；
  且 `apiKeyRefreshCache` 只增不减，重启才清理。
- 修复：删除前先 `APIKeyGet` 取出旧串再 `Del`。

### M-2 出站构造失败被记成"渠道故障"，可误伤冷却（已验证）

- `handler.go`：`buildOutbound` 返回 err（如授权协议位全非法）后仍走
  `request.startRound` → 失败分支 → `ChannelStatsUpdate(RequestFailed=1)` +
  `recordRouteFailure`（攒够 2 次即冷却该成员）。
- 本地配置错误被记为上游故障并污染成功率、触发冷却转移。
- 修复：`buildOutbound` 失败直接 `markFailed + 502`，不计渠道失败、不进冷却。

### M-3 渠道/成员失败计数含重试轮次，与请求级口径不一致（已验证）

- 每轮失败都给渠道/模型/凭据 +1 `RequestFailed`（`handler.go` 错误分支），
  而请求级（total/hourly/daily/apikey）只在终态记一次（`state.go:finishLocked`）。
- 渠道页"成功率"分母天然大于全局请求数，重试越多的渠道看起来越差——
  恰好是故障转移最卖力的渠道。可接受但必须在 UI 注明口径，或拆 `attempt_failed` 列。
- 同类：`WaitTime` 在渠道侧记的是失败轮耗时，请求侧记全程，两处不可比。

### M-4 定时任务无单飞保护，并发落库可 last-writer-wins 回退（已验证）

- `task/task.go:runTask` 每 tick 起一个 `go entry.fn()`；`StatsSaveDB` 超过间隔即重叠。
- 两次 flush 各自读快照、各自写库，后写者用旧 total 覆盖新 total（内存缓存不受影响，
  下次 flush 自愈，但 DB 里出现统计回退）。
- 修复：`sync.Mutex` try-lock 跳过重叠执行，或 `singleflight`。

### M-5 `/v1/models` 按请求头选形状而非按客户端协议（已验证）

- `handlers/model.go:getModelList`：带 `x-api-key` 头 → Anthropic 形状，否则 OpenAI 形状。
  但两种鉴权头都可调三种协议——用 Bearer 调 `/messages` 的客户端拿到 OpenAI 形状的
  models 列表，部分 SDK 会校验 `object=="list"` 失败。
- 修复：按路由端点定形状，或同时返回两种字段。

### M-6 备份导入不碰 relay 内存路由状态（已验证）

- `importDB`（`handlers/setting.go`）末尾只 `op.InitCache()`；`relay.routes` 里旧分组的
  冷却/亲和/探测残留：同 ID 不同语义的分组会继承旧冷却；已删分组条目永久泄漏。
- 修复：导入成功后按导入的分组 ID 集合调 `relay.ResetRouteState`。

### M-7 备份导入整文件 `io.ReadAll` 进内存，无上限（已验证）

- `importDB` 两条路径（multipart / raw JSON）都是无界 `ReadAll`；
  统计量大的库导出数百 MB，一个请求即 OOM。仅 admin 可达，仍应
  `http.MaxBytesReader` 设限（如 256MB）+ 超限 413。
- 同类（未核实，axonhub 侧）：relay `httpclient.ReadHTTPRequest` 的 body 上限。

### M-8 JWT 密钥派生自用户名+密码哈希

- `server/auth/auth.go`：`secret := user.Username + user.Password`。
  改名/改密即全员 token 失效（副作用上倒是"自动登出"，但不可控）；密钥强度绑定口令。
- 修复：首次启动生成独立随机密钥落库/env 可覆盖（升级报告 P0-1 已列）。

### M-9 管理 cookie 无 HttpOnly/Secure

- `handlers/user.go:52` 与 `middleware/auth.go` 清理 cookie 两处：
  `SetCookie(..., false, false)`。XSS 可盗 admin 会话；非 localhost 明文传输。
- 修复：HttpOnly=true 必做；Secure 跟随"是否公网/TLS"配置。

## Low / Warning（边缘、提供方相关，需用例确认）

- L-1 `protocol.go`：OpenAI Chat 流中任一非 JSON data 行即判整流失败；
  提交后才发现时会把已交付部分记 `failed`。部分网关的 ping 行可触发，建议只跳过不认识的行。
- L-2 `protocol.go`：Anthropic SSE 事件名与正文 `type` 不一致即失败；
  经改写事件名的代理会全灭，可降级为 warning。
- L-3 `handlers/channel.go:fetchAnthropicModels`：`HasMore` 恒真 + `LastID` 不变则分页死循环，加 100 页上限。
- L-4 `op/group.go:syncGroupItems` / `op/channel.go` 三 sync：请求内重复 grant/重名 key-model
  靠 DB 唯一键兜底 → 500 无友好错误；入口加重复项校验即可。
- L-5 `handlers/channel.go:updateChannel`：渠道已落库后价格写入失败才返 500，
  客户端重试会撞渠道名唯一键；应先写价格或返回 207 语义。
- L-6 `handlers/model.go`：OpenAI models 列表 `Created: 1763395200` 硬编码，改成 `time.Now()`。
- L-7 `relay/route.go`：`Cooldowns` 过期条目不清（仅删成员时清理），长期运行的组常驻小 map；
  顺手在 pick 时删 `deadline<=now` 且非探测中的项。
- L-8 `db/db.go`：SQLite `MaxOpenConns=100` 配单写者 + busy 5s，高并发下 flush 易失败；
  写路径收敛到小池或调大 `busy_timeout`。
- L-9 自更新无校验和/签名、重启不排空（升级报告 P0-4/P1 已列，此处只记 bug 性）。
- L-10 渠道改名产生孤儿自动分组（worklog 已有遗留三连，此处引用不展开）。
- L-11 小时统计仅保留当日（升级报告 P1-14 引用）。
- L-12 `login` 的 `Expire` 参数无钳位：极大值可使 token 有效期计算溢出（需登录态才可达，自残级）。

## 有意不报（已核实无问题）

- `sendPassthroughStream` 非 2xx 路径：`ReadAll` 后 `Close` 再判错，body 已关，无泄漏。
- `probeRequest` 超时：`WithContext` 正确覆盖传入 ctx，无泄漏。
- JWT `exp/nbf`：jwt/v5 `Parse` 默认校验时间 claims，无"永不过期 token"问题。
- `UserChangePassword/Username` 改密钥派生材料 → 旧 token 自动失效，符合预期。
- `interruptRound` 轮次失配丢弃：注释已说明语义，非 bug。
- `decodeDBDump` 空文件兼容旧 `{code,message,data}` 包裹：容错存在，非 bug。
- `decodeModelList` 先判状态码再解 JSON：已防"错误 JSON 解成空列表"，正确。
- `rhttp.Proxy()` 双重检查锁 + 旧客户端 `CloseIdleConnections`：正确。
- 渠道专用代理独占客户端的 `closeIdle` 移交：透传/转换两条流式路径均已覆盖，未发现泄漏。
- `clearActiveItems` 的子查询用法（`grantsOf` 传 `*gorm.DB` 进 `IN (?)`）：GORM 支持，非 bug。
