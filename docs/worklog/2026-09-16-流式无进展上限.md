# 流式「无进展」上限（T-timeout-001）—— 首帧之后不再把客户端挂到放弃

> 触发来源：用户服务器日志包 `D:\奇怪的软件\octopus-本地数据\`（只读，未提交）中的 Caddy 网关日志（2026-09-09 ~ 09-13，当时版本 v0.13.2）。

## 一、现象与证据

日志去重后 321 条，其中 `http.log.error` 60 条：34 × 502 + 26 × 504，除 2 条外全部来自境外自动化客户端（64.90.x.x），49 条打在 `/v1/chat/completions`、11 条打在 `/v1/responses`。

时长分布（有明确耗时字段的 51 条）：min 16.3s、**中位 343s**、max 761.5s；39 条 ≥ 300s、51 条 ≥ 120s。另有 258 条 `aborting with incomplete response`（客户端在收到部分响应后放弃）。

当时生效的成员中继配置（`relay_config.json`）：

| 配置项 | 值 |
| --- | --- |
| member_stream_first_event_timeout_seconds | 25 |
| member_non_stream_response_timeout_seconds | 120 |
| member_max_attempts | 2 |
| member_retry_interval_seconds | 1 |
| member_cooldown_seconds | 600 |
| member_affinity_seconds | 30 |

非流式最坏耗时 = 2 × 120 + 1 = 241s < 观测到的中位 343s / 最大 761s ⇒ **这些是流式请求**。流式当时只有 25 秒「首事件」上限，首帧之后没有任何上限。

## 二、根因

1. `internal/relay/upstream.go`（127-138）为流式只在**读到第一个事件**后返回 `upstreamResponse{events, first, last}`。
2. `internal/relay/handler.go` 的单路分支在 `sendPassthrough` 返回后即 `timeoutTimer.Stop()`（约 193 行）——本轮上限只覆盖「首帧之前」。
3. 随后的转发循环 `if !result.events.Next()` 是**没有任何 deadline 的阻塞读**；SSE 解码器来自依赖 `github.com/looplj/axonhub/llm@v0.0.0-20260909170523`，其 `httpclient/decoder.go`（348 行，bufio 实现）全文**没有 Timeout/Deadline**。

⇒ 上游吐完首帧就静默时，连接一直挂着，直到客户端自己放弃（正是日志里的 300–760s）。这不是「慢」，是「没有上限」。

## 三、修复

新增分组中继配置 `member_stream_idle_timeout_seconds`（语义：两次「进展」之间允许的最长间隔）：

- 默认值 300 秒（`DefaultGroupRelayConfig`）；**0 = 关闭**；负数归零。
- 归一化**不用默认值兜底**：`NormalizeGroupRelayConfig` 只把负数改成 0，于是存量分组（库里存的 JSON 没有该键 → 0）升级后行为不变 —— 不静默改变线上行为。
- 计时器在「成功写给客户端一帧」与「读到新事件」两处重置；命中后通过 `cancelRoundCause(errStreamIdleTimeout)` 结束本轮。
- 循环结束后把 `context.Cause(roundCtx)` 还原为 `errStreamIdleTimeout`，使记账走 `markFailed`（真实失败，计渠道/成员/凭据统计），而不是被取消读错误误判成 `canceled`。
- 首字节已提交 ⇒ 遵循既有铁律**不换目标重试**，直接把这次响应结束。

配套（同一根因的另一面）：`/api/v1/group/events` 的 SSE 处理器原来**连上不发任何字节**，心跳恰好 15 秒——与常见 15 秒空闲上限同刻竞速。日志里 107 条该连接全部在 15.001–15.015s 被客户端断开，正是这一处。修复：连接后立即发 `: connected` 注释帧，心跳 15s → 10s；`/api/v1/log/overview/stream` 心跳同口径改为 10s。

## 四、验证

**单元测试取舍（写明理由）**：`internal/relay` 现有 15 个单测全是选路器纯函数测（无 HTTP 端到端夹具），而本保护在转发循环里；按仓库既有惯例用 mock 驱动的活体套件验证。

新增活体套件 `scripts/api-tests/run_stream_idle_test.py`（已注册进矩阵，共 28 套件），装置 = 新渠道 `DS-TEST-idle` 指向本地 mock，模型名 `mock-stall`（mock 只发第一个 SSE 帧，然后保持连接静默：不写 `[DONE]`、不关连接）：

| 用例 | 读数 |
| --- | --- |
| I1 装置就位：新字段可写入且读回 | channel=48 grant=471 idle=2 |
| I2 看门狗生效：首块先到、响应在 2s 后被结束 | HTTP 200 首块 0.0s 总 2.01s 收到 214B |
| I3 记账：relay_logs 记 failed 且已有首字节 | `('failed', 'DS-TEST-idle', 2)` |
| I4 成员统计：request_failed +1 | 渠道统计 before=0 after=1 |
| I5 不换目标重试：上游只收到 1 次尝试 | member_max_attempts=2 但上游收到 1 次 |
| I6 判据 0=关闭：3 秒时请求仍在途中 | idle=0 在途=True |

**I2 与 I6 构成同一二进制内的对照实验**：同一个静默上游、同一个模型，唯一差别是 `member_stream_idle_timeout_seconds`（2 vs 0）——2 时响应在 2.01 秒结束，0 时 3 秒仍在途中。这就是「是这个看门狗结束的响应」的直接证据，无需再靠摘代码的变异验证。

面板侧：分组编辑表单新增该字段（min=0）+ 三语文案；`scripts/api-tests/run_panel_asset_test.py` 新增 P7 断言产物里含 `streamIdleTimeout` 与三语文案（防「源码改了、产物没重建」）。PANEL 7/7。

## 五、测试装置顺带修掉的两处口径错误（非产品缺陷）

1. **成员统计不能读库**：`op.ChannelModelStatsUpdate` 是内存缓存累加 + 周期性落库（`channelModelCache` + `channelModelStatsNeedUpdate`），所以直读 `channel_models.request_failed` 永远是旧值。套件改为读 `/api/v1/channel/stats`（返回的就是运行时缓存）。首版断言 `before=0 after=0` 即此坑。
2. **首块耗时不能信 `resp.read(n)`**：Python `HTTPResponse.read(n)` 对分块响应会读到凑够 n 字节，量到的是「流结束时刻」而不是「首块到达时刻」（首版读数为 `首块 2.04s 总 2.04s`）。改用 `read1()` 后读数变为 `首块 0.0s 总 2.01s`，这才真正证明了「首字节先提交、随后被结束」。

## 六、待用户决定

存量分组的 `member_stream_idle_timeout_seconds` 保持 0 = 关闭（不静默改变线上行为）。是否给现有分组统一打开（例如都设 300 秒），需要用户一句话；打开后可能误伤「假流式」中转站（正文要等整段生成完才下发），所以默认值取宽松的 300 秒。
