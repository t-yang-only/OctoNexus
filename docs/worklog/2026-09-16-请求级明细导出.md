# 请求级明细导出（U-key-001 余项 / T-export-001）

> 目标：`relay_logs` 里的请求级明细（输入/输出 token、缓存命中、费用、首字与总耗时、命中渠道与模型、错误）
> 一直是齐的，缺的只是**能拿出去的出口**。本轮补上 CSV 导出（后端接口 + 面板按钮）。
> 这是需求事实源 §4 未立项项第 5 条（U-key-001 的剩余部分）。

## 1. 口径

- **与面板同一套筛选**：`status` / `model` / `channel` / `apikey` / `q` 与 `/api/v1/log/history` 完全一致
  （共用 `relayLogQuery`，避免"看到的"和"导出的"两套条件口径）；导出不分页 —— 导出就是"当前筛选的全量"。
- **流式写**：逐行 `Rows()` + `ScanRows` 直接写进响应，内存不随条数增长（先把整表拉进切片再导会先 OOM）；
  单次上限 `RelayLogExportMaxRows = 200000` 行，达到即截断并记 Warn 日志。
- **给 Excel 的 BOM**：首行前写 UTF-8 BOM，否则 Excel 打开中文表头是乱码。
- **不给下游留假值**：未提交首字节在库里是 `-1`，导出成空串，让表格工具按"无数据"处理、不污染均值。
- **第一列是日志行主键，不是请求 ID**：一个客户端请求可能留多行（重试/多轮），请求 ID 会重复，
  只有行主键能唯一定位一行（本轮实测 457 行里有重复请求 ID 的情况）。
- **协议列给人看**：导出可读名（`openai-chat` / `openai-responses` / `anthropic-messages`），不导位掩码数字。
- 响应头 `Content-Type: text/csv; charset=utf-8` + `Content-Disposition: attachment` + `X-Accel-Buffering: no`
  （导出可能很大，让浏览器尽早开始落盘、别被中间层缓冲）。

## 6. 踩坑

- **请求 ID 不是行标识**：首版导出第一列给请求 ID，用它跟 `/history` 对账时出现"同一 ID 匹配到不同行"的假失败
  （重试/多轮会为同一个请求留多行）→ 加"日志ID"列作为唯一行标识，对账与去重都以它为准。
- **`0` 是合法值**：测试脚本里写 `first_byte or -1` 会把"0ms 首字节"误判成"未提交"，必须显式判 `None`/`<0`。
- **流式响应里改不了状态码**：正文写出后再出错只能记日志，故实现里先做 BOM/表头再逐行写，
  并把写出失败的原因与已写行数一起记入日志，便于事后判断文件是否完整。

## 7. 未覆盖 / 后续

- 面板上的**导出范围选择**（时间范围、按 Key 分文件）没做：当前导出沿用内存筛选栏的状态与关键字，
  时间范围筛选尚未进入 `/history` 与导出（两者共用同一套参数，后续一起加即可）。
- 导出**不落审计**（谁在什么时候导了多少行）；`/api/v1/log/clear` 已有删除动作，导出若也要留痕需另加审计表。
- 超过 20 万行只截断不提示（日志里有 Warn，接口响应没有提示头）；如需精确提示可加 `X-Export-Truncated` 头。
