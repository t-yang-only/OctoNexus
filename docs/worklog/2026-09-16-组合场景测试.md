# 组合场景测试：加权 × 计费 × 竞速 × 流式 × 冷却 × 日志统计

日期：2026-09-16　执行：dsh-local（NM-DS-021 / 台账 T-test-005）

## 1. 为什么补这一套

到本轮为止，每个特性都有自己的活体套件：`weighted`（加权选路）、`hedge`（首字竞速）、`failover`、`probe`（冷却探活）、
`stats`/`reallog`（日志统计）……但**没有一个套件验证它们叠在同一个分组上还成立**。
按用户「细致的往完成调用测试工作」的要求，这一轮补的就是这个缺口：`scripts/api-tests/run_combo_test.py`。

装置（只用本地 mock）：一个 `weighted` 模式的分组，两条成员来自**两个不同渠道**——
便宜渠道放 `mock-slow`（上游 sleep 15s）、贵渠道放 `mock-good`（顺带写上倍率 3 / 按次 0.02）。

## 2. 五个用例与结果（5/5 通过）

| 用例 | 断言 | 实测 |
| --- | --- | --- |
| C1 加权选路 + 首字竞速 | 权重只给延迟 → 排名把慢成员放第一；竞速 800ms 后并发快成员，快者胜出且两条成员都被尝试过 | HTTP 200，**0.8s**，上游尝试 `['mock-slow','mock-good']`，命中渠道=贵渠道（快成员所在）|
| C2 组合下落选者不进冷却 | 被竞速取消的慢成员不冷却、不记失败 | 慢成员 item=1410，`cooldowns={}` |
| C3 计费权重决定胜者（关竞速）| 倍率权重拉满 → 倍率低的渠道胜出（哪怕 priority 靠后），且不触发竞速 | HTTP 200，**0.0s**，上游只被尝试 **1** 次，命中贵渠道（倍率 3 < 便宜渠道的 5）|
| C4 组合下日志统计一致 | 每个请求恰好一行日志，成功行带首字节 | 行数 2→3，末行 `('success','DS-TEST-combo-price','mock-good', 2ms)` |
| C5 流式 + 竞速 + 加权 | 首个 SSE 块由竞速胜出的成员给出 | HTTP 200，首块 **0.8s**，两条成员都被尝试 |

关键点：C1/C5 证明「加权把慢成员排第一」这种看起来会变慢的选择，会被竞速兜住；
C3 证明计费权重（倍率/按次/余额/包月）真的参与决策，而不是摆设；C4 证明这些组合动作不会把统计打歪。
