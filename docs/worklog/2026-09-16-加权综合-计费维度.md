## 1. 这一阶段补了什么

用户点名的六个维度里，上一阶段落了「质量」，这一阶段补齐**倍率 / 按次 / 余额 / 包月**：

| 维度 | 数据来源 | 方向 | 默认权重 |
| --- | --- | --- | --- |
| 倍率 | 渠道新字段 `multiplier`（用户填）| 越低越好 | 15 |
| 按次单价 | 渠道新字段 `per_call_price`（用户填）| 越低越好 | 10 |
| 余额 | **配额扫描**读到的剩余额度（内存快照，不落库）| 越多越好 | 15 |
| 包月余量 | 渠道新字段 `monthly_quota` / `monthly_used`（用户填）| 剩余比例越高越好 | 10 |

- 渠道上新增 5 个可空字段：`billing_mode`（metered 按量 / per_call 按次 / subscription 包月 / 留空未知）、`multiplier`、
  `per_call_price`、`monthly_quota`、`monthly_used`。全部由 GORM 在启动时自动加列（纯增量、可空、不动既有数据），
  实测重启后 `channels` 表确实多出这 5 列。
- **余额不需要用户填**：配额扫描本来就会取到 `quota/used/remaining`，这次把 `remaining` 也存进内存快照
  （`op.RecordChannelBalance` / `op.ChannelBalance`），加权选路直接读它。
  重启后到下一轮扫描前按「未知」处理（与乐观先验一致，不会因为重启就把某个成员永久打死）。
- **包月用尽的处置做成了设置项** `route_monthly_exhausted_action`：
  `demote`（默认，降权——该维度 0 分，但仍可能被选到）/ `exclude`（剔除，不再参与；全员用尽时按无人可用处理，等下一轮）。
  这是用户点名的第三个取舍点，现在由用户拍板，不用改代码。

## 2. 过程中发现并修掉一个真实的接线缺陷（值得记下来）

第一版的活体用例 T6 一直失败：把倍率权重拉满、两条成员分别来自倍率 1 与倍率 3 的渠道，结果仍然选了倍率 3 的那条。
二分定位（把两个渠道都显式写上倍率再打一次）后确认**不是打分逻辑的问题，而是生产热路径根本没拿到计费数据**：

```go
// 旧: 热路径另抄了一份 routeDeps 字面量, 没有 billing
func pickGroupItemHot(group) { return pickGroupItemByMode(group, routeDeps{cost:…, quality:…, latency:…, busy:…, load:…}, …) }
// 新: 热路径统一走 hotRouteDeps(), 新增维度只在一处接线
func pickGroupItemHot(group) { return pickGroupItemByMode(group, hotRouteDeps(), RouteBalanceEnabled()) }
```

这类漏接线的特征很阴：**模式支持、单测全绿（单测自己注入 provider）、生产上该维度静默失效**。
修完加了一条守卫测试 `TestHotRouteDepsCoversEveryDimension`：`hotRouteDeps()` 的六个 provider 任何一个为空就红。
