# 最低延迟选路 lowest_latency（T-route-004 / NM-DS-006）

> 触发：「Iterative Upgrades」迭代——用户此前的目标是让网关能自动挑更好的 API 用
> 执行：dsh-local ｜ 状态：**已交付并活体验证**

## 1. 口径

1. **指标**：成员最近一次尝试的耗时。写点就在既有的成功/失败上报处——`recordRouteSuccess` /
   `recordRouteFailure` 增加 `latencyMs` 参数，handler 用已有的 `roundStartedAt` 差值填入
   （成功路径复用本来就要算的 `roundWaitTime`）。样本窗口 300s、写入时衰减、不落库、无后台协程，
   与质量样本同一张表同一把锁；
2. **排序**：耗时升序 → priority 升序 → ID 升序；**没有耗时数据的成员按 0ms 参与排序**（乐观先验，
   与 quality_first 的中性先验同哲学）：未知者先当成快的试一次、试出真相后自然沉底。若反过来按"无数据沉底"，
   新成员会被已知的慢成员永久压住——这是本轮刻意选择的取舍；
3. **过滤/冷却**与 lowest_cost / quality_first 完全同源（`partitionCandidates`）：不可用与剩余额度归零剔除、
   冷却成员压队尾、可尝试为空则等待；
4. 模式本身即开关：不选 lowest_latency 的分组行为一字不变；`route_balance_enabled` 语义不变；
5. 只有耗时 > 0 的尝试才更新耗时（上游错误等测不出耗时的情形不会把已知值冲成 0）。

## 2. 改动

| 层 | 文件 | 内容 |
|----|------|------|
| 指标 | internal/relay/metrics.go | 样本增加 `latency` 字段与 `memberLatencyMs` provider；文档口径改写为"成员指标"（质量+延迟共用） |
| 选路 | internal/relay/strategy.go | 新增 `routeDeps{cost,quality,latency}` 依赖结构体、`rankByLatency`、`memberLatencyScore`、`pickGroupItemLowestLatency` |
| 分发 | internal/relay/route.go | `recordRouteSuccess/Failure` 增加 `latencyMs`；`pickGroupItemByMode` 改为收 `routeDeps`；热路径注入 `memberLatencyMs` |
| 计时 | internal/relay/handler.go | 失败路径填 `time.Since(roundStartedAt)`、成功路径填已算好的 `roundWaitTime` |
| 模型 | internal/model/group.go | `GroupModeLowestLatency` + `IsValid` + 三处 binding oneof（按 5 点清单核对） |
| 前端 | web/src/api/group.ts、group/Editor.tsx、三语 locales | 模式下拉新增「最低延迟」，modeHint 同步扩写 |

顺带做了一次小重构：`pickGroupItemByMode` 原本是 4 个位置参数（cost/quality/balance），加上延迟会变成
5-6 个同形状的函数参数、极易传错，故改为 `routeDeps` 结构体；9 处测试调用点同步更新。

## 3. 验证

**单测 4 例**（internal/relay/latency_test.go）：延迟窗口（含"只记 >0 的耗时"与窗口过期）、
耗时定序（无数据按 0 乐观）、provider 未接线时退化为 priority 序、冷却成员压队尾、
模式真的改变选中的人（failover 按 priority 选慢成员、lowest_latency 选快成员），
以及**生产 provider 端到端**（先记录 5ms / 3000ms，选择随之反转）。加上既有质量测试，
relay 包与全量 `go test ./... -count=1` 九包全绿；前端 pnpm build 通过（产物含 lowest_latency）。

**活体 5/5**（脚本 run_latency_test.py；成员 mock-slow 上游 sleep 15s / priority 1，mock-good 正常 / priority 2）：

| 场景 | mock 上游收到的尝试 | 结果 |
|------|--------------------|------|
| DS-TEST-latency 第 1 次（双方无耗时数据 → 平手 → priority） | `['mock-slow']` | 200，**15.0s**：确实先撞慢成员 |
| 第 2 次（慢成员已记录 15s、快成员无数据按 0 乐观） | `['mock-good']` —— 慢成员 0 次尝试 | 200，**0.0s** |
| 第 3 次（两边都有耗时数据） | `['mock-good']` | 200，0.0s，最快者继续当选 |
| 对照 DS-TEST-latencyf（同成员同优先级、failover） | `['mock-slow']` | 200，15.0s 仍先撞慢成员 |

即"按延迟自动切换"成立：**15.0s → 0.0s，且不再浪费一次慢调用**。

## 4. 已知限制与后续

- 样本按**展平后的成员行**（GroupItem.ID）聚合：同一授权挂在不同分组里各算一份（跨分组不共享学习结果）。
  改成按 `ChannelGrantID` 聚合语义更对，代价是要动 8+ 处测试调用点与 handler 的取值，已记入 ledger 待办；
- `least_busy`（在途数最少）本轮未做：它需要在每次轮次的**所有出口**成对释放计数（含客户端取消、
  人工中止、失败继续、成功后移交流式），漏一处该成员就会永久显示"忙"、被后续请求一直跳过。
  已拆分为 ledger **T-route-006** 并写明要挂的钩子位置（handler.go 现有的两处 `releaseRouteProbe` 调用点 +
  `recordRouteSuccess/Failure` 内部，以及"选中成员"处的 acquire 侧）。

## 5. 踩坑

模式枚举仍是 5 点清单（常量 / `IsValid` / 三处 binding oneof / 备份导入校验 / 前端联合类型+下拉+三语）——
本轮按清单逐个核对，没有再出现上一次"漏 binding 导致建档 400"的问题。
