# 号池扩展层第三批：查询面与机器可读的操作清单（R-pool-ext-001）

日期：2026-09-16　执行：dsh-local（NM-DS-024）
上游：`.../2026-09-16-号池扩展性-design.md`、`2026-09-16-号池扩展层接口.md`（第一批）、`2026-09-16-号池扩展层生命周期操作.md`（第二批）

## 1. 这一批解决的问题

前两批让外部工具能"发现后端"（`/kinds`）和"调操作"（`/entries/:kind/:id/{probe,...}`）。
但真正接一个工具箱进来时，还会立刻撞到两种问题：

1. **问不出细分问题**：池子里哪些是停用的？哪些 24 小时内到期？某个账号在哪几条里？——只有"全部列出来"是不够的。
2. **得硬编码路径**：工具要自己记住"probe 是 POST 到 /entries/{kind}/{id}/probe"，octopus 一改路径它就崩。

所以这一批补：**过滤/汇总/导出** + **操作清单（Operations）**。

## 2. 新增内容

**`internal/pool/query.go`**（新文件，避免 pool.go 继续膨胀）：

- `Filter` + `ParseFilter`：按 kind / provider / status / 名称子串 / enabled / healthy / 有无到期时间 / 多久内到期过滤；
  非法取值**报错**而不是静默当 false —— 否则"过滤没生效"看起来会像"没有数据"。
- `ListResult`：同时回 `total`（过滤后）与 `scanned`（过滤前），调用方一眼看出"被过滤掉了"还是"后端本来就空"。
- `SummaryOf`：总数/启用/停用/健康/不健康/带错/24 小时内到期/已过期 + 分后端/分服务商/分状态 + 取不到数据的后端（`kind_errors`），
  让"池子是空的"与"某个后端坏了"可区分。
- `ExportRows`：固定字段的扁平行（**结构里没有任何凭据字段**，并有单测用 JSON 序列化断言不含 token/cipher/secret/password/api_key 字样）。
- `Operation` + `operationsOf`：**由能力位推导**的 HTTP 调用清单。声明了 `probe` 就自动有 probe 那条路由——
  自描述与实际路由不可能漂移，外部工具照清单渲染按钮即可。

**新增接口**：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/pool/entries?...` | 新增过滤参数：`kind/provider/status/q/enabled/healthy/expiring_within/has_expiry` |
| GET | `/api/v1/pool/summary` | 汇总视图（切分维度见上） |
| GET | `/api/v1/pool/export?format=json\|csv` | 导出（不含凭据） |

**`/api/v1/pool/kinds` 现在每个后端都带 `operations[]`**：能力位 → 具体方法+路径+说明。

## 5. 顺带修掉的一个测试装置缺陷（T-test-006）

跑全量矩阵时 stats 套件报 usage > relay_logs（12/13）。逐层查下来**不是产品或统计口径缺陷**，是那条断言自己的基线不对：

1. 它用 `/api/v1/log/history?limit=200&offset=0` 的单页当基线，而该表当天已有 1700+ 行 —— 本小时日志一超过 200 条，基线就被截断，于是 usage 看起来比日志多（套件其实已经算出了 page_full，但没用在断言里）。

2. 我先把基线改成翻页取全，比较变精确了，但**翻页期间新行插入会让 offset 漂移、跳过一行** —— 实证：同一小时「数据库 123 行 / 单页 limit=500 = 123 行 / 200×N 翻页 = 122 行」，request_id 也对得上。

3. 于是基线改为**优先一页取满（500）**，不够再翻页。

4. 剩下的 ±1 是**跨小时归属**：usage 的桶与 relay_logs 的小时归属取的时间戳不同，跨小时的那个请求会落进不同的小时桶。实证：hour 09 的差是 (−1, 0, −11, −7)、hour 10 的差是 (+1, 0, +11, +7)，token 签名 11/7 完全对上。

收尾把这条断言拆成两条守卫（比原来更强，而不是更松）：

- **当前小时**：允许一个小请求的跨小时归属余量（计数 1、token 20）——真正的重复计入会让整小时成倍偏高，这点余量挡不住；

- **已结算的上一小时**：**严格** usage ≤ relay_logs，不加任何余量。跑出来 116 vs 117（usage 更低，符合未落库的桶会丢）→ 通过，说明**没有重复计入**。

这条线的价值：原来那条断言在本小时日志超过一页后必然误报，而它恰恰是唯一守着「统计会不会翻倍」的检查。
