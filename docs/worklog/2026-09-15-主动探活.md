# 主动探活（R-probe-001 / T-probe-001）

> 目标：冷却中的成员不再干等冷却到期——后台任务主动发一次最小真实请求，确认恢复就立刻解除冷却，
> 让流量在冷却到期前回到该成员；同时给质量/延迟策略喂真实健康信号。
> 本轮同时把这条链路补进仓库内的 API 测试套件（第 16 套 `probe`）。

## 1. 口径（三条，实现与测试都按它们判）

1. **探的是成员绑定的真实模型，不是渠道的 `/v1/models`。** 凭据有效但模型仍在上游报错的成员，
   只探模型列表会被误判成"已恢复"，而冷却后的第一次真实请求照样失败——这是本需求最容易做错的地方。
2. **默认关闭。** 每次探测都是一次真实计费请求，是否花这笔钱由用户显式决定（`route_probe_enabled`，默认 `false`）。
3. **探测失败不改冷却、不重试。** 冷却是"成员不可用"的既有证据，探测失败只是再次确认：只记日志，
   下一轮再探；只有探测成功才解除冷却，并作为一次成功样本进入质量/延迟指标（`recordMemberOutcome`）。

另外三条实现口径：

- **只探仍在冷却期内的成员**：冷却已到期的成员本来就会被下一个真实请求当作探测请求放行
  （`route.go` 的 `ProbeItemID` 语义），后台不必跟它重复。
- **只探可用成员**：渠道/凭据被停用的成员转发不了，探它只是白花钱（`item.Available` 为假即跳过）。
- **探测走生产同一套出站链路**：`buildOutbound` 选协议（优先 OpenAI Chat，授权不支持时按既有兜底顺序）
  + `applyChannelConfig` 套渠道参数覆盖与自定义 Header + `resolveUpstreamClient` 按渠道代理取客户端，
  否则会出现"探测通过而真实请求失败"的假恢复。请求体 `max_tokens=1`，超时 20s，单轮最多 10 个成员。

## 3. 单测（`internal/relay/probe_test.go`，6/6 通过）

用隔离内存库 + `httptest` 桩上游（不使用内存构造的分组——那正是"探测走生产路径"的验收点）：

1. `TestProbeCoolingMemberRecoversAndClearsCooldown`：冷却中成员被探一次 → 上游 200 → 冷却解除；
   断言探测打的是 `/v1/chat/completions`、模型是成员绑定的 `probe-model`、请求体 `max_tokens=1`。
2. `TestProbeFailureKeepsCooldown`：上游 500 → 冷却截止时间一字不变，且只尝试 1 次（不重试）。
3. `TestProbeSkipsExpiredCooldownAndManualMode`：冷却已到期不探（交给真实请求）、手动模式不探。
4. `TestProbeUsesGrantSupportedProtocol`：授权只有 Anthropic Message 时探 `/v1/messages`。
5. `TestProbeErrorBodyOn200IsNotRecovery`：200 + `{"error":...}` 不算恢复。
6. `TestProbeSkipsUnavailableMember`：凭据停用（成员不可用）不探。

## 6. 踩坑

- **`op.SettingSetString` 要求设置键已存在**（缓存里没有直接报 `setting not found`）：新增设置必须同时加进
  `model.DefaultSettings()`，它会在启动时补齐缺失行——否则接口能过校验却写不进去。
- **`GroupList()` 不过滤不可用成员**（`GroupGetByName` 才过滤），故探活侧必须自己按 `item.Available` 跳过，
  否则会对停用渠道白花探测费。
- **`model.GroupItem` 的展示字段是 `gorm:"-"`**（由 `groupSnapshot` 回填）：单测落库时只能写
  `GroupID/ChannelGrantID/Priority`，`ModelName` 等由缓存回填，不能手写。
- 探活开关是**全局**的：套件里临时打开时，其它分组处于冷却中的成员也会被探到。故套件把它当作有窗口的资源，
  正例跑完立刻复原（`finally`），并写进 README 的套件说明。

  得在 `RouteState` 或 stats 上加字段，属后续项。
