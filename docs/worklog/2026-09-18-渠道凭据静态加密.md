# 渠道凭据静态加密（R-sec-001 余项）

用户对十项清单的第 ⑥ 项回复是「要」。这一项的最后一块拼图是 `channel_keys.key` 一直是**明文**落库：
数据库文件、`数据备份*.json`、或者任何一个能读到数据文件的人，都能直接拿走全部上游凭据。
官方账号与号池规格早已是 AES-256-GCM 密文（`op/official_account.go`、`op/pool_adapter.go`），
只剩渠道凭据这一条明文路径。

## 1. 口径：库内密文、进程内明文

收口位置选在**缓存层**，而不是在转发链路里逐个改造：

| 方向 | 收口点 | 说明 |
| --- | --- | --- |
| 库 → 内存（解密） | `channelRefreshCache`、`reloadChannelChildren`、`officialPoolKeys` | 全部走 `secret.DecryptRows`；解不开就整次刷新失败，绝不把密文放进缓存 |
| 内存 → 库（加密） | `syncChannelKeys`（新建 / 更新）、官方账号物化（新建 / 更新） | 全部走 `sealChannelKeyForStore` |
| 存量行 | 迁移 015 + 启动时补加密 | 幂等：只处理没有前缀的行 |

好处是**转发链路一行都没改**：选路、探测、配额扫描、号池刷新都从 `channelKeyCache` 取凭据，
它们看到的一直是明文；也就不存在"某个分支忘了解密，于是把密文当 API key 发给上游"这种最难查的故障。

密文形状：`enc:v1:` + base64(nonce‖ciphertext)，AAD 固定 `credential:channel-key`
（官方账号与号池规格的密文拿到这里解不开，反之亦然）。三条约定的理由：

1. **带前缀才是密文**：没有前缀的值按明文处理 —— 存量行不需要一次性迁移就能继续用，
   迁移只改存储形态，不是让旧数据失效。
2. **解密失败一律报错**：绝不把密文当明文返回。密文当 API key 发出去，得到的是上游 401，
   而不是一条能定位问题的日志。
3. **写入侧宽松、读取侧严格**：真的没有可用密钥时（连密钥文件都写不出来），写入退回明文并**只告警一次**
   —— 把"加密能力缺失"升级成"功能不可用"才是误伤；读取侧仍然报错，因为那时数据确实解不开。

## 2. 密钥从哪来（两个来源都支持，环境变量优先）

第 ⑥ 项唯一悬而未决的是"密钥来源"，本轮按用户「我全都要」的一贯口径**两个都做**：

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1 | 环境变量 `OCTOPUS_OFFICIAL_KEY` | 与官方账号**同一把**密钥，避免出现两套密钥体系；已配置的安装升级即生效 |
| 2 | 数据目录下的 `credential.key` | 与 `database.path` 同目录，首次使用时自动生成（32 字节随机数的 base64），Unix 权限 0600；启动日志会打印路径 |

密钥缺失时**不会**静默生成到别处、也不会把服务卡死：启动日志明确写出"当前是明文"。

**两个必须知道的后果**（写在启动日志与本文档，不靠人记）：

- `credential.key` 丢失 = 已加密的凭据解不开（面板可以重新填写，没有别的办法找回）——
  请与数据备份一起保存。Windows 上权限由文件系统 ACL 决定，Go 写文件不会落地 0600。
- **降级要小心**：加密后的行只有新版本能读。老版本二进制会把密文当 API key 发给上游（表现为 401），
  所以回退前要先把凭据改回明文（面板重新填写即可）。

## 3. 过程中撞到的三个坑

1. **比较必须在明文上做**：`syncChannelKeys` 原来直接比 `current.Key != requestedKey.Key`。
   库内是密文、提交的是明文，这个比较**永远为真** —— 每次保存都会重新加密一次（密文变化），
   既白写一次库，也让"到底改没改"再也判断不出来。已改为先把既有行解密再比。
   单测 `TestSyncChannelKeysDoesNotRewriteUnchangedKey` 钉住这一点。
2. **迁移不能依赖 op**：`internal/db/migrate` 依赖 `internal/db`，而 op 也依赖它 ——
   迁移里 `import op` 直接成环（`import cycle not allowed`）。解法是把与业务无关的加解密原语
   下沉到新的 `internal/secret` 包（只依赖 conf/model/log/gorm），op 与 migrate 共用同一份实现。
   这条是"同名能力要放在能被两边共同依赖的层"的典型例子。
3. **加密必须是幂等的**：`Seal` 对已带前缀的值原样返回，否则每次保存都会二次加密、密文越滚越长；
   空串保持空串（空凭据的模型层语义不能被加密改掉）。

## 4. 判据

**单测**（`go test ./internal/secret/ ./internal/op/ ./internal/db/migrate/`）：

| 用例 | 覆盖 |
| --- | --- |
| `TestSealOpenRoundTrip` | 往返一致、密文含前缀且不含明文、两次加密结果不同（随机 nonce） |
| `TestSealAndOpenEdgeValues` | 空串原样返回、对已加密值 Seal 幂等 |
| `TestOpenTreatsUnprefixedValueAsPlaintext` | 存量明文行继续可用 |
| `TestOpenFailsOnTamperAndWrongKey` | 篡改密文 / 换一把密钥都必须报错 |
| `TestKeyFileFallbackCreatesKeyAndReloads` | 无环境变量时生成密钥文件、非 Windows 断言 0600、模拟重启后仍能解密 |
| `TestSealLegacyChannelKeysIsIdempotent` | 只加密明文行、空串与已加密行不动、跑两次第二次为 0 |
| `TestSyncChannelKeysStoresCiphertext` / `DoesNotRewriteUnchangedKey` / `ReEncryptsChangedKey` | op 侧：落库密文、重复提交不重写、换值真的换 |
| `TestMigrate15SealsPlaintextChannelKeys` / `SkipsWhenNoCipherKey` / `NoTableIsNoop` | 迁移三条分支：加密、无密钥时跳过、没有表时不报错 |

**活体** `scripts/api-tests/run_credential_encryption_test.py`（新套件，矩阵第 31 套）**6/6**：

| 用例 | 读数 |
| --- | --- |
| E0 装置就位 | 渠道 288（凭据 cipherkey）+ 授权 + 分组 |
| E1 落库即密文 | 库内长度 71、前缀 `enc:v1:L`、含明文 False |
| E2 端到端解密 | HTTP 200，上游 Authorization 指纹 `bearer:7d8838592455` == 明文凭据指纹 |
| E3 判据自检 | 另一把凭据的指纹 `bearer:cce7561a58b8` 未出现（否则 E2 可能恒真） |
| E4 管理面口径不变 | 渠道详情仍回明文（面板可编辑，admin-only） |
| E5 全库凭据无明文 | 共 49 行，**明文 0 行**（含重启时迁移处理的存量行） |

两条关键说明：

- **E2 是本套件的核心**，不是 E1：mock 不校验密钥，收到密文也会回 200。
  只有直接看上游实际收到的 Authorization 指纹（与 `mock_upstream._redact` 同款算法，只落指纹不落原文），
  才能证明"库里是密文、发出去的是明文"。
- **E5 是迁移的实证**：重启前这些行全是明文，重启后 49/49 行都是密文，0 行明文。

另外，全部 31 个套件里所有渠道夹具都是经 API 新建的（新建即密文）、所有转发都依赖缓存里的明文凭据，
所以**矩阵本身就是一个大范围的解密回归**：解密一旦坏了，绝大多数套件会因为上游 401 而变红。

## 5. 边界与未覆盖

- **存量明文行的读取路径只有单测覆盖**：活体环境里迁移会在启动时把它们加密，因此活体上没有明文行可测。
  这不是没测，而是这条路径在活体上被迁移"提前消灭"了。
- **转发口不提供凭据**：E4 断言的是**管理面**（`middleware.Auth()`）仍可读到明文供面板编辑；
  这是既有口径（admin-only），本次不改。转发口历来不回显凭据（见 T-sec-001 的跳转令牌审计）。
- **备份转储里现在是密文**：`DBDump` 导出的 `channel_keys.key` 已是密文，但它**没有额外脱敏**——
  备份的可恢复性优先于"导出即安全"。拿不到密钥文件的人打不开这些值，这是本轮的收益；
  但"备份里根本不该出现凭据"是另一件事（R-sec-001 原文里的"导出默认脱敏"），未在本轮做。
- **不是磁盘加密的替代**：静态加密保护的是"数据文件/备份被拿走"，不保护运行中被攻破的进程
  （密钥就在同一台机器上）。
