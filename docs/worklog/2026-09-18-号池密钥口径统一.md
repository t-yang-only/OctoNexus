# 号池密钥口径统一（T-pool-key-001）

日期：2026-09-18
触发：用户在本地部署（无 `OCTOPUS_OFFICIAL_KEY` 环境变量）里点号池，报
「授权失败：official credential cipher key not configured (set OCTOPUS_OFFICIAL_KEY)」，
要求"把这些号池项目修好先"。

## 根因：同一台机器两套密钥口径

| 用途 | 改成之前怎么取密钥 | 结果 |
| --- | --- | --- |
| 渠道凭据 `channel_keys.key` | `internal/secret`：环境变量 → 数据目录 `credential.key`（首次自动生成） | 正常加密，库内密文 |
| 官方账号 AccessCipher/RefreshCipher | `op.officialCipherKey()` **只读环境变量**，没设就报错 | 一用就 503「密钥未配置」 |
| 号池声明式适配器 spec | 复用 `officialGCM()`，同上 | 一注册就报「pool declarative cipher key not configured」 |

于是出现最反直觉的现象：**同一实例里渠道凭据加密是好的，号池整条功能却不可用**，
而且报错把人指向一个环境变量（在 Windows 上尤其难配置），而不是指向真实故障面。

## 改法

1. `internal/secret` 新增导出 `CipherKey()`，作为**唯一**密钥解析口径（环境变量优先，回落密钥文件、
   首次自动生成）——保留原有 AAD 隔离（`credential:channel-key` / 服务商名 / `pool:declarative`），
   换用途的密文照旧解不开。
2. `op.officialCipherKey()` 改为经 `secret.CipherKey()`，并把底层原因包进 `ErrOfficialKeyMissing`
   （handler 的 503 映射与既有调用方按键值语义不变）。
3. 号池同步（`OfficialPoolSync`）显式实现「解不开就记原因、一行不改」：新增 `officialPoolRawKeys`
   （只取行不解密），解密失败时**记一条 Note 并返回**，而不是整轮失败。
   这条降级以前"看着是好的"，只是因为渠道凭据那条路径缓存了轮换前的旧密钥；口径统一后必须显式写出来。
4. handler 文案从"设置 OCTOPUS_OFFICIAL_KEY"改成"设置环境变量，或让数据目录可写以便生成 credential.key"。

## 判据与证据

- 新增 `internal/op/official_cipher_source_test.go` 3 例：
  - 不设环境变量 → 官方账号凭据可加可解，且 `credential.key` 真的落盘；
  - 不设环境变量 → 号池 spec 可加可解，且**官方账号密文不能当号池规格解开**（AAD 隔离反向自检）；
  - 设了环境变量 → 仍优先用环境变量（存量安装升级后能解开自己的密文），换回文件密钥必须解不开。
- **变异检查**：把 `officialCipherKey()` 改回"只读环境变量"→ 前两例立刻变红，
  报错文本正是用户看到的那一句；恢复后全绿。
- 既有用例按新契约修正（不是放宽）：
  - `TestOfficialAccountAuthorizeRejectsWithoutKey` 改用"数据目录被文件占住"制造**真**的密钥不可得
    （原来它把"没设环境变量"当不可得，等于把缺陷固化成契约）；
  - 池同步轮换用例补 `secret.ResetKey()`（密钥是进程内缓存一次，换环境变量等价于重启），
    并把"既有凭据没被改"的判据落在**库内那一行（密文）**上，另加"切回原密钥仍可读"的反向自检。
- 活体（本地实例 33000，**刻意不设** `OCTOPUS_OFFICIAL_KEY`）：
  - `POST /api/v1/account/official/authorize` → 不再报密钥错，而是报出真正的下一步前提
    `official OAuth client id not configured for openai`（HTTP 400 而非 503）；
  - 号池声明式适配器：白名单为空时 403 fail-closed；写入白名单后注册 200，
    `pool_declarative_adapters` 设置项落库 **352 字符密文、不含明文 secret**；列表/删除均正常；
  - 号池只读面 `kinds/entries/summary/stats/adapters/templates` 全 200；channel 口径 46 条凭据在册。
- 回归矩阵：`run_all.py --only cipher,pool,poolapi,pooldecl,backup` → 5 套全过（6/6、14/14、45/45、9/9、22/22）；
  单测 16 包全绿；`go build ./...` / `go vet ./...` 干净。

## 顺带查清的事实（不是缺陷）

- 池里 46 条渠道凭据只有 16 条"健康"：判据是 `stationEntryHealthy`＝历史成功数不少于失败数，
  数据来自线上导出的累计统计，属如实反映。
- 官方账号池目前 0 条：它的授权需要**各服务商自己的 OAuth client id**
  （`OCTOPUS_OFFICIAL_CLIENT_ID_OPENAI/GEMINI/CLAUDE` + redirect URI）。
  项目自己的收口记录（`docs/worklog/2026-09-14-T-acct-001收口验收229.md`）已写明这属"部署环境提供"，
  不是代码缺陷；未提供时现在的报错把人指向缺什么，而不是指向密钥。
