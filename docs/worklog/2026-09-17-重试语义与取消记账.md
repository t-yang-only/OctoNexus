### 修 A：客户端取消不再计入成员失败

- 证据：探针客户端自己的 60s 上限先到 → 客户端断开；`handler.go` 首字节**已提交**的流式分支按 `err != nil` 一律 `RequestFailed = 1`，而提交前的分支早已把"客户端取消"排除在外（同一条语义在两处口径不一致）。
- 后果：354 次探针里 123 次超时取消把它们打过的成员"判死"，最终降级 128 项；`Forestapi/deepseek-v4.1-flash` 累计 158 成功 0 失败也被降级。
- 修法：提交后记账与提交前统一 —— `ctx.Err() != nil`（客户端离开）不计成员失败，服务端自己的超时/看门狗照旧计失败。
- 实证：`run_stream_idle_test.py` I7「客户端首字节后放弃不计成员失败」→ 成员失败计数 `1→1`。

### 修 B：单请求尝试上限 + 退避（杀掉无限重试）

- 上游 issue #388（报在 v0.13.4，正是本项目基线）：手动模式无限重试。代码事实：`recordRouteFailure` 对手动模式**直接 return false**（永不冷却），`pickGroupItem` 手动分支又无条件返回 `ActiveItemID` ⇒ 每 `member_retry_interval_seconds` 打一次同一个成员，永不停止。
- 上游 issue #338 的同款症状：客户端超时后服务端继续空转。
- 用户的 `relay_config`：`member_max_attempts=2`、`cooldown=600s` ⇒ 全成员冷却后循环只能按 1s 间隔反复选路，1 秒一次的稳定流量正是中转站判定"攻击行为"并封 IP 的形态。
- 修法（`internal/relay/retry.go`）：`attemptCap = clamp(成员数 × 单成员尝试次数 × 2, 6, 64)`；同一成员连续失败的等待退避 `1→2→4→8→16→30s`（从配置的重试间隔起翻倍，封顶 30s）；到点用 `failRequest` 按客户端协议回 502，把上游最后的错误原文带给客户端。
- 实证：R1 `HTTP 502 / 5.0s / 上游 6 次（上限 6）`；R5 手动模式 `HTTP 502 / 31.0s / 上游 6 次`（修复前是无限）。

### 修 C：确定性错误不再重试（上游 #375）

- `400/405/406/413/414/415/422/501` → "请求本身非法"：换任何成员都会被同样拒绝，因此**不计成员失败**（不是成员的锅，计了会拉低成员质量）、**不打冷却**（否则一个坏请求能把健康成员冻住），只把该成员记入本请求的拒绝集合，换下一个；全部成员都拒绝时立刻以明确错误结束（不空转）。
- `401/402/403/404/407` → "成员自身问题"：记 1 次失败并**立即按尝试次数用尽**冷却换人，不再白耗剩余的尝试次数与退避时间。
- 其余（408/409/429/5xx/网络/超时）保持可恢复语义。
- 实证：R2 `502 / 1 次尝试 / 成员失败 0→0`；R3 `[mock-reject400, mock-good] → 200 / 0→0`；R4 `[mock-reject401, mock-good] → 200 / 0→1`。
