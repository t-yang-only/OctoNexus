# 修掉官方版本的已知问题：入站请求体 64 MiB 上限（T-bodylimit-001）

> 日期：2026-09-18
> 分支：`master`（工作区改动，未提交）
> 用户原话：「解决目前官方版本的已知问题 **failed to read request body: request body too large**」
> 现场：Codex 执行 remote compact 时，`api.yangonly.com`（Caddy → 本机 8080 → 本项目二进制）返回
> `{"error":{"message":"failed to read request body: request body too large","type":"invalid_request_error"}}`

## 1. 根因：不是上游，是我们自己的网关（依赖库写死的 64 MiB）

顺着报错文本找唯一来源：

```
github.com/looplj/axonhub/llm@v0.0.0-20260909170523-3786f2c5c8de/httpclient/utils.go
    var maxRequestBodySize = 64 * 1024 * 1024        // 包内私有常量：外部既读不到也改不了
    var ErrRequestBodyTooLarge = errors.New("request body too large")
    func ReadHTTPRequest(rawReq *http.Request) (*Request, error) {
        body, err := readLimited(rawReq.Body, maxRequestBodySize)
        if err != nil { return nil, fmt.Errorf("failed to read request body: %w", err) }
```

本项目只有一个调用点：`internal/relay/handler.go` 的转发入口（读完整正文 → 解析 model → 建请求状态 → 每轮改写）。
`rejectRequest` 把所有读取失败统一翻成 **400 + invalid_request_error** —— 于是报文长得像上游错误，
而实际上请求在**鉴权之后、选路之前**就被自家网关丢掉了（这也是用户排查时被绕住的原因）。

**本地实测边界（改造前，决定性红）**：

| 请求体 | 结果 |
| --- | --- |
| 8 MiB | 400 `model not found`（已过读取阶段，走到后面的业务判断） |
| 63 MiB | 400 `model not found`（同上） |
| **65 MiB** | 400 **`failed to read request body: request body too large`** |
| 70 MiB | 同 65 MiB |

即上限正好卡在 64 MiB，与依赖里的常量完全对应。

## 2. 改法

1. **自己读入站正文**：新增 `internal/relay/inbound_body.go`
   - `readInboundRequest` 复刻依赖库的字段填充（Method/URL/Path/Query/Headers/Auth/RequestID/ClientIP/RawRequest）
     与内容编码解码（identity/gzip/x-gzip/deflate/zstd，解码后同样删 `Content-Encoding`/`Content-Length`）；
   - 上限改由**设置项**决定；超限仍返回同一个哨兵错误 `httpclient.ErrRequestBodyTooLarge`，
     保证"是不是超限"只有一种判定方式；
   - `inboundBodyLimitOnlyOneSource`：上限只认设置项（不另加环境变量）——两处来源迟早出现
     "面板显示 256 MiB、实际按 64 MiB 拦"的排查陷阱。
2. **新增设置项** `relay_max_request_body_bytes`（默认 `268435456` = 256 MiB，`0` = 不限制），
   走既有约定三处：常量 + `DefaultSettings` + `Validate`（负数直接拒绝，不静默夹紧）。
   内存代价写进了常量注释与面板提示：正文整份驻留内存、每轮改写再复制一份，上限越大单请求峰值内存越高。
3. **超限报错可自救**：`rejectRequestTooLarge` 回 **413**（不再混在笼统的 400 里），文案点名设置项与当前上限，
   并保留 `request body too large` 原话（既有抓取/告警关键词继续命中），同时 `log.Warnf` 留痕
   （这类拒绝发生在请求状态登记之前，只能靠日志回溯）。
4. `go.mod`：`github.com/klauspost/compress` 从 indirect 提升为直接依赖（zstd 解码分支现在由我们直接引用）。

## 3. 判据

**单测**（`internal/relay/inbound_body_test.go`，全部绿）：

| 用例 | 挡住的偏差 |
| --- | --- |
| `TestReadInboundRequestMatchesDependency` | 同一请求分别过我们与依赖库的实现，**逐字段比对**（方法/URL/路径/查询串/客户端 IP/RequestID/正文/头部改写）——"我抄漏了"会立刻变红 |
| `TestInboundRequestRejectsUnsupportedEncodingSameWay` | 不认识的编码必须和依赖库一样报错（不能静默当明文收下） |
| `TestInboundBodyLimitIsConfigurableAndExceedsOldCap` | **回归判据**：65 MiB（> 旧上限）必须被接受；上限调成 1 MiB 后同一份正文必须被拒且是哨兵错误；上限 0 必须放行 |
| `TestLimitAppliesToDecompressedBody` | 压缩正文按**解压后**大小判（否则 gzip 一个说谎包就能绕过上限） |
| `TestInboundClientIPParsing` | XFF 第一跳 / X-Real-IP / RemoteAddr 去端口的取值顺序与依赖库一致 |
| `TestReadInboundRequestLargeRandomBody` | 4 MiB 随机正文读回一致（真实内存布局路径） |

**活体**（`scripts/api-tests/run_bodylimit_test.py`，已登记进 `run_all.py`，**5/5**）：

```
B0 边界: 63 MiB 与 65 MiB 都不再被读取阶段拒（都在模型不存在这一步才失败）
B1 端到端: 65 MiB 正文经真实分组转发到本地 mock → HTTP 200 0.7s（修复前在这里就是 400）
B2 可调:   上限调 1 MiB → 2 MiB 正文被拒 413 且文案点名 relay_max_request_body_bytes
B3 关闸:   上限设 0 → 同一份 2 MiB 正文放行（是"可调"，不是把闸门焊死）
B4 校验:   负数上限被拒（400，越界不静默夹紧）
```

**面板**：新增设置项与三语文案进产物 —— `run_panel_asset_test.py` 新增 **P17**（17/17 全绿）。

## 4. 遗留

- 用户线上的 `api.yangonly.com` 跑的是**上游原版二进制**（2026-09-10 构建），本修复需要换成我们的发布件才生效；
  上线是用户侧动作（人工替换二进制，见 `docs/deploy/`）。
- 若上游后续把上限改成可配，我们可以退回直接用依赖库的实现（届时删掉本文件这份复刻即可）；
  现在之所以复刻，是因为它是**包内私有常量**，外部没有任何合法途径改它。
