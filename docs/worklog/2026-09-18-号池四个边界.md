# 号池四个边界（声明式适配器 · 只读通道 · sync 方向 · 首批模板）

用户对号池扩展性设计里「待拍板的四个取舍」的回复是**「我全都要」**。本轮把四条都落成代码里的硬约束，
而不是文档里的承诺——因为这四条的本质都是**边界**，写在文档里没人拦得住，写在代码里才拦得住。

## 1. 边界①：运行时声明式适配器（开放，但默认谁都接不进来）

`internal/pool/declarative.go`：一份 JSON 描述一个外部反代工具包，不改代码、不重编译就能进统一视图。
最危险的一点是"让 octopus 按 JSON 去请求任意 URL"，所以五条约束全部实现成硬检查：

| 约束 | 实现 | 为什么这么定 |
| --- | --- | --- |
| 域名白名单 | 设置项 `pool_declarative_hosts`，**为空即一律拒绝**（fail closed）；spec 不能自带白名单 | 默认敞着的入口迟早会被接上不该接的东西；宁可让用户显式列域名 |
| 只读能力位 | 只允许 `list`/`get`；`sync`/`toggle`/`provision`/`revoke`/`refresh`/`probe` 一律拒绝注册 | 写操作要么改外部系统、要么要按条目拼 URL，超出"只读清单"的范围；要写就写内置适配器（过代码评审） |
| 不跟 3xx 跳转 | `CheckRedirect` 直接拒绝 | 否则白名单可以被一个 302 绕过 |
| 有界请求 | 超时 10s、响应体上限 1MiB | 一个坏后端不该把号池页拖死 |
| 命名隔离 | kind 必须以 `custom-` 开头；内置 kind 不可覆盖、不可移除 | 一份 JSON 不能顶掉官方账号/渠道凭据适配器 |

认证三型：`none` / `bearer`（静态令牌）/ `login`（登录换 token，401 重登一次，令牌只在内存）。
凭据只进加密存储与内存：整份 spec 用 AES-256-GCM 落库（AAD 固定 `pool:declarative`，与官方账号同一密钥
`OCTOPUS_OFFICIAL_KEY`）。**缺密钥时拒绝注册，而不是明文落库**——这条是被测试逼出来的：第一轮活体 D2 报
400 时，错误信息直接指向"密钥未配置"，而不是把凭据悄悄写进库里。

## 2. 边界②：外部工具包的只读 APIKey 通道

`internal/server/handlers/pool_apikey.go`：转发口 `/v1/pool/{kinds,entries,stats,summary}`，
走 `middleware.APIKeyAuth`，与管理面同源同口径。三条硬边界：

- **只读**：写动作（probe/refresh/toggle/sync、注册适配器）在这条通道上**根本不存在**（实测 404），
  想动号池只能走管理面（那里是 `middleware.Auth()`）；
- **凭据永不回显**：复用统一视图，`Entry` 只带元数据；
- **不额外放大权限**：能调模型的 Key 就能读号池规模与状态，读不到任何凭据、也改不了任何东西。

为什么值得单独开一条：外部工具包（面板、巡检脚本、账号 hub）大多已经拿着一个转发用的 APIKey，
让它们为此再存一套管理员口令，等于把管理面凭据散到更多地方。

## 3. 边界③：sync 抽象（结论是"已经有了，本轮把它写成契约"）

核查后确认 `internal/pool/ops.go` 的 `Sync` 就是这条抽象：**能力位门禁 + `Syncer` 类型断言**分发，
声明式适配器因为只允许 `list`/`get`，结构上不可能声明 `sync`。因此本轮不新增抽象，而是把方向写死：

- 方向固定为**单向**：号池条目 → 渠道凭据，永远不反向写外部系统；
- 声明式（外部 JSON）永远拿不到 `sync`：想同步就必须是内置适配器；
- 声明的能力位与实际实现不一致时（声明了 sync 却没实现 `Syncer`）报 `ErrUnsupported`，不是静默跳过。

## 4. 边界④：首批要接哪些工具包（只读运维信息优先）

`GET /api/v1/pool/adapters/templates` 给出三个形态的只读模板：`custom-new-api` / `custom-one-api` /
`custom-sub2api`（登录端点、列表路径、字段映射按各形态常见形状给，模板里不含任何凭据）。
与选型报告（R-pool-003 全文）第 4 节的判断一致：**先接余额/可用性这类只读信息，不接账号托管，
也不接自动签到这种"以你的身份对外动作"的能力**。

## 5. 判据

**单测** `internal/pool/declarative_test.go` 9 例：白名单空/后缀命中/绝对 URL 越界、写能力位全部拒绝、
形状校验六种、运行时注册表可替换可移除、内置 kind 不可覆盖不可移除、字段映射与认证头、3xx 不跟跳、未知能力位。

**活体** `scripts/api-tests/run_pool_declarative_test.py`（新套件，矩阵第 30 套）**9/9**：

| 用例 | 读数 |
| --- | --- |
| D1 未配白名单 → 403 | `未配置域名白名单（设置项 pool_declarative_hosts），声明式适配器一律拒绝注册` |
| D2 配上白名单后同一条 spec 注册成功 | 200（与 D1 是差分对照，只差白名单这一件事） |
| D3 自描述只声明只读能力位 | `caps=['get','list']`，`builtin=false` |
| D4 声明 `sync` → 400 | `声明式适配器只支持只读能力（list/get），"sync" 需要写内置适配器` |
| D5 白名单外的域名 → 403 | `base_url 的主机 "example.com" 不在白名单 [127.0.0.1] 内` |
| D6 统一视图真的读到了外部清单 | 读的是 mock 的 `/v1/models`，条目 8 条 |
| D7 移除后可再注册 | 删除 200 → 再查 400 `unknown pool kind` → 再注册 200 |
| D8 只读 APIKey 通道 | 读 200 / 匿名 401 / 写 404 |
| D9 凭据原文不出现在任何响应里 | 注册响应、适配器列表、自描述三处都无泄漏 |

**变异检查**（`%TEMP%\octopus-dstest\mutation_pooldecl*.py`）：

| 变异 | 结果 |
| --- | --- |
| MD2 放开写能力位 | D4 如期变红 |
| MD3 `hostAllowed` 恒真 | D5 如期变红 |
| MD1c 同时破坏两层 fail-closed 防线 | D1 如期变红 |

**MD1/MD1b 两次单点变异不变红，原因是查明的、不是掩盖的**：fail-closed 是**双重**保障——
`ValidateDeclarativeSpec` 的显式分支，加上 `hostAllowed` 对空名单本就匹配不上任何主机。
破坏任意一层，行为不变（只是错误文案不同）。这是"防线有两层"的正常形态；要让"默认放行"这个真实缺陷
可被测出，必须同时破坏两层（MD1c 即是）。这条按既有纪律处理：**变异不变红时先判断是装置还是守卫的问题**，
判断结论要写下来。

## 6. 未覆盖 / 边界

- 未做：声明式适配器的 `login` 流程在活体套件里没有覆盖（单测覆盖了 bearer 与形状校验）——
  `login` 需要目标站点返回固定形状，mock 上游没有相应端点；要覆盖得先给 mock 加一个登录端点。
- 未做：白名单收紧后**已注册**适配器的行为是"下一轮刷新失败并进 warnings"，注册表里仍保留它。
  刻意如此：静默摘掉别人的适配器比让它报错更难查。
- 边界：`items_path`/`fields` 是 gjson 路径，不做 JSONPath 全集；字段类型目前统一按字符串映射，
  数字/时间按需解析（`enabled`/`healthy`/`expires_at` 已做别名匹配）。
