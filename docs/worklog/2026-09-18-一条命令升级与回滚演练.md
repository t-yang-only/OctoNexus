# 一条命令升级与回滚（T-deploy-005）

**起点**：v0.14.0 的发布件、运行手册、回滚口径都已就绪，但"上线"仍是一串手工步骤
（备份 → 停服 → 换二进制 → 启动 → 检查 → 出问题再回滚），任何一步漏了都是线上事故。
本轮把它压成**两条命令**（升级 / 回滚），并在 WSL 里搭出"旧版在跑 + 明文凭据"的真实现场
演练到底。

## 交付物

| 文件 | 位置 | 作用 |
| --- | --- | --- |
| `upgrade-on-server.sh` | 仓库 `docs/deploy/` + 发布件目录 | 服务器侧一条命令升级/回滚（干跑、备份、原子换件、健康检查、日志要点、随件自检、回滚命令） |
| `verify.sh`（改） | 仓库 `docs/deploy/` + 发布件目录 | 新增第 5 个参数「安装目录」：在发布件目录里调它时，库内形态/日志检查要去看**安装目录** |
| 运行手册 §2.5 | `docs/deploy/上线-v0.14.0-Ubuntu单二进制.md` | 一条命令升级的参数表与三条不可省的关键动作 |
| RELEASE.md | 发布件目录 | 文件清单补 `verify.sh`/`upgrade-on-server.sh`，提交与校验值只指向 `build-record.txt` |

## 脚本口径（每一步都对应一次真实踩坑）

1. **备份整个 `data/` 目录**（含 `credential.key`），不是只备份 `data.db`：只备份库会丢掉解密能力。
2. **换二进制是「装 `octopus.new` → 校验版本 → 原子 `mv` 落位」**：任一步失败，线上那份一个字节没动。
3. **回滚 = 二进制回滚 + `data/` 整目录替换**：只换二进制会让旧版读到 `enc:v1:` 后全线 401；
   只覆盖 `data.db` 也不行 —— SQLite 的 `data.db-wal` 里可能留着升级后的密文，回放后密文又回来。
   回滚前那份 `data` 会整目录挪进备份目录留档（不删数据）。
4. **健康检查**：管理面必须在 45 秒内就监听且拒匿名（401/200），否则按 `--rollback-on-fail` 自动回滚。
5. **dry-run 不需要 root**（只读预览谁都能跑），落盘动作才要 root。

## 三条装置教训（都是脚本缺陷先被演练抓出来的）

1. **进程识别不能按命令行字符串匹配**：手工部署的命令行是相对的（`cd /opt/octonexus && ./octopus start`），
   用 `pkill -f "$DIR/octopus start"` 一个都匹配不到 → 脚本以为"已经停了"，新实例和旧实例抢端口挂死
   （第一版演练卡到超时就是这么来的）。改为按 `/proc/<pid>/exe` 反查，并接受 `(deleted)` 形态。
2. **版本解析必须锚定行首**：`awk '/Version/{print $2}'` 会先命中 `Go Version: go1.27.0 linux/amd64`
   这一行，于是"现版本/新版本"显示成 Go 版本（演练实测）。改为 `/^Version:/{print $2; exit}`，
   并抽成 `version_of()` 一处实现。
3. **自检脚本要显式接收安装目录与转发口**：在发布件目录里跑 `verify.sh` 时，库内形态与日志检查
   找的是发布件目录下的 `data/`、`logs/`（那里没有），于是两项常年被"跳过"；转发检查若把管理口
   当转发口用会得到 404。改法：第 5 个参数传安装目录（缺省 = 脚本自身目录），转发口独立传参。

> 附带的口径澄清：本轮演练里的"旧版"同为 v0.14.0（自带加密迁移），所以回滚后它启动时会把明文
> 再补加密一次 —— 看到密文属正常。判断回滚成功看两点：二进制 sha 回到旧值；备份里那份
> `data-*.tar.gz` 解出来的库内凭据是明文（脚本就是按这个还原的）。

## 边界

- 未在**真实服务器**上执行（需要用户的服务访问与授权）：脚本的一切行为都在 WSL Ubuntu 里演练，
  系统管理方式覆盖了 systemd（单元存在则 `systemctl stop/start`）与无 systemd 的进程模式。
- key 轮换（T-sec-001）与上线拍板（T-deploy-002）仍是用户侧动作。
- 脚本不动 `octopus` 之外的东西：不碰 Caddy/Nginx 配置，不改端口，不注册 systemd 单元。
