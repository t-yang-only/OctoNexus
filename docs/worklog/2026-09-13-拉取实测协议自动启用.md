# 2026-09-13 拉取模型时自动实测三协议并自动启用

- 仓库：https://github.com/bestruirui/octopus
- 本地：`d:\奇怪的软件\octopus`
- 分支：`master` 跟踪 `origin/master`
- 台账编号：`NM-CUR-011`（进行中 → 已完成，见 `agent_word/工作登记表.md`）
- 需求：模型点击从 key 拉取时自动测试支持的协议（chat / response / message），
  支持的自动启用对应协议位；了解每个模型对应的 API 和 key 分别支持什么

## 目标

1. `fetch-model` 拉取时对每个候选模型 × 三协议各发一次最小真实请求，实测该 key 在该模型上讲得通的协议
2. 实测通过的协议位自动并入表单授权矩阵，无需人工逐格勾选
3. 响应携带逐协议明细（ok/status/error），可了解每个模型在当前 key 下各协议的支持情况

## 前置调查

- 原实现：`fetchModel`（`internal/server/handlers/channel.go`）并发拉两侧 `/models`，
  OpenAI 侧出现即记 `ProtocolOpenAIResponse`，Anthropic 侧记 `ProtocolAnthropicMessage`，
  **Chat 永远不会被记上**（官方已标记弃用），且 `/models` 能列出 ≠ 该协议真能转发
- 转发链路：`relay.buildOutbound` 按 `grant.Protocols` 选协议，位不准会导致转发选错或无路可选
- 前端：`probe.ts` 把 `/models` 结论直接 OR 进 `grants`，`FormGrants.tsx` 按 `grantKey(model, key)` 渲染矩阵，
  授权矩阵本就是 模型 × key 两级，天然能展示"每个模型分别支持什么"

## 执行操作

### 后端

1. `internal/model/channel.go`：
   - `ChannelFetchModelRequest` 新增 `Probe bool`
   - 新增 `ChannelProtocolProbe{Protocol, OK, Status, Error}` 与 `ChannelFetchModel.Probes []ChannelProtocolProbe`
2. `internal/server/handlers/channel.go`：
   - `fetchModel` 保留原非实测路径（`!request.Probe` 时行为不变），实测分支走 `probeModels`
   - `probeModels`：模型间并发、同模型三协议并发，信号量限 4 防上游限频
   - `probeSingleModel`：候选位（并集）内逐协议发最小请求，chat=1 token chat/completions、
     response=max_output_tokens=1 responses、message=1 token messages，按位值定序保证明细稳定
   - `probeRequest`：单发 20s 超时；**2xx 且响应体可解 JSON 才算讲得通**（防部分网关对未知路径回 200 空体）；
     失败正文截 256 字节压平成一行摘要
   - `probeModelProtocols`：结论折算协议位掩码，实测位可能多于或少于 `/models` 侧推断
     （例如 chat 实测通过会补上、response 列在 /models 但实测 401 则剔除）

### 前端

3. `web/src/api/channel.ts`：`FetchModelRequest` 加 `probe?: boolean`；
   新增 `ProtocolProbe`、`FetchModel.probes` 类型，与后端 JSON 对齐
4. `web/src/components/modules/channel/probe.ts`：拉取一律带 `probe: true`；
   结果按 `grantKey(model, key)` OR 合并进 `grants`——只自动启用新证实的位，
   **不降级**人工已勾选的位（避免上游偶发失败撤销人工配置）；toast 改用 `modelRefreshProbed`
5. `web/src/locales/{en,zh_hans,zh_hant}.json`：新增 `modelRefreshProbed` 文案

### 验证

6. 新增 `scripts/check_protocol_probe.py` 24 项静态检查，`py` 运行全部通过：
   Probe 字段、三 sender 覆盖三协议、2xx+JSON 判定、20s 超时、并发限 4、
   前端 probe=true、OR 不降级、三语 i18n、4 个编辑文件括号/字符串/注释平衡
7. IDE 诊断：4 个编辑文件无 linter 错误

## 遗留问题

- 本机无 Go 工具链（T-env-001），`go build/vet/test` 未跑；合入前须在有 Go 1.26 的机器验证
- 实测会向上游发真实请求（每模型 × 每协议 1 token），量大渠道首次拉取会比纯 `/models` 慢：
  并发 4 × 20s 封顶下 60 模型约 2-3 分钟量级；后续可加"仅拉列表"开关让用户二选一
- 实测请求未带渠道 `param_override`：转发时会注入的参数与实测略有差异，极端情况实测通过但转发失败；
  暂接受（探测与转发共用地址/路径/代理/Header 已保证主干一致）
- `NM-CUR-008` 与 `NM-CUR-013` 仍是"进行中"：008 的目标被本任务覆盖完成，
  013 为另一会话的侦察任务，均未在本会话闭环，移交对应会话处理
- probes 明细目前只在响应里，前端未展开渲染（授权矩阵已表达结论）；若要在 UI 上看每协议 error 摘要，需再补一个展开视图
