## 1. 为什么需要容错解析

本地日志有**两个来源、两套字段形状**，卡片此前只认第一种：

| | 实时快照 `RelayLogOverview`（SSE） | 持久化历史 `RelayHistoryItem` |
|---|---|---|
| 用量 | 嵌套 `usage.prompt_tokens / completion_tokens / prompt_tokens_details.cached_tokens` | 扁平 `prompt_tokens / completion_tokens / cached_tokens` |
| 耗时 | `duration` 纳秒（进行中还要按共享时钟估） | `duration_ms` |
| 首字 | 靠 `first_byte_at - started_at` 两个时间戳相减 | `first_byte_ms`（未提交为 -1） |
| 总量 | `usage.total_tokens`（结束前可能给 0） | 无，需要输入 + 输出兜底 |

于是实时快照中途缺字段时（未选出成员、还没首字节、用量未回填）要靠散落各处的内联兜底，
而持久化历史行**根本渲染不了**。

## 2. 口径：回退链（每项只在"确实没有"时回退，绝不凭空造值）

新增 `web/src/components/modules/log/display.ts`，一次解析出卡片所需的全部字段：

| 字段 | 回退链 |
|------|--------|
| 身份 | `id` → `request_id` |
| 首字 | `first_byte_ms` → `first_byte_at - started_at` → **-1（未提交，界面显示占位）** |
| 耗时 | `duration_ms` → `duration`（纳秒）→ 进行中按 `now - started_at` 估算 |
| 输入量 | `usage.prompt_tokens` → `prompt_tokens` |
| 缓存量 | `usage.prompt_tokens_details.cached_tokens` → `cached_tokens` |
| 总量 | `usage.total_tokens` → 输入量 + 输出量 |
| 实际模型 | `target_model` → 客户端请求的 `model`（未选出成员时至少显示请求的模型名） |
| 费用 | 两个来源都直接给；缺失即 0（**不在前端凭价格表推算**） |
| 速率分母 | 已结束用最终耗时；进行中用 `now - started_at` |

另出 `formatJsonForCopy(text)`：能解析成 JSON 就按两空格缩进重排，否则原样去首尾空白；
解析失败不抛错（上游错误体常常是一行挤在一起的 JSON，复制下来很难读）。

## 6. 踩坑

- `relay_logs` 的列名是 **`completion_toks`**（GORM 由字段名 `CompletionToks` 派生），
  而 API/JSON 层是 `completion_tokens`（`json:"completion_tokens"`）。写脚本直接读库列时不能按 JSON 字段名取值，
  否则会静默拿到 0/undefined——本次校验脚本第一轮就栽在这里（是我脚本的问题，不是产品问题）。
