# 手动订阅独立表（R-acct-004 余项）

清单第 ⑦ 项问的是"手动订阅放哪"。这一项在之前的指导口径里已经给过建议（独立表，不塞进渠道凭据），
本轮把它落成实现：**上游没有余额接口的站点，由人录一条套餐余额与有效期，按与自动读数同一口径折算后并入总余额**。

## 1. 为什么是独立表，不是渠道凭据的一部分

| 维度 | 渠道凭据（channel_keys） | 手动订阅（manual_subscriptions） |
| --- | --- | --- |
| 内容 | 能连上游的秘密 | 我在哪买了套餐、还剩多少、什么时候到期 |
| 加密 | 必须静态加密（本轮已做） | 不含上游密钥，不需要加密面 |
| 生命周期 | 轮换、吊销、按凭据粒度停用 | 到期、续费、临时调整余额 |
| 备份含义 | 泄露一份等于泄露上游账号 | 泄露只是采购信息 |

把两者塞进一张表，会让"备份里哪些字段是敏感面""哪些值要跟着轮换"两件事同时失去边界。
所以：**新表 + 新接口 + 首页新区块**，渠道凭据一个字都没动。

## 2. 口径（与总余额同源，不引入第二套算法）

- 记录的余额单位是**点数**，与自动读到的渠道余额同一口径，因此可以直接相加；
  折算由后端 `balance_points_per_unit` 完成，也允许**按条覆盖**（`points_per_unit`）——
  不同站点的点数基数不同（new-api 是 500000 点 = 1 单位，别家不一样），不允许覆盖就没法录。
- 三条入账规则（这是本轮最需要钉死的部分）：

| 情形 | 是否计入总额 | 面板怎么显示 |
| --- | --- | --- |
| 启用、未过期、绑定的渠道**没有**自动读数 | ✅ 计入；该渠道由「未知」变成「已知（来源 manual）」 | 渠道行标注"（手动录入）" |
| 启用、未过期、绑定的渠道**已有**自动读数 | ❌ 不计（自动读数是更可信的那一份，同一笔钱不能算两遍） | 明细标「未计入」 |
| 停用 / 已过期 | ❌ 不计 | 明细标「未计入」/「已过期」，并在标题旁提示 `N 条已过期`（提醒续费） |
| 不绑定渠道（通用额度/年付包） | ✅ 计入 | 渠道列显示「不绑定（通用额度）」 |

- 每条明细都带 `counted` 字段，**面板显示的就是后端的判断**，前端不重复实现折算与判定 ——
  两处算法必然会对不上，这类"总额对不对"的问题不该靠人去核对两套实现。

## 5. 本轮踩到的两个坑

1. **面板不调用列表接口**：首页读的是余额快照里的 `manual_subscriptions`（单一数据源），
   因此 `subscription/list` 这个字面量被打包器摇掉了 —— 我最初拿它当 P14 的产物标记，
   结果假红。**教训：面板产物标记只能挑"面板真的会调用/真的会显示"的东西**，
   接口本身的存在性由活体套件（M1/M8）证明，不该靠打包产物证明。
2. **活体装置的"匿名"会被前面的登录污染**：M1 一开始写在登录之后，读到 200 就误判成"接口没鉴权"。
   现在 M1 显式跑在登录之前，并在注释里写明原因。

## 6. 边界与未覆盖

- 不做自动续费/自动重置：手动订阅就是手动，语义一旦自动化就要区分"额度重置"与"重新购买"，
  那是另一个功能；面板只负责显示"剩余 N 天 / 已过期"。
- 不做按币种分行：货币名沿用全局 `balance_currency`（一个总额只能有一个货币单位，
  混币种会让"总额"这个数字失去意义）。
- 手动订阅**不影响转发与选路**：它只参与余额聚合，不会被当成"该渠道可不可用"的依据
  （M7 就是钉这条）。真要按余额停用渠道，那是号池/配额停用的职责，已有 `QuotaZeroStop`。
