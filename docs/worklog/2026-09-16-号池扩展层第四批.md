# 2026-09-16 号池扩展层第四批：分页排序、批量动作与机器可读文档

## 1. 这一批解决什么

前三批给了外部工具包"发现后端 / 调操作 / 问细分问题"的能力。真接一个工具包进来还会撞到三件事：

1. **号池大了要翻页**：原来 `/pool/entries` 一次全回，几百条时既慢又难用。
2. **要成批干活**：探活所有不健康的、刷新所有临期的——一条条点不现实。
3. **要能生成客户端**：接一个新工具包，最省事的路径是照文档生成，而不是读 octopus 源码。

## 2. 分页与排序

`/api/v1/pool/entries` 新增 `limit / offset / sort / desc`（`sort` 可选
`kind / name / provider / status / enabled / expires`）。

- **过滤后条数与本次返回条数分开回**：`total`（过滤后、未分页前）与 `returned`（本次）。
  这一条是本批最容易写错的地方——把"这一页"当"全部"正是第三批修掉的那类误读，
  所以在响应里把两个数都摆出来，调用方不用猜。
- 先排序再分页；`offset` 越界回空列表（翻页越界是正常操作，不该报错），`total` 保持不变。
- `sort` 传了未知字段**不报错**，回退按 kind 排：外部工具传错字段是常事，
  为一个拼错的排序参数把整请求打回来不划算。

## 3. 批量动作

`POST /api/v1/pool/entries/batch`，`action` ∈ `probe / refresh / enable / disable`。

设计取向：**逐条独立**。

- 一条失败不影响其余，每条结果都有自己的错误与条目，最后给 `total/ok/failed/skipped`。
- 后端没声明该能力位时，**逐条**回 `capability not supported`，而不是整批 400
  —— 否则一个没声明 toggle 的后端会让整批 enable 全废。
- 目标二选一：`ids` 显式列出，或 `filter + max` 按条件取。**不允许"不写条件就全量"**：
  那是运维事故而不是功能，所以既不给 ids 也不给 filter 直接 400。
- 条数上限：默认 50、硬上限 200；超出的计 `skipped`（显式告诉调用方还有多少没做，不静默丢）。

## 4. OpenAPI 文档

`GET /api/v1/pool/openapi.json` 返回一份 OpenAPI 3.0.3 文档，**由注册表推导**：

- 已注册的 kind → `kind` 路径参数的枚举；
- 能力位 → 操作路由：声明了 `probe` 才有 `/probe`，没声明 `toggle` 就**没有** enable/disable；
- 12 个组件 schema（Entry / AdapterInfo / FieldSpec / Operation / Summary / BatchRequest / BatchResult …）。

这条线的价值：**新适配器注册进来，文档自动长出来**，不需要有人记得改文档——
自描述与实际路由不可能漂移。

## 5. 一个真实的传输层噪声（记录备查）

活体用例里"无 cookie 的 POST 应回 401"实测三次出现过一次 `code=0`（客户端侧连接重置）：
服务端在读完请求体之前就拒绝了请求，客户端还在写就被断开。手动复现时是正常的 401。

- 定性：不是接口缺陷（鉴权对 GET/POST 都生效，实测均为 401），属传输层抖动。
- 处理：断言**不放宽**（仍要求 401），只对传输层 code=0 重试至多 3 次，并把真实异常文本带上
  ——真坏了照样 FAIL。
