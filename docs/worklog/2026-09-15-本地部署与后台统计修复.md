## 5. 发现并修复的缺陷

用量明细三个缺陷叠加（前两个互相掩盖，第三个只在落库多周期后显形，均在 `internal/op/usage.go`）；另有统计保存周期不热生效（`internal/server/handlers/setting.go`，见 5.5）与 API Key 创建时的 `enabled:false` 被静默忽略（`internal/model/apikey.go` + `internal/server/handlers/apikey.go`，见 5.6）各一处。

### 5.1 查错表：接口恒返回空

```
2026/09/15 11:21:38 ERRO usage query error: SQL logic error: no such table: usage_rows (1)
```

`UsageQuery` 直接 `Find(&[]UsageRow)`，GORM 从扫描目标推出表名 `usage_rows`（真实表 `usage_hourlies`），
错误只进日志、调用方仍拿空切片 → 面板「用量明细」永远是空的。
修复：查询显式给定实体类型 `db.GetDB().Model(&model.UsageHourly{})`，表名由实体推导。

### 5.2 内存桶被算两次：数值翻倍 + 重复行

原实现先把未落库内存桶整批 append 进结果，随后又按键「并入」一次：
要么同键两行（重复），要么把同一桶再加一遍（**当小时数值翻倍**）。
修复：先按库内行建下标索引，内存桶命中即按下标累加、未命中收进 `pending` 再追加。

### 5.3 落库用覆盖而非累加：同小时更早窗口的用量被抹掉（实测塌陷）

内存桶落库后即被取走，因此它只装「上次落库之后」的增量，而库内同键行是更早窗口的累计值；
`clause.OnConflict{UpdateAll:true}` 直接用增量覆盖整行 → 同一小时里更早窗口的计数丢失。
现场证据（`stats_save_interval` 临时置 1 分钟以缩短观察窗口）：

```
11:46:58  db_usage_mock_good=[10,110,70]  api_usage_mock_good=[12,132,84]  db_daily=[27,2]
11:47:13  db_usage_mock_good=[ 2, 22,14]  api_usage_mock_good=[ 2, 22,14]  db_daily=[33,2]   <== 落库
```

同一次落库：日统计 27→33（正确累加，因为它写的是**全量快照**），用量行却从 110 掉到 22（被增量覆盖）。
修复：落库前把增量并进库内同键行（`mergeUsageRows`，读-加-写，方言无关，仍在后台任务里、不上转发热路径），
失败回滚逻辑抽成 `restoreUsageBuckets` 复用。

  其中 `usage == relay_logs` 在 1 分钟落库周期下跨多次 flush 逐项相等。

### 5.5 统计保存周期改值不热生效（同批修复）

`handlers/setting.go` 的 `setSetting` 只对 `model_info_update_interval`、`quota_scan_interval` 调 `task.Update`，
改 `stats_save_interval` 只写库、不重注册任务 → 面板改完要等重启才生效，与兄弟设置不一致。

修复：补 `case model.SettingKeyStatsSaveInterval`，按既有写法调 `task.Update`；注册时该周期与历史日志清理同周期，
故 `TaskStatsSave` 与 `TaskRelayLogClean` 一起跟随，避免落库与清理节奏错位。

实测（不重启，通过公开接口改值）：

```

2026/09/15 12:07:28 INFO task stats_save interval updated to 1m0s
2026/09/15 12:07:28 INFO task relay_log_clean interval updated to 1m0s
DB row updated after 60s -> (2, 22, 14)   # 新周期即时生效: 10 分钟的旧节拍不可能在 60s 内落库
2026/09/15 12:09:08 INFO task stats_save interval updated to 10m0s   # 复原为备份里的 10
```

### 5.6 新建 API Key 时 `enabled:false` 被静默忽略（Key 级审计新增）

模型里 `Enabled bool` 带 `gorm:"default:true"`，而 GORM 对带默认值标签的零值字段**不会把值写进 INSERT**
（改写成 `DEFAULT`），于是"创建一条禁用的 Key"实际落库成启用。实测（本地实例，修复前）：

```
POST /api/v1/apikey/create {"name":"DS-TEST-diag-off","enabled":false} -> 200 {"enabled": true}
GET  /api/v1/apikey/list   -> persisted enabled = True
POST /v1/chat/completions  (用这条"禁用"Key) -> 200 正常转发
```

试过两种写法都不行（都已实测）：`Select("*")`、显式列名列表 —— GORM 仍对该列写 `DEFAULT`。
正解是把默认值从模型搬到入口：

1. `internal/model/apikey.go` 去掉 `gorm:"default:true"`（零值从此即 false，插入按入参原样落库）；
2. `internal/server/handlers/apikey.go` 的 `createAPIKey` 改用 `createAPIKeyRequest{model.APIKey; Enabled *bool}`，
   `nil`（没传）→ true 保持既有约定，显式 false → 真的停用。

影响面极小：`APIKeyCreate` 只有一个生产调用方（该处理器），`Enabled` 只在 `middleware/auth.go:54` 读取；
前端 `CreateAPIKeyRequest` 的 `enabled` 本就是可选，故"不传即启用"的既有行为不变。
新增 `internal/op/apikey_test.go` 2 例（修复前第 1 例实测 FAIL，修复后 2/2 PASS）。

修复后实测：`create {enabled:false}` → 返回与落库都是 `false`，用该 Key 转发 → **401 `API key is disabled`**。

## 6. 结论为非缺陷（实测确认）

- **全员不可用时继续等待**：`handler.go` 明确设计为等冷却到期/人工改配置，客户端放弃后请求记为 `canceled` 并计一次失败。
- **冷却后重入只给一次机会**：`recordRouteFailure` 的探测语义，属设计。
- **取消请求计入 `request_failed`**：`state.go` 口径「非成功即失败」，日志行仍保留精确 `canceled` 状态与原因。
- **备份中 47 条价格为 0**：数据事实，成本即 0。

- **删除不存在的 API Key 返回 500 而非 404**：`deleteAPIKey` 把 `op.APIKeyDelete` 的
  "API key not found" 归到 `StatusInternalServerError`；实际动作没发生、数据没错，属状态码瑕疵（本轮两次删除同一 id 时复现）。
- **删除 Key 会连同它的统计行一起删**（`APIKeyDelete` → `StatsAPIKeyDel`），而 aggregate `total` 保留那部分流量：
  于是 `total - Σapikey` 会等于"历史被删 Key 的用量"。本轮实测差额恰为 8 次成功 / 165 in / 85 out，与 Key 级审计里
  那些"用后即删"的测试 Key 流量逐项吻合 —— 语义自洽，非记账错误。
- **`/api/v1/apikey/stats` 返回 `{stats, info}` 两个子对象**（Key 自助视角），与 admin 侧 `/api/v1/stats/apikey`
  的平铺行不是同一形状；两者数值一致（本轮 12/12 里 T2 逐项比对过）。
