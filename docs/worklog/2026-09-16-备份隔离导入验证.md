# 2026-09-16 第十一批：备份隔离导入验证（R-test-001）与它查出的迁移缺陷（T-migrate-001）

## 本轮要办的事

需求登记里 R-test-001「本地备份隔离测试」是用户自己提的（原话口径）：把
`../octopus-本地数据/数据备份(勿提交).json` 导进一个**隔离**环境，验证登录、渠道、分组、
协议转化都正常，**不许碰生产**。本轮把它做成可反复执行的活体套件，并在过程中查出并修掉了

## 一、交付：备份隔离导入套件（scripts/api-tests/run_backup_import_test.py，22/22）

### 隔离是怎么做到的（三层，缺一层都不算隔离）

1. **独立实例**：用 `octopus.exe start --config <临时配置>` 起第二个实例，配置里写明
   自己的端口（13304 / 11235）与自己的数据库文件（`%TEMP%\octopus-dstest\lab\lab-data.db`）。
   仓库的 `internal/conf/config.go` 是按 cwd 的 `data/config.json` 找配置的，`--config` 能
   直接指到临时文件，所以实验室与生产实例的库、端口、缓存完全分离。
2. **脱敏副本**：导入的是备份的副本 —— 12 个渠道的 `base_url` 全部改指本地 mock
   （`http://127.0.0.1:18099`），其余字段逐字保留。这一层挡的是"直连调用"。
3. **关掉后台出网类任务**：产品自带两条会**自己**按渠道 `base_url` 出网的路径 ——
   余额扫描（`quota_scan_interval` 默认 5 分钟一轮）与冷却成员主动探活
   （`route_probe_enabled`，代码注释明写「探测是真实计费请求」）。脱敏副本里把
   `quota_scan_interval=0`、`route_probe_enabled=false`、`model_info_update_interval=9999`，
   并把 5 个告警渠道与 SMTP 目标清空（否则实验室出的告警会真的推到用户手机）。
   这一层挡的是"不发请求也会出网"。

### ★ 硬安全闸门

导入**之前**先断言"实验室的临时库文件确实存在"（证明实例真的用了自己的库，而不是
忽略 `--config` 回落去开生产库）。不满足就立即中止、绝不导入 —— 否则备份会被写进生产库。
这是本套件里唯一一处"宁可整个失败也不继续"的设计，写在代码注释里。

### 判据设计上的两个修正（都是自己踩出来的）

- **不能拿生产库 mtime 当"没被改动"的判据**：生产实例自己会周期性写统计，mtime 必然变化，
  拿它做断言既会假失败、也会掩盖真正的写入。改为"六张用户数据表计数 + 渠道指纹"。
- **`channel_grants` 没有 `channel_id` 列**：它经 `channel_model_id` / `channel_key_id`
  两侧各自回指渠道。挑调用测试分组的 SQL 必须从 `channel_models` 取渠道、从 `channel_keys`
  取凭据，并断言两侧同属一条渠道。

## 二、查出的真实缺陷：全新安装第一轮没有请求日志表（T-migrate-001）

### 怎么发现的

套件跑到 L15（"调用落进 relay_logs"）时直接报 `no such table: relay_logs` —— 实验室是
**全新库**，而生产库有 2757 行。这不是套件的问题，是产品的问题。

### 根因

- `relay_logs` 曾在 2025-12 以另一种形状存在（`time`/`request_model_name`/`ftut`/`use_time`/`request_content`…）。
- 迁移 009（2026-08-24）的职责之一就是**删掉这张遗留表**，它注册在 **AfterAutoMigrate**。
- 2026-09-13 的日志卡片改造又**重新引入**了 `relay_logs`（列与旧形状无一处同名，且加入了
  `AutoMigrate` 列表）。
- 于是全新库首次启动的顺序变成：`AutoMigrate` 建好新表 → 009 紧跟着把它 DROP 掉。
  而 009 的迁移记录已经写下，后续启动不再重跑；要等**下一次启动** `AutoMigrate` 才会把空表建回来。
- 后果不只是"日志页空"：`RelayLogSave` 是 `_ = Create().Error`（忽略错误），
  所以第一轮运行期间**每一条请求日志都被静默丢弃**，日志页与 CSV 导出都是空的。

### 证据（先复现，再修）

一次性临时库、独立端口、不碰生产、不打任何上游，跑两轮启动：

```
第一轮启动（全新库）: 表 20 张；relay_logs 存在=False
第二轮启动（同库重启）: 表 21 张；relay_logs 存在=True
```

修复后重跑同一脚本：两轮都是 21 张、`relay_logs 存在=True`。

### 修法：原地加"形状判据"，不挪迁移阶段

`internal/db/migrate/009.go` 改成**先判形状再删**：表存在**且**含旧形状独有的列
（`request_model_name`/`actual_model_name`/`ftut`/`use_time`/`request_content`）才删。
判据成立的前提是 GORM 的 `AutoMigrate` **只加列不删列** —— 所以即使它已经给旧表补齐了新列，
旧列依然在，判据在 AutoMigrate 前后都成立。

**为什么不是把 009 整体挪到 AutoMigrate 之前**（那是最直觉的修法）：同批的迁移 005 依赖
遗留的 `channels.base_urls` 列做迁移，009 提前删列会让 005 失去输入，旧库升级时 `base_url` 会丢。
所以只在原地加判据，不动阶段。

三个路径的最终行为：

| 场景 | 行为 |
|---|---|
| 全新库 | `AutoMigrate` 建的新表保留（**本轮修复点**），第一轮就有日志 |
| 旧库升级（表是旧形状） | 旧表照旧被删（原意保留：旧格式日志行列列不同名，留着只会让日志页读到脏行） |
| 现有库（009 记录已在） | 迁移整条跳过，2757 行日志与原样保留（已实测核对：列全为新格式、无旧列残留） |

### 回归测试与变异验证

新增 `internal/db/migrate/009_test.go`（4 例）：全新形状保留且**能真正落一行并读回**、
旧形状被删、表不存在时不报错、同批的 `channels.base_urls` 删列行为没被带偏。

变异验证（判据有效的证据必须是"去掉修复就变红"）：把 `if legacyRelayLogs(db)` 改成 `if true`
（等价修复前的无条件 DROP）→ `TestMigrate9KeepsFreshRelayLogs` 立刻失败，报文正是
`relay_logs was dropped on a fresh install: 新装第一轮会没有请求日志表（正是要修的缺陷）`；
还原后 4 例全绿。

## 四、复现处方（下次直接用）

- 起第二个实例做隔离验证：`".\octopus.exe" start --config "<临时配置 json>"`，
  配置里写 `server.admin_port` / `server.relay_port` / `database.path`；
  按端口停进程（`netstat -ano | findstr LISTENING | findstr ":PORT "` + `taskkill /PID .. /T /F`），
  绝不按进程名杀。
- 导入真备份前，必须先把渠道 `base_url` 指向本地桩**并**关掉 `quota_scan_interval` /
  `route_probe_enabled` / 告警目标，否则后台任务会自己出网、真推送。
- 导入前先断言临时库文件确实生成 —— 这是防"配置没生效、备份写进生产库"的唯一一道闸。
