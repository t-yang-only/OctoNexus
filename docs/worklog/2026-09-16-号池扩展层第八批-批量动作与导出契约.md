# 2026-09-16 号池扩展层第八批：批量动作上页面 + CSV 导出给表格软件用

## 1. 批量的口径：选择就是 ids，绝不隐式全量

后端 `/pool/entries/batch` 在第四批就做好了，页面一直没用上。这一批把它接上，并且坚持一个口径：
**批量动作的目标必须来自"人选中的条目"，不提供"对当前筛选条件全量执行"这种入口**。
理由很直接 —— 号池里的启停会直接影响线上路由，误伤面必须由人显式圈定。

页面实现：
- 每行一个复选框，表头一个"全选本页"；选中态按 `kind:id` 存，跨页保留；
- 工具栏显示「已选 N · 本页 M」，并提示单次上限（后端硬上限 200，超出部分回执里记 `skipped`）；
- 批量按钮的可用性看**选中条目所属后端是否声明了该能力位**（没声明就置灰，不替后端兜）；
- 一次调用只针对一种后端：选中的键按 `kind` 分组，逐组调用（条目 id 自身可能含冒号，
  如 official 的 `provider:account_id`，所以按**第一个**冒号切分）；
- 跑完只保留**失败/未执行**的那几条选中：既方便直接重试，也不会把已成功的重复提交一遍；
- 回执拼成一条人读得懂的话：`成功 N · 失败 M（｜失败原因前三条）`，失败的走红字。

## 2. CSV 导出的两处真实改进

导出这条路的使用者是"人/表格软件"，之前有两处不顺手：

1. **没有 BOM**：中文条目名在 Windows 的表格软件里打开就是乱码。
   现在响应体首字节写 `EF BB BF`，`Content-Type` 仍是 `text/csv; charset=utf-8`。
2. **部分后端取不到数据时没法察觉**：CSV 里没有地方写"哪个后端这次失败了"（JSON 分支有 `kind_errors`）。
   现在这种情况会带一个响应头 `X-Pool-Error-Kinds: <kind,kind>`，外部工具可读。

注意：加 BOM 会改变首行内容，**原先 P15b 的 `lines[0].startswith("kind,id,...")` 断言会因此变红** ——
这不是回归，是断言要跟着契约走：已改为先剥 BOM 再判表头，并新增 P15c 专测 BOM 与每行列数。

## 5. 踩坑（本轮新增，可复现）

- **React Compiler 不接受"手工记忆化 Map/Set"**：把选中键按 kind 分组写成
  `useMemo(() => { const map = new Map(); ...; return map; }, [selected])` 会被
  `react-hooks/preserve-manual-memoization` 判错（"Existing memoization could not be preserved"）。
  改法是**直接算**（选中规模就是几十条，不值得 memo）——注释里写清了为什么不用 useMemo。
- `useMemo` 依赖里用 `entries.data?.items ?? []` 会触发 `react-hooks/exhaustive-deps` 警告
  （每次渲染都是新数组），把 `items` 自己包一层 `useMemo` 即可。
- `setSelected((prev) => { const next = new Set(prev); ...; return next; })` 是类型错误
  （返回类型必须还是 `string[]`）→ `return [...next]`。
