# 速度观测与速度应对（T-speed-001）

> 日期：2026-09-18
> 分支：`master`（工作区改动，未提交）
> 用户原话：「每个 key 可能只有一点钱所以要进行分压,按照剩余请求数，api 进行最优分配，还有一些限流和速度不是很好你都要给我做出应对的办法,进行迭代升级,并给前端页面升级更加项详细的监控页面」
> 本轮范围：这句话里的**「速度不是很好」**那一项（分压/限流/监控页已在上一轮交付，见 `2026-09-18-额度分压与限流监控.md`）

## 1. 目标

把「速度不好」从一句抱怨变成三个可量、可调、可验证的机制：

1. **量出来**：每个成员的首帧耗时（TTFB）与输出吞吐（token/s），样本不足不下结论；
2. **体现到分配上**：慢成员少分流量（只削权、不剔除，避免成员无声消失）；
3. **提前止损**：平时很快、突然卡住的成员，别让整个请求陪着它等满超时。

## 2. 做了什么

新增 `internal/relay/speed.go`（约 200 行）：

| 机制 | 口径 |
|------|------|
| 观测窗口 | 每个成员最近 **120s** 内的成功样本：首帧耗时取均值（只有流式有真值）、吞吐 = completion tokens ÷ 本轮耗时 |
| 结论门槛 | 样本 < 3 一律不下结论：折扣 = 1、看门狗不动（未知不惩罚） |
| 削权 | `(1/慢度)^(强度/100)`，慢度 = max(1, 首帧÷慢阈值, 慢阈值吞吐÷吞吐) —— **最差的那一维说话**，只削权到 1、从不剔除 |
| 自适应看门狗 | 流式「等首帧」预算 = `min(分组配置, 实测首帧 × 倍数, 下限)`，默认倍数 4、下限 5000ms，**只收紧不放大** |
| 掐断的代价 | 按真实失败处理：计尝试次数 + 按配置冷却 + 换下一个成员（既有重试路径，未新增语义） |

接线（都在既有装配点上，没有第二条选路路径）：

- `internal/relay/allocate.go`：`allocatePlan` 里健康折扣与速度折扣**取最差**（`math.Min`，不叠加）；
  `allocateSettings` 带上 `speed` 子结构，仍是同一份设置读取入口。
- `internal/relay/handler.go`：流式首事件超时改为走 `firstEventBudgetDuration`；成功路径记录
  `recordMemberSpeed`（非流式只记 TTFB=0 与 tokens，流式记首帧 + 吞吐）。
- `internal/relay/allocmon.go` + 前端首页监控页：新增「速度（首帧 / 吞吐）」列、「慢成员」卡片、
  速度设置项提示，四行「生效口径」说明。
- `internal/model/setting.go`：5 个新设置键 `route_allocate_speed_weight`(40)、`route_speed_slow_ttfb_ms`(3000)、
  `route_speed_slow_tps`(8)、`route_speed_first_event_multiple`(4)、`route_speed_first_event_floor_ms`(5000)，
  越界在 `Validate` 阶段拒绝（强度 0-100）。
- 前端三语（zh_hans / zh_hant / en）：`setting.routing.speed*` 12 个键 + `home.allocation` 的列/卡片/提示。

## 4. 本轮踩到并被判据抓住的东西

1. **装置测错了对象**：V3 一开始用「客户端可见耗时」当判据，实测开=60.0s（客户端超时）、关=15.0s。
   读 `handler.go` 认定：单成员分组被掐断后，该请求会落进既有的「等可用成员」循环直到客户端超时 ——
   这是**改造前就有的**行为（分组自己配的 30s 首事件超时同样如此），并不是看门狗引入的。
   于是把判据换成「该成员何时进入冷却」（诚实、可差分的外部事实），V3 立刻 5/5。
   附带教训：被掐断的那一轮**不产生速度样本**，装置必须先让慢成员攒够 3 个样本（预热时关掉看门狗），
   否则用例测的是装置不是功能。
2. **变异是编译错误时不算抓到了**：第一版 SP1 把 `math.Min(healthFactor, speedFactor)` 换成 `healthFactor`，
   结果 `speedFactor` 未使用 → 编译失败 → 「红」但只证明编译器拦住了，不证明判据抓到了行为变化。
   改成可编译的变异（`_ = speedFactor`）后**全套单测仍然绿** —— 真实缺口：只测 `memberSpeedFactor` 的用例
   抓不到「折扣有没有接进分压」。补了穿过装配点的判据 `TestAllocatePlanAppliesSpeedDiscount`
   （两成员余额相同 + 一个量成慢 → 权重必须更低；关掉强度 → 权重必须相等），该变异随后变红。
   纪律：凡「新维度接入既有决策」，必须有一条穿过真实装配点的判据，不能只测算分函数。

## 5. 全量矩阵与两处装置修正

全量活体矩阵：**34 个套件、未通过 0 个**（本轮把新的 `speed` 套件登记进 `scripts/api-tests/run_all.py`）。
矩阵第一次跑出 2 个红，两个都查到了根因，且都不是「随手改绿」：

1. **`allocate` 9/10 —— 新默认值把老用例变成「两个变量同时动」**：A2 原本断言「余量 9:1 → 分配 ≈ 11:1」，
   而 mock-slow 这个名字本身就代表它天然慢（首帧 15s）。速度维度带上默认强度 40 之后，同一个 12 次分配里
   「额度比例」和「速度折扣」同时在动，实测变成 9:3，红的说不清是谁的原因。**修装置而不是改断言**：
   A2 拆成两相 —— 相 1 把速度强度归零，只留额度这一个变量（实测 11:1，符合 900:100）；
   相 2 恢复默认强度、**只读监控不再发请求**（样本相 1 已攒够），断言「同一个比值跨相下降」。
   这里还踩了一个坑：分压权重先把剩余请求数铺成「组内最大 = 100」再乘折扣，所以本装置里被削权的 mock-slow
   仍是组内最高权重（32 vs 11）——拿「慢成员权重 < 快成员权重」当判据会冤枉正确实现。
   最终 A2b 实测：慢/快权重比 **9.091 → 2.909**（正好是 0.32 的速度折扣），且两成员都还在分配里。
2. **`pooldecl` 8/9 —— 一次瞬时连接错误被记成「写=0」**：D8 的写探针（转发口的 `POST /v1/pool/adapters`
   必须 404）偶发拿不到状态码。手工复现（含真实报文与 8KB 大报文）**全部稳定 404**，说明不是产品问题；
   而用例把「拿不到响应」这个异常折成一个裸 `0`，红了也看不出原因。修法是让失败信息带上原文
   （`call()` 返回的 `_raw`），随后复跑 9/9，下一次真出问题能直接看到异常类型。
   **教训：断言失败必须自带病因**，否则「偶发红」只能靠重跑掩盖。

3. **`allocate` 收尾把实例留在「测试隔离值」上**：套件运行期为了让断言单变量把健康折扣压成 0，
   但收尾没恢复出厂默认，于是跑完矩阵后本机实例停在非默认状态（下次人工看现象会与发布件行为对不上，
   看起来像功能坏了）。已在收尾显式恢复 `route_allocate_health_weight=40`，并从监控接口读回出厂值确认。
   **纪律：套件收尾恢复的是「出厂默认」，不是「测试期间改掉的那个值」；收尾后要用外部可观测事实（接口读回）
   确认，而不是假定写进去了。**
