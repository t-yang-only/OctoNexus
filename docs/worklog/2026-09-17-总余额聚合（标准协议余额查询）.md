# 总余额聚合：把各中转的剩余额度折成一个总余额，并按标准协议可查（T-balance-001）

## 需求（用户原话）

> 我还需要进行所有的apikey以及各个中转的剩余次数和余额根据计算自动转化成总余额，请求api的时候可以通过标准的请求协议查看到这个余额

拆成三件事：① 汇总「各中转/渠道」的余额；② 汇总「各 API Key」的额度与「剩余次数」；③ 折算成一个总余额，并**通过标准请求协议**（就是客户端已经在用的那几个计费端点）查得到。

## 口径决定（全部建立在既有事实上，不新增采集）

| 数据 | 来源（既有事实） | 本项目的处理 |
| --- | --- | --- |
| 渠道余额 | `op.ChannelBalance` 内存快照 ← 配额扫描 `task/quota_scan.go` 与号池站点刷新 `pool/station.go` 写入（加权选路的 `balance` 维度读的就是它） | 按 `balance_points_per_unit`（默认 500000，new-api 惯例）折成货币值 |
| 剩余次数 | 渠道的 `MonthlyQuota - MonthlyUsed` | 只有填了包月额度的渠道计入合计；没填的记 0，不当成「用完了」 |
| API Key 额度 | `APIKey.MaxCost` + `StatsAPIKey`（`middleware.APIKeyAuth` 判额读的同一份） | 逐 Key 回 上限/已花/剩余/请求数/词元数；不限额度用 `unlimited` 表达 |
| 总余额 | 上表第一行求和 | **只累加「读到过余额」的渠道**，未读到的只计入 `unknown_channels` |

两条刻意的取舍：

1. **未知余额不计入总额**。把「还没扫到」当 0 会显示成「你没钱了」，当有值又会虚高——两种都会让人做出错误判断（比如误以为该充值了）。
2. **客户端 Key 的额度不计入总额**。`MaxCost` 是「你允许花多少」，不是「上游还能用多少」；把它加进总余额会把自设的上限当成上游资产。它只作为明细与本 Key 的自查（标准协议的 `usage` 端点回的正是它）。

## 端点（T-balance-001）

| 端口 | 路径 | 鉴权 | 形态 |
| --- | --- | --- | --- |
| 转发口 | `GET /v1/dashboard/billing/subscription` | `APIKeyAuth` | one-api / new-api 口径：`hard_limit_usd`/`soft_limit_usd`/`system_hard_limit_usd` 都是**总余额 + 本 Key 已花**，另附 `total_available`/`total_monthly_remaining` 等自有字段 |
| 转发口 | `GET /v1/dashboard/billing/usage` | `APIKeyAuth` | `total_usage`（分，乘 100）、`total_usage_usd`、`requests`、`tokens` |
| 转发口 | `GET /v1/balance` | `APIKeyAuth` | 本项目自有：总余额 + 逐渠道明细 + **本 Key** 额度 |
| 管理口 | `GET /api/v1/balance/summary` | `middleware.Auth()` | 面板首页与设置页读的完整快照（含全部 Key 明细） |

三个转发端点挂在 `/v1` 路由组下、复用同一套 `middleware.APIKeyAuth`：**用哪把钥匙调用模型，就用哪把钥匙查余额**，不需要额外的管理凭据。管理面必须先登录——快照里有各渠道名称与余额，匿名可读等于把上游账号的资产状况公开（活体用例 B1 就是这条守卫，第一版漏了 `middleware.Auth()`，被 B1 当场抓出 401→200）。

### 语义自洽（客户端是这么算的）

客户端普遍按 `hard_limit_usd - total_usage/100` 显示余额。本项目让这个减法**正好等于总余额**：

```
hard_limit_usd           = 总余额 + 本 Key 已花
total_usage (分) / 100   = 本 Key 已花
hard_limit_usd - total_usage/100 = 总余额
```

活体读数（B5）：`limit=34.35374467260005`、`used=34.34994467260005`、`total=0.0038`，等式成立。

`start_date`/`end_date` 只接受不解释：本项目只有累计口径的用量统计，假装支持区间过滤会给出一个**比真实值更可信的错数**。

## 判据灵敏度（变异检查，T-balance-002）

把两处守卫改回旧行为，要求对应用例变红（`%TEMP%\octopus-dstest\mutation_check.py`，BAL 系列）：

| 变异 | 改法 | 期望用例 | 实测 |
| --- | --- | --- | --- |
| BAL1 折算口径写死 | `ConvertBalancePoints(remaining, pointsPerUnit)` → 传默认 500000（设置项静默失效） | B2b | **如期变红**：`balance=0.00076`（应为 0.0038） |
| BAL2 管理面不要求登录 | `Use(middleware.Auth())` → `Use(middleware.RequireJSON())` | B1 | **如期变红**：匿名读回 `HTTP 200`（应为 401） |

两条变异各修了一次装置：

- BAL1 第一次把期望用例写成 B3a（断言 500000 口径下 380 点 = 0.00076）——**它恰好等于默认口径的折算，所以不会红**；套件里真正抓到这条变异的是 B2b（断言 100000 口径下 0.0038）。教训：变异不变红时先看「是不是撞上了另一条口径」，再改期望用例，而不是删用例。
- BAL2 第一次用「注释掉中间件」的改法，`middleware` 导入变成未使用 → 编译失败（装置不成立，不算数）。改成替换成同包另一个已导出的中间件（保持导入被使用），才测的是「鉴权有没有」这件事本身。

## 边界与未做

- **不新增采集**：余额仍由既有的配额扫描（默认 5 分钟）与号池刷新写入；快照是内存态，重启后到下一轮扫描前按「未知」处理（与选路同口径，不写库）。
- **不做货币换算**：`balance_currency` 只是显示名，换 CNY 不改变任何折算；真正的口径是 `balance_points_per_unit`（不同站的「点」价值不同，只能由用户填）。
- **未做日期区间过滤**（见上）。
- **未做 Key 级别的余额告警**：现有告警是渠道级（余额阈值/归零停用），Key 超额只在鉴权时拒绝。
- 渠道凭据静态加密（R-sec-001）与本次无关，未触碰。
