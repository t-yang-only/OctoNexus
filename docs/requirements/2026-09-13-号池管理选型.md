## 0. 结论摘要（一句话）

**自建为主、外部并入为辅**：账号来源坚持走官方 OAuth（sub2api 那条路线），凭据与运维面继续用本项目
既有的渠道层 + 号池扩展层；外部开源项目只当**适配器接入对象**，不把号池托管出去。
逆向类与批量注册类工具一票否决。

推荐顺序：**OpenAI → Gemini → Claude**（官方账号池）；运维信息先接 all-api-hub 式**只读**视图；
opencodex 的会话级粘性只借机制、不接代码。

**红线判据（一票否决，不进候选）**：绕过验证码、协议/Cookie 逆向、盗用他人凭据、批量注册、
临时邮箱注册、把"别人的订阅"当默认供给来源。上表后两行即按此出局——它们技术上"能用"，
但一旦接进来，风险与控制权都不在我们手里（封号、ToS、法律）。

## 2. 合规红线（与 R-sec-001 / T-acct-001 同口径）

1. 账号只走**官方 OAuth / 扫码授权**；凭据密文落库（AES-256-GCM，`OCTOPUS_OFFICIAL_KEY`，AAD 绑服务商）
   ——已在 `internal/op/official_account.go` 交付；跳转令牌只存 SHA-256 哈希。
2. 渠道 Key 的**静态加密迁移**仍是未决项（R-sec-001 余项）：在该项完成前，不新增任何明文落库路径。
3. 日志 / 导出 / 响应头**绝不出现凭据**——已有外部可观测判据守着（凭据隔离覆盖 10 条协议路径 +
   判据自身的负向对照自检），新增出口必须一起纳入该判据。
4. 不接逆向类与批量注册类；不把"订阅拼车"做成默认配置（自建有需要可以，但出厂预设不提供）。

## 4. 推荐优先级（以及"先接哪些工具包"的初判）

1. **OpenAI**：官方 OAuth 最成熟、封号风险最低 —— 先接；
2. **Gemini**：次之；
3. **Claude**：订阅共享的 ToS 灰区最大 —— 最后；
4. **第三方池项目只作适配器接入对象**：先接 all-api-hub 式的**只读运维信息**（余额/可用性/价格），
   不接账号托管、不接自动签到这类"以你的身份对外动作"的能力。

与本报告配套的四个边界（⑩，落地时逐条拍板）：
① 声明式适配器的安全边界（能力白名单、禁止任意网络/任意写）；② 只读 APIKey 渠道（外部项目只读其视图，
不回写）；③ 通用入口 → 凭据同步的方向与撞名规则；④ 先接哪些工具包（本报告第 4 节已给初判）。
