- 台账编号：`NM-CUR-025`
- 日期：2026-09-13
- 用户指令（本轮原话要点）：
  1. **最大程度保留 bestruirui/octopus 的外观**，不加得过于复杂，要简洁
  2. 只要**一个这样的细致监控**（指 new-api「模型调用分析」截图那类：总数/额度/token/RPM/TPM/成功率/延迟/吞吐/分模型健康/消耗分布时序图）
  3. 数据 Agent 决议：**小时桶保留 180 天滚动删**（覆盖此前 90 天建议）

## 设计裁决（写入需求文档，供各 Agent 对齐）

| 项 | 裁决 | 理由 |
|---|---|---|
| 页面形态 | **不做 new-api 式三 Tab 看板、不新增导航页**。在 octopus 首页（Home）现有四件套（Total/Activity/StatsChart/Rank）之后追加一个「模型监控」区块 | 最大程度保留原外观；首页本就是统计页，监控是统计的细化 |
| 图表库 | **复用本仓现有图表组件**（home/chart 所用栈），不引入 VChart/recharts 新依赖 | 简洁 + 外观一致 + 零新依赖 |
| 监控内容（单块内） | ① 分模型小时明细表：模型 × 小时 → 次数/成功率/平均延迟/token/费用，近 24h/7d/30d 切换；② 消耗分布堆叠柱（按模型分色，与首页图同风格）；③ 模型健康徽标行（成功率着色，照截图语义但用本仓 Badge 样式） | 用户要的"细致监控"三要素：明细、分布、健康 |
| 数据模型 | 新增 `UsageHourly` 表：`hour(截断到小时) × model_name × channel_id`，字段复用 `StatsMetrics`（Input/OutputToken、Input/OutputCost、WaitTime、RequestSuccess/Failed） | 与现有 stats 口径完全一致，前端计算逻辑可复用（RPM/TPM=次数或token/分钟跨度；成功率、平均延迟=WaitTime/次数） |
| 写入路径 | relay 转发成功/失败处一行 `LogUsageHourly`（内存 map 按小时桶累加，同 `StatsMetrics` 现有模式），随 `StatsSaveDB` 周期批量落库 | 零新调度器；与统计保存策略同构，不新增配置项 |
| 清理 | 落库任务顺带 `DELETE FROM usage_hourly WHERE hour < now-180d`（每轮一次，无新任务） | 用户拍板 180 天；实现为搭车清理，不加 cron |
| API | admin 口新增 `GET /api/v1/stats/usage?range=24h|7d|30d&group_by=model|channel`，返回小时桶行 + 聚合汇总 | 双端口已拆好，管理数据走 3303 |
| 不做（YAGNI 砍掉） | 分流 Tab、用户统计 Tab、偏好设置弹窗、柱/面积切换、uptime 面板、告警通知、perf_metrics 独立表 | 用户明确"不要复杂"；后续要再加 |
