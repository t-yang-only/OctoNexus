# 号池扩展性设计（R-pool-ext-001）

日期：2026-09-16　执行：dsh-local（NM-DS-022）
用户原话：**「我要号池加入高度的扩展性，可以基于已有的，开发大量 api 接口，后面好可以进行各种反代工具包的扩展」**

## 1. 现状（先把"已有的"说清楚）

号池目前只有一种形态，链路是：

```
OfficialAccount（官方账号, 凭据加密入库）
      │  op.OfficialPoolSync（幂等物化 + 临期刷新）
      ▼
Channel「官方账号池-<provider>」 ── 每个账号 = 一条 ChannelKey（凭据即解密后的 token）
      │  信道拉取模型 + 三协议实测
      ▼
ChannelModel + ChannelGrant ────► 选路（Group/GroupItem）
```

- 服务商固定三类：`openai` / `gemini` / `claude`（`model.OfficialAccountProvider`）。
- 已有接口散在 `/api/v1/account/official/*`（authorize/callback/list/usage/pool-sync/pool-list）与 `/api/v1/account/jump/*`。
- 「统一号池视图」已有雏形：`model.OfficialPoolStatus{Members[]}`（账号 → 凭据映射）。
- 另有一套「中转站账号读取」客户端（`internal/health/relay_account*.go`），但**没有存储表**，也未接入号池。

问题：**每加一种号池后端，都要改 op 层、加 handler、再改前端**；接口是按后端切分的，外部工具无法先问"有哪些后端、各自能做什么"，也无法用同一套调用处理不同后端。

## 2. 三种方案与取舍

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 适配器注册表 + 统一视图（选定）** | 新增 `internal/pool`：Adapter 接口 + Registry + 统一 Entry；每种后端一个适配器；接口按统一视图给 | 新后端只加一个适配器文件；接口/前端不用改；能力位自描述，外部工具可发现 | 需要一层投影（既有实现不动） |
| B. 只加接口，不改抽象 | 直接为官方账号池多写几十个 REST 接口 | 快 | 每加一种后端接口翻倍；前端要认两套字段；外部工具没法复用 |
| C. 插件进程 / 外部服务 | 号池后端跑成独立进程，经 RPC 接入 | 隔离彻底 | 部署复杂度、权限与凭据传递面变大；当前规模不值 |

选 **A**：它让"扩展"落在**新增一个适配器**这件事上，而不是"再写一遍接口"；同时保留升级空间——将来外部后端可以用声明式 spec 注册（见 §5），也可以实现成独立进程再由适配器转发。

## 3. 架构（已落地部分）

```
internal/pool/pool.go
  ├─ Capability       能力位：list/get/probe/refresh/toggle/provision/revoke/sync
  ├─ AdapterInfo      自描述：kind/title/capabilities/fields/secret 标记
  ├─ Entry            统一视图一行：kind/id/name/provider/status/enabled/healthy/plan/expires/labels/detail
  ├─ Adapter          统一接口：Info() + Entries(ctx)
  ├─ Register/Kinds   注册表（重复 kind 报错、能力位与 kind 校验）
  ├─ Entries(ctx,kind) 统一视图（kind 空=全部）
  ├─ Snapshot(ctx)    聚合计数
  └─ safeEntries()    适配器 panic 兜底 → 变 warning，不打死整张表

internal/pool/official.go
  └─ 官方账号池适配器（内置）：投影 op.OfficialPoolStatusList，只读、不新增表、不动选路
```

三道**刻意**的设计决定：

1. **能力位必须显式声明**，接口层按位拦截。没实现的写操作宁可说"没有"，也不要让外部工具调到一半才发现后端不支持。
2. **一个后端坏了不拖垮整张表**：错误进 `warnings[]` 且 HTTP 仍 200。号池是排查现场的地方。
3. **适配器 panic 兜底**：适配器是扩展点，将来是别人写的代码。panic 变 warning（`safeEntries`）。

安全口径沿用既有号池：**凭据永不回显**。`FieldSpec.Secret` 只用于告诉外部工具"这个字段是凭据、别指望接口回显"；`Entry` 只带元数据。

## 4. 接口面（第一批已交付，只读）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/pool/kinds` | 已注册后端 + 能力位 + 字段说明（含 secret 标记）——**外部工具包的自发现入口** |
| GET | `/api/v1/pool/entries?kind=` | 统一视图；kind 留空=全部；单后端失败进 `warnings[]` |
| GET | `/api/v1/pool/stats` | 聚合计数（总数/启用/健康/分后端） |

规划（按价值排序，等确认）：

| 批次 | 接口 | 说明 |
| --- | --- | --- |
| 2 | `GET /api/v1/pool/entries/:kind/:id` | 单条详情（含后端特有明细） |
| 2 | `POST /api/v1/pool/entries/:kind/:id/{probe,refresh,sync}` | 按能力位开放的生命周期操作 |
| 2 | `POST /api/v1/pool/entries/:kind/:id/{enable,disable}` | 人工启停（需要适配器声明 toggle） |
| 3 | `POST/DELETE /api/v1/pool/adapters` | **运行时注册声明式适配器**：用 JSON spec 描述一个反代工具包（基址/登录/刷新/余额/列表的端点与 JSON 路径），不改代码就接入新工具包 |
| 3 | `GET /api/v1/pool/events`（SSE）或 webhook | 号池状态变化外发，供外部工具联动 |

声明式 spec 的形状（草案，第三批）：

```json
{
  "kind": "custom-relay-x",
  "title": "某反代工具包",
  "capabilities": ["list", "probe", "refresh"],
  "auth": {"type": "login", "url": "{{base}}/api/user/login",
           "body": {"username": "{{username}}", "password": "{{password}}"},
           "token_path": "data.access_token"},
  "list": {"url": "{{base}}/api/token/?p=0", "items_path": "data.items",
           "fields": {"id": "id", "name": "name", "status": "status", "enabled": "status==1"}},
  "probe": {"url": "{{base}}/api/user/self", "healthy_path": "success", "balance_path": "data.quota"}
}
```

## 5. 三种扩展姿势（这就是"高度扩展性"的落点）

1. **内置适配器**：在 `internal/pool` 加一个文件（实现 Info/Entries），init 注册即可 —— 改动面 = 1 个文件。
2. **启动期外部注册**：外部工具包在自己的 `init` 里 `pool.Register(myAdapter{})`（octopus 作为库嵌入时）。
3. **运行时声明式注册**（第三批）：`POST /api/v1/pool/adapters` 提交 JSON spec，不重新编译就接入。

## 6. 待用户拍板的取舍（我不擅自定）

1. **运行时声明式适配器是否开放**：它最"扩展"，但等于开放一个"让 octopus 按 JSON 去请求任意 URL"的入口 —— 是否需要限制（仅本地、仅白名单域名、还是不加限制）？
2. **API 认证范围**：号池接口现在全在 Admin 端口 + Auth 之后。外部工具包是否需要一个**只读的 APIKey 通道**（例如 `GET /pool/entries` 用 APIKey 鉴权）？
3. **通用 sync 抽象**：要不要把"号池条目 → 渠道凭据"抽象成所有适配器都能实现的 `sync`（官方账号池已有此逻辑），还是各后端自己负责？
4. **首批要接哪些反代工具包**：我按 `new-api / sub2api / one-api` 三个常见形态准备声明式模板，是否合适？是否有你实际在用的站点（给域名/接口形态即可，**不要给凭据**）？
