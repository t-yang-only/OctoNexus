## 1. 一句话目标

把 **bestruirui/octopus**（Web 管理面板 + 渠道管理 + 协议互转 + 转发）与
**BerriAI/litellm**（模型路由/协议转换、下游虚拟子 key、余额/Token 计费、调用明细）
两条能力缝合，**本次升级新增上游渠道监控 + 负载均衡模块**，形成完整的
LLM API 中转聚合平台。**前端继续以 octopus（React19 + Vite + Tailwind）为唯一核心**，不引入 litellm 前端。

## 3. 现有代码接缝（新增模块要挂上去的地方）

- `internal/relay/route.go`：`pickGroupItem` 是唯一选路点，按 `Group.Mode` 分支；
  `RouteState{CurrentItemID, Cooldowns, AffinityUntil, ProbeItemID}` + `recordRouteSuccess/Failure`
  + `publishRouteLocked`（SSE）。**负载均衡 = 在此之上加策略维度；监控 = 喂给它健康信号。**
- `internal/model/group.go`：`GroupMode` 目前 `manual|failover`，`GroupRelayConfig` 已有
  `MemberMaxAttempts/Retry/Timeout/Cooldown/Affinity`。**新增策略需扩 `GroupMode`/config，注意 binding oneof。**
- `internal/model/apikey.go`：已有 `MaxCost`（预算）、`ExpireAt`、`SupportedModels`。
  **虚拟子 key 扩展 = 加限流/余额字段。**
- `internal/op/`：`ChannelStatsList/ChannelList` 供面板；`groupRefreshCache` 刷缓存。
  **监控结果需进 op 缓存供面板与选路读取。**
- `internal/server/handlers/`：`/api/v1/*`（admin 3303）与 `/v1/*`（relay 1234）双端口已拆好。
  **监控面板 API、子 key 明细 API 挂 admin；转发挂 relay。**
- `web/src/`：`modules/channel|group|apikey|log|home` 已有；新增页面按既有 shadcn + react-query 模式。

## 4. 范围判定与拆分（brainstorming：多子系统须先拆）

本需求含**三个可独立交付的子系统**，建议按依赖顺序拆成三份 spec，各自 brainstorming→设计→实施：

1. **M1 上游渠道主动监控**：后台定时对每个 Channel/Grant 发最小探活请求，记录
   健康态（up/down/degraded）、延迟、错误率、最近探测时间；结果进缓存 + 面板展示 + SSE。
   （源自 api-monitor 思路，落到 octopus 的 Channel/Grant 模型。）
2. **M2 负载均衡策略**：在 `pickGroupItem` 之上引入策略枚举（least-latency / least-busy /
   weighted / usage / 现有 failover），与健康信号联动（不健康成员不参与选路）。
   （源自 litellm `router` 策略。）
3. **M3 下游虚拟子 key + 限流 + 调用明细**：扩 APIKey 的预算/RPM/TPM/余额，补请求级
   调用明细（输入/输出 token、费用、耗时、命中成员），面板可视化与导出。
   （源自 litellm virtual key + spend logs。）

依赖：M1 产出健康信号 → M2 消费；M3 相对独立，可与 M1/M2 并行，但明细字段要与 M1 探测、
M2 命中成员打通。**前端全程用 octopus 组件栈。**
