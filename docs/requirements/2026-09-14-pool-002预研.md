## 1. 形态假设：官方账号→渠道模型映射

| 官方账号侧 | octopus 映射 | 说明 |
|---|---|---|
| 一个 OAuth 授权（Google/ChatGPT） | `Channel`（1 渠道=账号池入口）+ `ChannelKey`（1 key=1 授权，`Enabled` 即账号可用） | 多账号=同 Channel 下多 Key（与 53HK 多凭据同形） |
| 账号可调用的模型 | `ChannelModel`（按官方模型名登记） | 与现有"渠道×上游模型"同形 |
| 账号×模型可用组合 | `ChannelGrant`（Protocols 位=该组合实测协议） | 与 53HK grants 同形；协议位由 T-proto-001 矩阵口径实测填充 |
| 客户端可见模型 | `Group`（聚合分组，按需 `Failover`） | 复用现有 group 路由，无需新表 |

- **凭据形态**：OAuth access/refresh token 按 T-acct-001 口径密文落库
  （`OfficialAccount.AccessCipher/RefreshCipher`，响应 JSON 禁明文）；
  转发 key 与探测 token 分离（`ProbeToken` 口径，146 审计）。
- **不新增模型表**：现有四层已能表达"多账号×多模型"；若后续要"按套餐到期排序"，
  在 `ChannelKey` 扩展到期字段而非新表（待 acct-001 落地时定）。

- 现状（186+197）：`internal/relay/balance.go` `rankCandidates` 纯函数已定序口径

  **但 186 claim 明确"未接热路径"**——`handler.go` 仍走 `pickGroupItem`（161/162 展平语义），

     对 eligible 子集调 `rankCandidates` 定序（round 由调用方自增计数持有）；
  2. 冷却键=展平成员行 ID（162 口径），归零集合来自阈值事件打中的授权 ID
     （`zeroBalanceGrantIDs` 参数，调用方=quota 消费链）。
- 缺口（实施前必须补）：
  1. `balance_verify_test.go` 为 186 自带验证单测（在树）——需确认其覆盖"轮转覆盖"

  2. round 计数持有者未定（RouteState 扩展 vs handler 局部）——实施设计时定，本预研不定；

## 4. 余额/停链路口径差异（T-quota-001/002）

- 现状：余额链只读采集（117/147：`FetchBalance`+指纹+阈值事件）+归零停用（124：
  `QuotaZeroStop`+审计）；197 前提成立（负剩余守卫）。
- 官方账号差异：
  1. 套餐制账号（包月/按席）无"剩余额度"数字——`ParseBalancePayload` 会走
     "未知/失败→不停用"分支（163 接线清单第④例），不会误停；
  2. 点数制账号（按量）走现有采集口径（NA `/api/user/self`、S2 三读、
     通用 JSON `FetchCustomBalance`）；
  3. 采集凭证映射（baseURL/monitorToken/useProxy 来源）是 quota-001 实施项
     （B-117 在途），pool-002 实施时直接复用其映射表，不另起配置。
- 跳转页兜底：T-acct-005 跳转页（一次性令牌+120s TTL）是"账号掉线→人工重登"的
  现成兜底，号池实施时直接引用，不重做。

## 5. 合规红线（与 T-acct-001 同口径，不可谈判）

1. 仅官方 OAuth/扫码授权；**禁验证码绕过、禁逆向、禁 cookie 盗用**；
2. 凭据密文落库（`AccessCipher/RefreshCipher`），读回解密仅内存态；
3. 日志/报告/响应 JSON 永不出现 key/token 明文（R-sec-001；本预研零凭据）；
4. 探测 token 与转发 key 分离存储（146 审计口径）。
