## 2. HIGH 发现

### R3-F1：任意账号更新全量重建渠道，静默丢失人工配置

位置：`internal/op/sub2api.go:290-305,465-470`；下游 `internal/op/channel.go:106-180,578`。

Notes 等普通字段更新也重新生成仅含默认字段、default Key、硬编码模型和授权的 ChannelDetail。ChannelUpdate 是完整替换接口，未提供字段会被清零，额外 Key/模型被删除及级联清理授权。自定义端点、计费倍率/包月额度、参数覆盖、专用代理等也可能丢失。

已复现：先通过正规 ChannelUpdate 设置 `/custom/chat`、subscription 计费、900 月额度和 private-model，再只更新账号备注；端点恢复默认、月额度变为 0、private-model 消失。

修复方向：定义账号管理字段和人工管理字段，读取已有渠道并只同步受管字段；模型/Key/授权按稳定身份增量协调。若产品决定完全托管渠道，需要阻止冲突编辑并提供明确迁移规则。

### R3-F2：移除敏感头后无正式转发读取路径，探测与调用不一致

位置：`internal/op/sub2api.go:265-279,299-302`；对照 `internal/relay/channel.go:42,207-220`、`internal/op/sub2api.go:525-570`。

Round 3 删除敏感头复制循环后，新渠道仅保留非敏感头和单一 api_key。Cookie、额外 X-Auth-Token 等保存在账号加密块，relay 只消费 Channel/ChannelKey，没有账号凭据读取或敏感头引用。探测却解密并发送这些头。依赖附加 Cookie 的网关可出现探测成功、正式请求缺鉴权。自定义 Authorization 优先级也未统一，relay 现有代码还保护转换器已生成的敏感头不被覆盖。

已观察：本地 httptest 上游确认探测收到合成 Cookie；同账号 ChannelDetail 无 Cookie。正式链路读取入口缺失由调用路径静态确认；本次未把该观察冒充完整 relay HTTP 端到端测试。

修复方向：设计加密敏感头或稳定凭据引用，正式转发按协议加载注入；probe/relay 共享鉴权构建器，明确默认认证与自定义认证优先级；不支持的组合在保存时拒绝并解释。

### R3-F3：账号/渠道不在同一事务，失败留下已生效的半更新

位置：`internal/op/sub2api.go:450-475`；对照 `internal/op/channel.go:72-103,106-180`。

渠道新建/更新/删除先各自提交、刷新缓存，最后才 Save 账号。最后失败没有回滚；新增物化也可能遗留孤立渠道。Channel CRUD 本身还可能在 DB 提交后因缓存刷新失败返回 error，不能简单当成完全未写入来补偿。

已复现：隔离库注入账号名唯一约束，令最后 Save 失败；渠道 BaseURL 已提交新值、账号保留旧值。唯一索引仅用于故障注入，生产模型当前未声明此唯一约束。

修复方向：提取接收同一 tx 的渠道写入原语，与账号一起提交，提交后刷新缓存；缓存失败形成可重试协调状态。并发更新加入版本检查或合适串行化，并验证账号所有权及关联唯一性。

### R3-F4：解绑吞掉删除错误，返回成功但保留可用孤立渠道

位置：`internal/op/sub2api.go:458-461`。

`_ = ChannelDel(...)` 吞错后仍清零 ChannelID 并保存。即使 DB 删除失败，API 仍成功，旧渠道和选路缓存可继续存在。

已复现：GORM 删除回调仅对 channels 注入错误，解绑返回 nil；账号 ChannelID=0、原启用渠道仍在。该问题区别于 F3：即使最后 Save 成功，也会返回错误的成功结果。

修复方向：仅将可识别的“已不存在”当成幂等完成；其他错误保留绑定并失败。纳入统一事务，处理“已提交、缓存待刷新”，使用哨兵错误而非字符串匹配。

### R3-F5：普通更新吞掉解密/JSON 错误，覆盖为空凭据并同步空 Key

位置：`internal/op/sub2api.go:376-393,431-440,467-469`。

本轮把凭据读写从请求含 Key/Headers 才执行扩展到每次更新。解密/JSON 失败被忽略，plainKey 默认空，随后空凭据重封覆盖原数据并同步渠道 Key。坏密文、异密钥恢复、格式损坏时，修改备注可能破坏可恢复密文和仍可用的渠道 Key。

已复现：将账号密文替换成无效数据，再只修改备注，API 成功；原密文变成有效但空 api_key/headers 密文，渠道 Key 同时变空。

修复方向：解密和结构校验失败明确报错、禁止写入；无关修改不无条件重封凭据。显式替换全部凭据与普通更新分开定义，保留旧密文恢复路径，不自动空值降级。

## 3. MEDIUM 与继承风险

位置：本提交仅改变构造器；`internal/db/migrate/017.go` 只清理旧索引，`internal/op/sub2api.go:64` 列表只读取数据。

修复方向：完成 F2 安全运行时通路后，按账号所有权迁移存量；幂等、可报告冲突、迁移前有恢复备份，日志不打印值。旧备份单独处理，按实际暴露情况考虑轮换。

### R3-F7：禁用账号物化出的渠道 enabled 仍被 GORM default:true 改为 true

位置：`internal/op/sub2api.go:290-302,314`；`internal/model/channel.go:83`；现有 false 测试 `internal/op/sub2api_test.go:111` 未开启 SyncChannel。

已复现：Enabled=false、SyncChannel=true，账号 false、渠道 true。default Key 当前保持 false，不能据此宣称立即出现可路由越权；但管理状态不一致，后续加 Key/人工启用 Key 会扩大风险。修复 ChannelCreate 显式保留 false，覆盖账号/渠道/Key/授权候选和重启读回。

### R3-F8：管理面没有更新入口，客户端缓存与 DTO 契约不足

位置：`web/src/components/modules/account/index.tsx:39-143`；`web/src/api/sub2api.ts:130`。

useUpdateSub2APIAccount 已定义，但卡片只接探测/删除，缺编辑、换 Key、启停、解绑及同步错误恢复。mutation 仅失效账号列表，未主动刷新渠道/分组。Partial<CreatePayload> 允许提交后端 UpdateRequest 不接受的 platform/account_type，容易出现静默无效更新。

修复方向：专用 UpdatePayload；补编辑/恢复入口，失效关联查询，展示可定位的同步状态。

其他继承限制，不重复计为本提交新缺陷：AccountType/AccountMode/RateLimit 大多仍是元数据，未形成对应认证流程或执行限制；模型硬编码；探测固定 GET /v1/models，200 HTML 也可能成功，不能证明三协议调用闭环。备份表已纳入导入导出，且有往返测试，但跨主密钥恢复、引用一致性和恢复后调用仍需专项验收。不能据此宣布旧 F1-F8 全部关闭。
