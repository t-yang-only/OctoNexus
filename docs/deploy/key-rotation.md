# 线上 key 轮换清单（T-sec-001）

## 为什么必须做

v0.13.4 及之前，octopus 把上游渠道凭据**明文**写进 `channel_keys.key`。也就是说：

- 数据库文件被读过（运维、备份、同步盘、误传）；
- 或者任何一个明文时代的备份文件（`数据备份*.json`）被复制过；

那么那些**旧凭据值就已经算泄露**。v0.14.0 的静态加密只改变"以后怎么存"，无法追回旧值。
唯一正确的处置是：**在服务商侧吊销旧 key，换发新 key**。

## 轮换对象（按优先级）

| # | 对象 | 在哪换 | 为什么 |
| --- | --- | --- | --- |
| 1 | 各上游渠道凭据（渠道页每一条 key） | 服务商控制台生成新 key | 明文时代直接落库，风险最高 |
| 2 | 面板管理员口令 | 面板 → 用户（首次登录默认 admin/admin） | 默认口令在线上的暴露面 |
| 3 | 客户端 API Key（`api_keys` 表） | 面板 → 密钥 → 重新生成 | 旧值在明文日志/备份里出现过 |
| 4 | 通知渠道凭据（Server酱 SendKey / SMTP 口令 / 机器人 webhook） | 各服务商控制台 | 出现在设置表里，也进过备份 |
| 5 | 官方账号 token（若有） | 面板 → 官方账号重新授权 | 本就加密存储，但轮换成本低 |

## 步骤（每个渠道重复）

1. **生成新 key**：到服务商控制台新建一把 key，权限与原 key 一致。
2. **替换**：面板 → 渠道 → 编辑 → 对应凭据行填新 key → 保存。
   - 该渠道下有多个模型共用这条凭据时，只要不动模型与授权，替换后立刻生效（不需要重启）。
3. **验证**：用这个渠道所在的分组发一条真实请求（面板日志页能看到这次请求），确认 200 且
   "判定理由"里指向的是这个渠道。
   - 若失败：看日志的 `上游轮次`——第一次就失败说明 key 不对；换过成员才成功说明渠道本身有问题。
4. **吊销旧 key**：确认新 key 工作后再回服务商控制台删掉旧 key。
   - 顺序不能反：先删旧 key 会让线上在替换完成前中断。
5. **记账**：在下面表格里打勾（谁、什么时候、旧值是否已吊销）。

## 明文时代备份的处置

轮换全部完成之后，旧备份里的凭据就都是**已吊销的死值**了，处置建议：

- 保留最近一份（回滚要用），但把它从任何同步盘/共享目录里移走；
- 其余旧备份删除；
- 此后的备份里凭据是密文（`enc:v1:`），但**仍建议与 `credential.key` 分开保管**：
  密文与密钥放在一起，等于没加密。

> 顺带说明：v0.14.0 的备份转储（`DBDump`）里凭据是密文而不是脱敏删除——这是刻意的取舍，
> 备份的可恢复性优先。真正需要"导出即脱敏"的场景（例如把配置交给别人排查）本轮未做，
> 需要的话单独提，那是另一件事。
