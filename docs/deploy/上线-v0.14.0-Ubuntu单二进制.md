# 上线运行手册：v0.14.0（Ubuntu 单二进制）

本手册对应**发布件**：`octopus-linux-amd64`（linux/amd64，单二进制，前端已内嵌，不需要 nginx 托管静态文件）。
约束来源：`docs/requirements/2026-09-13-Ubuntu部署约束.md`（目标 Ubuntu、不打包 exe）。

## 0. 上线前必做：key 轮换（T-sec-001）

**先做这一步再看后面的内容**。理由是历史事实：v0.13.4 及之前，`channel_keys.key` 是**明文**落库的，
你的生产库、以及在这个状态下产生的任何备份文件，都可能已经把上游凭据暴露出去。
升级只保护"升级之后"的存储形态，**不会追回已经泄露的旧值**——旧值必须在服务商侧吊销并换新。

逐条清单与操作步骤见同目录的 `key-rotation.md`。轮换完成后在下面第 6 节的检查表里打勾。

## 1. 备份（不可跳过）

```bash
# 在服务端，以运行实例的用户身份
systemctl stop octonexus            # 先停，避免备份到半写状态
tar czf ~/octonexus-backup-$(date +%F-%H%M).tgz -C /opt octonexus
```

要备份的东西按重要性排序：

| 内容 | 为什么 |
| --- | --- |
| `data/credential.key` | **渠道凭据的解密密钥**（本轮新增）。丢了它，升级后加密的凭据一条都解不开，只能在面板逐条重填 |
| `data/data.db`（含 `-wal`/`-shm`） | 全部渠道/分组/日志/统计 |
| `data/config.json` | 端口、数据库路径等 |
| 旧二进制 `octopus` | 回滚要用（见第 4 节，回滚有额外注意） |

> 如果你更希望用 `OCTOPUS_OFFICIAL_KEY` 环境变量作为密钥（与官方账号共用一把），
> 就在 systemd 单元里设它，并把它的值单独保存在密码管理器里；此时 `credential.key` 不会生成，
> 也就没有"这个文件丢了怎么办"的问题。两条路都可以，**不要两处都设**（环境变量优先，会盖掉文件）。

## 2. 替换二进制

```bash
install -m 0755 octopus-linux-amd64 /opt/octonexus/octopus.new
mv /opt/octonexus/octopus /opt/octonexus/octopus.old     # 保留旧件供回滚
mv /opt/octonexus/octopus.new /opt/octonexus/octopus
```

systemd 单元模板见同目录 `octonexus.service`（`WorkingDirectory=/opt/octonexus`，`data/` 落在同目录）。

## 3. 启动与检查清单

```bash
systemctl start octonexus
journalctl -u octonexus -n 60 --no-pager
```

日志里应当出现（顺序不固定）：

| 应当看到 | 含义 |
| --- | --- |
| `Version:    v0.14.0` | 新版本真的起来了（旧件回滚时这行会变回旧版本） |
| `渠道凭据静态加密已启用（密钥来源：…）` | 凭据加密生效；来源是环境变量名或 `credential.key` 路径 |
| `渠道凭据加密：N/M 行明文已转为密文` | 存量凭据已加密（N 可能为 0，表示此前已加密过） |
| `渠道凭据补加密：N 行明文已转为密文` | 启动时的补加密（备份导入回来的明文也会在这里被补上） |
| `服务已启动` 之类 + 两个端口 | admin 与 relay 都在监听 |

再跑一遍功能性检查（用你真实的一把客户端 Key）：

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  -H "Authorization: Bearer <你的客户端Key>" -H 'Content-Type: application/json' \
  -d '{"model":"<你的分组名>","messages":[{"role":"user","content":"ping"}],"max_tokens":16}' \
  http://127.0.0.1:1234/v1/chat/completions
# 期望 200；面板 → 日志里这一条应能看到「上游轮次」与「判定理由」两列
```

面板侧检查（浏览器打开 admin 端口）：登录 → 首页余额卡片有数 → 日志页有字段开关（首字时间/上游轮次/判定理由）
→ 渠道页能正常编辑并看到凭据明文（admin-only，这是设计口径）。

## 4. 回滚

```bash
systemctl stop octonexus
mv /opt/octonexus/octopus /opt/octonexus/octopus.failed
mv /opt/octonexus/octopus.old /opt/octonexus/octopus
systemctl start octonexus
```

⚠️ **回滚前必须先处理凭据**：v0.14.0 会把凭据写成密文（`enc:v1:` 前缀），老版本不认识这个前缀，
会把密文**当成 API key 原样发给上游**，表现为全线 401。两个可选做法：

1. 推荐：整目录回滚 —— 用第 1 节的备份把 `data/` 一起还原（回到升级前的明文状态）；
2. 或者：在面板里把受影响的渠道凭据**重新填一遍明文**（面板写的是解密后的明文，老版本能读）。

数据库结构本身是向后兼容的（新增列/新表，不改旧列语义），所以回滚不需要动 schema。

## 5. 本次升级会改动什么（数据面）

| 迁移 | 作用 | 影响 |
| --- | --- | --- |
| 014 | 给存量分组回填 `member_stream_idle_timeout_seconds=300` | 上游"首帧后不再出字"的流式请求会在 300 秒内被主动掐断并记账为真实失败（此前会挂到客户端放弃） |
| 015 | 把存量明文渠道凭据加密 | 幂等；无可用密钥时**跳过并告警**，不会把启动卡死 |
| 新增列/表 | 分组：`smart_route_threshold`、成员 `smart_tier`；日志：`attempts`、`decision`；设置：`relay_request_fault_action`、`balance_points_per_unit`、`balance_currency`、`pool_declarative_hosts`、`pool_declarative_adapters` 等 | AutoMigrate 自动加，旧数据不动 |

## 7. 已知运营项（都不需要改代码）

1. **Caddy 会掐流式响应**：线上日志（`docs/worklog/2026-09-13-线上部署日志核查071.md`）已定位
   `Caddy` 默认 15 秒冲刷/超时会切断 SSE。Caddyfile 里对该反代路由加：
   ```
   reverse_proxy 127.0.0.1:1234 {
       flush_interval -1
   }
   ```
   Nginx 对应的是 `proxy_buffering off;` + `proxy_read_timeout 3600s;`。
2. **价格/模型信息更新失败**：日志里的 `direct request failed, context deadline exceeded` +
   `download failed: proxy url is empty` 是"服务器没有出网代理"导致的，属环境；需要更新价格时给实例配代理。
3. **端口**：默认 admin 3303 / relay 1234。生产建议保持默认或用 `OCTOPUS_SERVER_ADMIN_PORT` /
   `OCTOPUS_SERVER_RELAY_PORT` 覆盖（本次发布件在 WSL 冒烟里用的是 23303/21234，见下）。
